Why ML-KEM is secure and how the numbers were chosen

9.1 Security models

IND-CPA (Indistinguishability under Chosen Plaintext Attack)

In this model, an adversary:

  1. Receives the public key \(ek\)
  2. Chooses two messages \(m_0, m_1\)
  3. Receives the ciphertext of one of them (chosen at random)
  4. Must guess which message was encrypted

The scheme is secure if: \(\Pr[\text{guesses}] \leq 1/2 + \text{negl}(\lambda)\).

K-PKE (the base encryption component) is IND-CPA under the MLWE assumption.

IND-CCA2 (Indistinguishability under Adaptive Chosen Ciphertext Attack)

Like CPA, but the adversary can also query a decryption oracle on any ciphertext (except the challenge one). This model captures real-world attacks (like Bleichenbacher), where an active adversary sends ad-hoc messages and observes responses.

ML-KEM is IND-CCA2. This is the level required for a secure KEM in real protocols like TLS or SSH.

ROM vs. QROM

Security proofs use idealized models for hash functions:

  • ROM (Random Oracle Model): hashes are perfect random oracles.
  • QROM (Quantum Random Oracle Model): the quantum adversary can query the oracle in superposition.

Modern proofs for the FO (Fujisaki-Okamoto) transformation used in ML-KEM guarantee security in the QROM, essential against quantum adversaries.

9.2 How to measure the difficulty of MLWE

Security as attack cost

There is no absolute proof that MLWE is hard. Security is estimated by computing the cost of the best known attack algorithm. A security of \(\lambda\) bits means that the attack requires about \(2^\lambda\) operations.

The parameters

The difficulty depends on:

  • \(n = 256\) (polynomial dimension, fixed)
  • \(k \in \{2, 3, 4\}\) (module dimension)
  • \(q = 3329\) (prime modulus)
  • \(\eta \in \{2, 3\}\) (noise width)

Lattice Estimator

The standard tool is the Lattice Estimator by Albrecht et al. For ML-KEM-768:

Attack Estimated cost (bits)
Primal attack (BKZ) ~178 bits
Dual attack ~175 bits
Combinatorial > 200 bits

The security margin is large compared to the 128-bit classical/quantum target.

9.3 Main attacks on lattices

BKZ (Block Korkine-Zolotarev)

This is the best general algorithm for finding short vectors. It divides the lattice into blocks of size \(\beta\) and solves SVP locally. Complexity: \(2^{O(\beta \log \beta)}\). For ML-KEM-768, \(\beta \approx 430\).

Primal attack (uSVP)

Reduces MLWE to a short vector problem in an augmented lattice containing the public key and ciphertext. The secret vector \((\mathbf{s}, \mathbf{e}, -1)\) becomes a short vector that BKZ tries to find.

Dual attack

Exploits the dual lattice to distinguish MLWE samples from uniform ones using statistics. Builds many short vectors in the dual to perform the distinguisher.

Choice of q = 3329

Being prime and lacking special algebraic structure, it prevents specific algebraic attacks. There are no small factors or simple relations that could be exploited.

9.4 NIST security levels

NIST defined 5 levels. ML-KEM covers levels 1, 3 and 5:

Scheme NIST Level Classical Security Quantum Security
ML-KEM-512 1 (AES-128) ~118 bits ~100 bits
ML-KEM-768 3 (AES-192) ~178 bits ~164 bits
ML-KEM-1024 5 (AES-256) ~230 bits ~218 bits

Recommendation: ML-KEM-768 offers the optimal security/performance balance for most use cases. ML-KEM-1024 is reserved for extremely high-criticality systems.

9.6 Side-channel and secure implementations

A correct implementation can be vulnerable if it leaks information through execution timing or power consumption.

Constant-Time (CT)

All operations must have constant time regardless of secret data. Critical example in Decaps:

// NOT secure (variable timing):
if (memcmp(c, c_prime, len) == 0) { 
    K = K_good; 
} else { 
    K = K_reject; 
}

// Secure (constant-time):
uint8_t mask = ct_memcmp(c, c_prime, len); // 0xFF if equal, 0x00 if different
K = ct_select(mask, K_good, K_reject);     // CT selection without branch

Critical areas for CT in ML-KEM

  • \(B_\eta\) sampling: bit additions without conditional branches.
  • NTT: butterfly operations must always be executed, even if the result doesn't change.
  • Ciphertext verification: use of ct_memcmp.

Reference implementations

  • pqclean: portable CT implementations.
  • liboqs: AVX2 optimizations with verified CT properties.

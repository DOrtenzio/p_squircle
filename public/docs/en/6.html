6.1 Formal definition of KEM

Triple of algorithms

A Key Encapsulation Mechanism (KEM) is a triple of probabilistic polynomial-time algorithms:

\[ \text{KEM} = (\text{KeyGen},\ \text{Encaps},\ \text{Decaps}) \]
  • KeyGen() → (ek, dk)
    Probabilistic algorithm (uses internal randomness). Takes no input.
    • ek: encapsulation key (public key)
    • dk: decapsulation key (private key)
  • Encaps(ek) → (K, c)
    Given ek, produces:
    • \(K \in \{0,1\}^\ell\): symmetric secret key (typically 256 bits)
    • c: ciphertext (the "capsule")
  • Decaps(dk, c) → K
    Given dk and c, recovers \(K\).

FIPS 203 terminological note: the standard uses ek for encapsulation key (not pk) and dk for decapsulation key (not sk). The distinction is intentional: it emphasizes that the public key is used to encapsulate, not to encrypt arbitrary messages.

Correctness

A KEM is correct if for every valid key pair:

\[ \Pr\bigl[\text{Decaps}(dk,\, c) = K \mid (K, c) \leftarrow \text{Encaps}(ek)\bigr] \geq 1 - \delta \]

where \(\delta\) is a negligible error probability (typically \(< 2^{-128}\)).
For ML-KEM-768: \(\delta < 2^{-142}\).

6.2 Security properties

IND-CPA (Indistinguishability under Chosen Plaintext Attack)

IND-CPA security game

Challenger Adversary \(\mathcal{A}\)
\((ek, dk) \leftarrow \text{KeyGen}()\)
\(ek \longrightarrow\)
Chooses challenge (implicit in KEM)
\((K_0, c) \leftarrow \text{Encaps}(ek)\)
\(K_1 \leftarrow \text{Random}\)
\(b \leftarrow \{0, 1\}\)
\((c, K_b) \longrightarrow\)
Returns \(b'\)

Advantage: \(\text{Adv}^{\text{IND-CPA}}_{\text{KEM}}(\mathcal{A}) = \left| \Pr[b' = b] - \frac{1}{2} \right|\)

The KEM is IND-CPA if the advantage is negligible for every polynomial-time adversary. Intuitively: the adversary cannot distinguish the real key \(K\) from a random one, even seeing the ciphertext c.

IND-CCA2 (Indistinguishability under Adaptive Chosen Ciphertext Attack)

Like CPA, but the adversary also has access to a decapsulation oracle:

Phase Action
Initialization \((ek, dk) \leftarrow \text{KeyGen}()\), sends \(ek\)
Phase 1 (Query) \(c_i \to K_i = \text{Decaps}(dk, c_i)\)
Challenge \((K_0, c^*) \leftarrow \text{Encaps}(ek)\), \(K_1 \leftarrow \text{Random}\), \(b \leftarrow \{0,1\}\). Sends \((c^*, K_b)\).
Phase 2 (Query) \(c_j \to K_j = \text{Decaps}(dk, c_j)\) with \(c_j \neq c^*\)
Guess Returns \(b'\)

IND-CCA2 is the security standard required for KEMs in real-world use.

Why is CCA2 necessary? In a real protocol (TLS, SSH), an active adversary can send manipulated ciphertexts and observe the server's responses. Even in MLWE, an adversary who knows the decapsulation of ciphertexts close to the challenge ciphertext could extract information about the secret. ML-KEM is IND-CCA2.

Additional desirable properties

  • Robustness: hard to construct ciphertexts that decapsulate to the same key with two different private keys.
  • Forward secrecy: if the private key dk is compromised in the future, past sessions remain secure (requires ephemeral keys).

6.3 KEM vs PKE: why KEMs

PKE (Public Key Encryption)

A PKE encrypts arbitrary messages: \(\text{Enc}(ek, m) \to c\). The problem is that if the message \(m\) has predictable structure (short password, card number), an adversary can exploit low-entropy attacks or padding oracle attacks (Bleichenbacher).

KEM: separation of roles

The KEM does not encrypt user messages. It generates a high-entropy symmetric key and encapsulates it:

\[ \text{System} = \underbrace{\text{KEM}}_{\text{exchanges } K} + \underbrace{\text{AES-GCM}}_{\text{encrypts data with } K} \]

Advantages:

  • The key \(K\) is always pseudorandom → no low-entropy attacks.
  • No complex padding needed for user messages.
  • \(K\) is used with a symmetric cipher (DEM) to encrypt the actual data.

6.4 Intuitive example: KEM from Diffie-Hellman

Before ML-KEM, the most widely used KEM was built on Diffie-Hellman. This example helps understand the structure.

Public parameters: prime \(p\), generator \(g\) of \(\mathbb{Z}_p^*\).

Alice
  1. Chooses secret \(a\)
  2. Computes \(A = g^a \bmod p\)
A → ← B
Bob
  1. Chooses secret \(b\)
  2. Computes \(B = g^b \bmod p\)
\[ \begin{aligned} \text{Alice computes: } & K = B^a \bmod p = g^{ab} \bmod p \\ \text{Bob computes: } & K = A^b \bmod p = g^{ab} \bmod p \end{aligned} \]

Numerical example: \(p = 17\), \(g = 3\), \(a = 5\).

  • \(ek = 3^5 \bmod 17 = 5\)
  • Bob chooses \(b = 7\): \(c = 3^7 \bmod 17 = 11\), \(K = H(5^7 \bmod 17) = H(10)\)
  • Alice decapsulates: \(K = H(11^5 \bmod 17) = H(10)\) ✓

6.5 The Fujisaki-Okamoto (FO) transformation

The problem: from CPA to CCA2

Starting from a CPA-secure PKE, how do you build an IND-CCA2 KEM? The answer is the FO transformation.

Core idea

  • Deterministic encryption: the randomness used in encryption is deterministically derived from the message via a hash. If the ciphertext is modified, re-encryption produces something different.
  • Verification in decryption: instead of decrypting directly, re-encrypt the decrypted message and compare with the received ciphertext. If they don't match → implicit rejection.

Simplified FO scheme

\[ \begin{aligned} \text{Encaps}(ek): & \quad m \leftarrow \{0,1\}^\ell, \ (K, r) = G(m), \ c = \text{Enc}(ek, m; r) \\ \text{Decaps}(dk, c): & \quad m' = \text{Dec}(dk, c), \ (K', r') = G(m'), \ c' = \text{Enc}(ek, m'; r') \\ & \quad \text{return } \begin{cases} K' & \text{if } c' = c \\ K_{\text{reject}} & \text{otherwise} \end{cases} \end{aligned} \]

Where \(K_{\text{reject}} = H(z \| c)\) with \(z\) fixed secret. This "implicit reject" prevents the adversary from using errors as an oracle.

6.6 From K-PKE (CPA) to ML-KEM (CCA2)

In ML-KEM, the two-level structure is:

ML-KEM (IND-CCA2)
└── K-PKE (IND-CPA) + FO transformation
    └── MLWE problem

ML-KEM.Encaps(ek)

m ← Random(32)                  // 256-bit random message
(K̄, r) = G(m ‖ H(ek))          // SHA3-512: K̄ = first 32 bytes, r = last 32 bytes
c = K-PKE.Encrypt(ek, m, r)     // deterministic encryption with randomness r
K = KDF(K̄ ‖ H(c))              // final key
return (K, c)

ML-KEM.Decaps(dk, c)

(dk_PKE, ek, h, z) = dk         // h = H(ek), z = fallback secret
m' = K-PKE.Decrypt(dk_PKE, c)   // decryption attempt
(K̄', r') = G(m' ‖ h)           // recompute
c' = K-PKE.Encrypt(ek, m', r')  // re-encryption for verification
if c' == c:
    K = KDF(K̄' ‖ H(c))         // decryption successful
else:
    K = KDF(z ‖ H(c))           // fallback: pseudorandom key
return K

Important details: The private key dk also contains ek to allow re-encryption. The comparison c' == c must be constant-time.

6.7 KEM in a real protocol: TLS 1.3

Client (Bob)
Server (Alice)
ClientHello (supports ML-KEM-768)
ServerHello + Certificate + KeyShare (ek)
KeyShare (c) + Finished (MAC with K)
Finished (MAC with K)

X25519 + ML-KEM hybrid

In practice, TLS 1.3 uses a hybrid approach:

\[ K_{\text{TLS}} = \text{HKDF}(K_{\text{X25519}} \,\|\, K_{\text{ML-KEM}}) \]

This ensures security if at least one of the two schemes holds. The X25519MLKEM768 group is already deployed in Chrome 131+.

6.8 Generic structure of the KEM flow

Complete flow Alice (Recipient) / Bob (Sender)

  1. Alice: KeyGen() generates \((ek, dk)\). Publishes \(ek\).
  2. Bob: Receives \(ek\). Runs Encaps(ek):
    • Generates random \(m\)
    • \((\bar{K}, r) = G(m \| H(ek))\)
    • \(c = \text{K-PKE.Encrypt}(ek, m, r)\)
    • \(K = \text{KDF}(\bar{K} \| H(c))\)
  3. Bob: Encrypts data with AES-256-GCM using \(K\) and a random nonce.
  4. Bob: Sends \((c, \text{nonce}, \text{ciphertext}, \text{tag})\) to Alice.
  5. Alice: Runs Decaps(dk, c) to recover \(K\).
  6. Alice: Decrypts data with AES-256-GCM. If the tag fails, discards the message.

Double protection: If c is tampered with, Decaps returns a pseudorandom key (\(K_{\text{reject}}\)). Even if the adversary guesses this key, the AEAD tag in AES-GCM would fail, ensuring integrity.

10.1 liboqs: la bibliothèque C de référence

liboqs est la bibliothèque C de référence pour la cryptographie post-quantique, développée par le projet Open Quantum Safe (OQS). Elle fournit des implémentations optimisées et en temps constant de ML-KEM et d'autres algorithmes PQC standardisés par le NIST.

Installation depuis les sources

# Dépendances (Ubuntu/Debian)
sudo apt-get install cmake gcc libssl-dev

# Clone et build
git clone https://github.com/open-quantum-safe/liboqs.git
cd liboqs
mkdir build && cd build
cmake -DCMAKE_INSTALL_PREFIX=/usr/local ..
make -j$(nproc)
sudo make install

10.2 Exemple complet: KEM avec ML-KEM-768 en C

#include <stdio.h>
#include <string.h>
#include <oqs/oqs.h>

int main() {
    OQS_STATUS rc;
    const char *kem_alg = OQS_KEM_alg_ml_kem_768;

    // Initialise l'algorithme
    OQS_KEM *kem = OQS_KEM_new(kem_alg);
    if (kem == NULL) {
        fprintf(stderr, "KEM non supporté\n");
        return 1;
    }

    printf("Algorithme: %s\n", kem->method_name);
    printf("Clé publique: %zu octets\n", kem->length_public_key);
    printf("Clé privée: %zu octets\n", kem->length_secret_key);
    printf("Chiffré: %zu octets\n", kem->length_ciphertext);
    printf("Secret partagé: %zu octets\n\n", kem->length_shared_secret);

    // Allocation mémoire
    uint8_t *pk = malloc(kem->length_public_key);
    uint8_t *sk = malloc(kem->length_secret_key);
    uint8_t *ct = malloc(kem->length_ciphertext);
    uint8_t *ss_enc = malloc(kem->length_shared_secret);
    uint8_t *ss_dec = malloc(kem->length_shared_secret);

    // 1. KeyGen (Alice)
    rc = OQS_KEM_keypair(kem, pk, sk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "KeyGen échouée\n"); return 1; }
    printf("✓ KeyGen terminée\n");

    // 2. Encaps (Bob: ne connaît que pk)
    rc = OQS_KEM_encaps(kem, ct, ss_enc, pk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "Encaps échouée\n"); return 1; }
    printf("✓ Encaps terminée\n");

    // 3. Decaps (Alice: utilise sk pour ouvrir ct)
    rc = OQS_KEM_decaps(kem, ss_dec, ct, sk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "Decaps échouée\n"); return 1; }
    printf("✓ Decaps terminée\n\n");

    // 4. Vérification
    if (memcmp(ss_enc, ss_dec, kem->length_shared_secret) == 0) {
        printf("✅ Les secrets partagés correspondent!\n");
        printf("   Premiers octets: ");
        for (int i = 0; i < 8; i++) printf("%02x", ss_enc[i]);
        printf("...\n");
    } else {
        printf("❌ ERREUR: secrets partagés différents!\n");
    }

    // Nettoyage sécurisé de la mémoire
    OQS_MEM_cleanse(sk, kem->length_secret_key);
    OQS_MEM_cleanse(ss_enc, kem->length_shared_secret);
    OQS_MEM_cleanse(ss_dec, kem->length_shared_secret);
    free(pk); free(ct);
    OQS_KEM_free(kem);
    
    return 0;
}

Compilation:

gcc -o kem_example kem_example.c -loqs -lcrypto
./kem_example

10.3 Utiliser la clé dérivée avec AES-256-GCM

Après avoir obtenu le secret partagé de ML-KEM, il est possible de l'utiliser comme clé pour un chiffrement symétrique. En production, il est recommandé d'utiliser HKDF pour dériver des clés séparées.

#include <openssl/evp.h>
#include <oqs/oqs.h>

// Après avoir obtenu ss (32 octets) de ML-KEM:
void encrypt_with_kem_key(const uint8_t *ss, const uint8_t *plaintext,
                           size_t pt_len, uint8_t *ciphertext, uint8_t *tag,
                           const uint8_t *nonce) {
    EVP_CIPHER_CTX *ctx = EVP_CIPHER_CTX_new();
    int len;

    // Initialise AES-256-GCM
    EVP_EncryptInit_ex(ctx, EVP_aes_256_gcm(), NULL, NULL, NULL);
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_IVLEN, 12, NULL);
    
    // Utilise le secret partagé comme clé
    EVP_EncryptInit_ex(ctx, NULL, NULL, ss, nonce);
    
    // Chiffrement
    EVP_EncryptUpdate(ctx, ciphertext, &len, plaintext, pt_len);
    EVP_EncryptFinal_ex(ctx, ciphertext + len, &len);
    
    // Récupère le tag d'authentification
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_GET_TAG, 16, tag);
    
    EVP_CIPHER_CTX_free(ctx);
}

10.4 Python: bindings liboqs

Liboqs fournit des bindings Python officiels pour des tests rapides et du prototypage.

pip install liboqs-python
import oqs

# Algorithme disponible
kem = oqs.KeyEncapsulation("ML-KEM-768")

# KeyGen
public_key = kem.generate_keypair()

# Encaps (côté Bob)
kem_bob = oqs.KeyEncapsulation("ML-KEM-768")
ciphertext, shared_secret_enc = kem_bob.encap_secret(public_key)

# Decaps (côté Alice)
shared_secret_dec = kem.decap_secret(ciphertext)

assert shared_secret_enc == shared_secret_dec
print(f"✓ Secret partagé: {shared_secret_enc.hex()[:16]}...")

kem.free()
kem_bob.free()

10.5 Python: kyber-py (pédagogique uniquement)

À des fins purement éducatives, il existe une implémentation Python pure qui ne nécessite pas de bibliothèques C externes.

Attention: kyber-py n'est pas en temps constant et ne doit pas être utilisé en production.

                    
                        from kyber import Kyber768
                        kem = Kyber768()
                        pk, sk = kem.keygen()
                        key, ciphertext = kem.enc(pk)
                        _key = kem.dec(sk, ciphertext)
                        assert key == _key

10.6 Benchmarks de performance

Benchmarks sur Intel Core i7-12700K (un cœur, sans instructions SIMD):

Opération ML-KEM-512 ML-KEM-768 ML-KEM-1024
KeyGen 24 µs 37 µs 54 µs
Encaps 28 µs 43 µs 62 µs
Decaps 32 µs 48 µs 70 µs

Avec optimisations AVX2

Opération ML-KEM-768 (sans SIMD) ML-KEM-768 (AVX2) Accélération
KeyGen 37 µs ~10 µs ~3.7×
Encaps 43 µs ~12 µs ~3.6×
Decaps 48 µs ~13 µs ~3.7×

Comparaison avec ECDH X25519

X25519 ML-KEM-768
KeyGen ~14 µs ~37 µs
Échange ~30 µs ~48 µs
Clé publique 32 B 1184 B

ML-KEM est environ 2× plus lent que X25519, mais le surcoût sur la latence du handshake TLS est négligeable (< 1 ms) sur la plupart des connexions réelles.

10.7 OpenSSL: installation du provider OQS

OpenSSL 3.x supporte ML-KEM via le provider oqsprovider. À partir de la version 3.4, le support est natif ou facilement intégrable.

# Build oqs-provider
git clone https://github.com/open-quantum-safe/oqs-provider.git
cd oqs-provider
cmake -DOPENSSL_ROOT_DIR=/usr/local/ssl .
make
sudo make install

# Vérification
openssl list -providers
# devrait lister: oqsprovider

10.8 Génération de clés ML-KEM avec OpenSSL CLI

# Génère une paire de clés ML-KEM-768
openssl genpkey -algorithm mlkem768 -out private.pem
openssl pkey -in private.pem -pubout -out public.pem

# Affiche les détails de la clé
openssl pkey -in private.pem -text -noout

10.9 TLS 1.3 avec ML-KEM-768

Test local (serveur + client)

# Serveur
openssl s_server -accept 4433 -cert server.crt -key server.key \
    -groups mlkem768

# Client (dans un autre terminal)
openssl s_client -connect localhost:4433 -groups mlkem768

Vérifier les groupes supportés

openssl list -key-exchange-algorithms | grep -i kem

10.10 Stratégie hybride: X25519 + ML-KEM-768

L'approche recommandée pour la migration est l'hybridisation: combiner ECDH (X25519) avec ML-KEM-768. La clé finale est dérivée des deux:

\[ K = \text{HKDF}(K_{\text{X25519}} \| K_{\text{ML-KEM}}) \]

Avantage: sécurisé si au moins l'un des deux schémas tient. Si un ordinateur quantique casse X25519, ML-KEM protège. Si ML-KEM avait un défaut inconnu, X25519 protège.

10.11 Suites de chiffrement hybrides dans TLS 1.3

Nom du Groupe Composition
X25519MLKEM768 X25519 + ML-KEM-768
SecP256r1MLKEM768 P-256 + ML-KEM-768

À partir de Chrome 131 (fin 2024), X25519MLKEM768 est le groupe par défaut. Firefox 128+ supporte le même groupe.

Configuration OpenSSL

# Serveur qui accepte à la fois X25519 classique et le groupe hybride
openssl s_server -accept 4433 -cert server.crt -key server.key \
    -groups X25519MLKEM768:x25519:P-256

# Client qui préfère le groupe hybride
openssl s_client -connect localhost:4433 \
    -groups X25519MLKEM768:x25519

10.12 Intégration dans des applications C avec OpenSSL

#include <openssl/ssl.h>
#include <openssl/err.h>

SSL_CTX *create_pqc_context(void) {
    SSL_CTX *ctx = SSL_CTX_new(TLS_server_method());
    if (!ctx) {
        ERR_print_errors_fp(stderr);
        return NULL;
    }

    // Définit les groupes préférés: hybride d'abord, puis classiques en repli
    if (SSL_CTX_set1_groups_list(ctx, "X25519MLKEM768:x25519:P-256") != 1) {
        fprintf(stderr, "Erreur de configuration des groupes\n");
        SSL_CTX_free(ctx);
        return NULL;
    }

    return ctx;
}

10.13 Checklist de migration

Pour les développeurs d'applications

  • Inventorier où la cryptographie asymétrique est utilisée (échange de clés, signature, KEM).
  • Identifier quelles données doivent rester secrètes pendant plus de 5 ans.
  • Mettre à jour les dépendances: OpenSSL ≥ 3.2, liboqs ≥ 0.10.
  • Adopter une approche hybride: X25519 + ML-KEM-768 pour TLS.
  • Pour les signatures numériques: migrer vers ML-DSA (FIPS 204) ou SLH-DSA (FIPS 205).
  • Tester la taille augmentée des clés et des chiffrés dans les protocoles.
  • Vérifier que les timeouts et les tailles de tampon ne supposent pas de petites clés.

Pour les gestionnaires d'infrastructure

  • Mettre à jour la pile TLS vers des versions avec support ML-KEM.
  • Activer X25519MLKEM768 sur les serveurs TLS.
  • Surveiller la compatibilité client (Chrome 131+, Firefox 128+ supportent PQC hybride).
  • Planifier la rotation des clés à long terme.

Normes de référence

Norme Contenu
FIPS 203 ML-KEM (Key Encapsulation)
FIPS 204 ML-DSA (signature numérique sur treillis)
FIPS 205 SLH-DSA (signature basée sur hachage, conservative)

10.14 Scénario: migration d'une API REST

Situation actuelle (pré-migration)

Client → TLS 1.3 avec X25519 → Serveur API

Phase 1: hybride (aujourd'hui, recommandé)

Client → TLS 1.3 avec X25519MLKEM768 → Serveur API

# Configuration nginx
ssl_ecdh_curve X25519MLKEM768:x25519:P-256;

# Configuration Apache
SSLOpenSSLConfCmd Curves X25519MLKEM768:x25519:P-256;

Phase 2: pur post-quantique (futur)

Client → TLS 1.3 avec ML-KEM-768 + ML-DSA → Serveur API

À adopter lorsque la majorité des clients supportent ML-KEM natif et que les certificats serveur utilisent ML-DSA pour la signature.

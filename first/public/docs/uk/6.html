6.1 Формальне визначення KEM

Трійка алгоритмів

Механізм інкапсуляції ключа (KEM) — це трійка ймовірнісних поліноміальних алгоритмів:

\[ \text{KEM} = (\text{KeyGen},\ \text{Encaps},\ \text{Decaps}) \]
  • KeyGen() → (ek, dk)
    Ймовірнісний алгоритм (використовує внутрішню випадковість). Не приймає вхідних даних.
    • ek: ключ інкапсуляції (публічний ключ)
    • dk: ключ декапсуляції (приватний ключ)
  • Encaps(ek) → (K, c)
    За ek виробляє:
    • \(K \in \{0,1\}^\ell\): секретний симетричний ключ (зазвичай 256 біт)
    • c: шифртекст ("капсула")
  • Decaps(dk, c) → K
    За dk і c відновлює \(K\).

Термінологічне зауваження FIPS 203: стандарт використовує ek для ключа інкапсуляції (не pk) та dk для ключа декапсуляції (не sk). Розрізнення навмисне: підкреслюється, що публічний ключ служить для інкапсуляції, а не для шифрування довільних повідомлень.

Коректність

KEM коректний, якщо для кожної допустимої пари ключів:

\[ \Pr\bigl[\text{Decaps}(dk,\, c) = K \mid (K, c) \leftarrow \text{Encaps}(ek)\bigr] \geq 1 - \delta \]

де \(\delta\) — знехтувана ймовірність помилки (зазвичай \(< 2^{-128}\)).
Для ML-KEM-768: \(\delta < 2^{-142}\).

6.2 Властивості безпеки

IND-CPA (Нерозрізненність при атаці на основі вибраного відкритого тексту)

Гра безпеки IND-CPA

Викликаюча сторона Противник \(\mathcal{A}\)
\((ek, dk) \leftarrow \text{KeyGen}()\)
\(ek \longrightarrow\)
Обирає виклик (неявний у KEM)
\((K_0, c) \leftarrow \text{Encaps}(ek)\)
\(K_1 \leftarrow \text{Random}\)
\(b \leftarrow \{0, 1\}\)
\((c, K_b) \longrightarrow\)
Повертає \(b'\)

Перевага: \(\text{Adv}^{\text{IND-CPA}}_{\text{KEM}}(\mathcal{A}) = \left| \Pr[b' = b] - \frac{1}{2} \right|\)

KEM є IND-CPA, якщо перевага знехтувана для будь-якого поліноміального противника. Інтуїтивно: противник не може відрізнити реальний ключ \(K\) від випадкового, навіть бачачи шифртекст c.

IND-CCA2 (Нерозрізненність при адаптивній атаці на основі вибраного шифртекста)

Як CPA, але противник також має доступ до оракула декапсуляції:

Фаза Дія
Ініціалізація \((ek, dk) \leftarrow \text{KeyGen}()\), надсилає \(ek\)
Фаза 1 (Запити) \(c_i \to K_i = \text{Decaps}(dk, c_i)\)
Виклик \((K_0, c^*) \leftarrow \text{Encaps}(ek)\), \(K_1 \leftarrow \text{Random}\), \(b \leftarrow \{0,1\}\). Надсилає \((c^*, K_b)\).
Фаза 2 (Запити) \(c_j \to K_j = \text{Decaps}(dk, c_j)\) з \(c_j \neq c^*\)
Вгадування Повертає \(b'\)

IND-CCA2 — це стандарт безпеки, необхідний для KEM у реальному використанні.

Чому необхідний CCA2? У реальному протоколі (TLS, SSH) активний противник може надсилати модифіковані шифртексти та спостерігати відповіді сервера. Навіть у MLWE противник, який знає декапсуляцію шифртекстів, близьких до шифртексту-виклику, може витягти інформацію про секрет. ML-KEM є IND-CCA2.

Додаткові бажані властивості

  • Стійкість (Robustness): важко побудувати шифртекст, який декапсулюється в той самий ключ з двома різними приватними ключами.
  • Перспективна секретність (Forward secrecy): якщо приватний ключ dk буде скомпрометований у майбутньому, минулі сесії залишаються безпечними (потребує ефемерних ключів).

6.3 KEM vs PKE: чому KEM

PKE (Шифрування з відкритим ключем)

PKE шифрує довільні повідомлення: \(\text{Enc}(ek, m) \to c\). Проблема в тому, що якщо повідомлення \(m\) має передбачувану структуру (короткий пароль, номер картки), противник може використовувати атаки з низькою ентропією або атаки на оракул доповнення (Блейхенбахер).

KEM: розділення ролей

KEM не шифрує користувацькі повідомлення. Він генерує симетричний ключ з високою ентропією та інкапсулює його:

\[ \text{Система} = \underbrace{\text{KEM}}_{\text{обмін } K} + \underbrace{\text{AES-GCM}}_{\text{шифрування даних на } K} \]

Переваги:

  • Ключ \(K\) завжди псевдовипадковий → немає атак з низькою ентропією.
  • Не потрібне складне доповнення для користувацьких повідомлень.
  • \(K\) використовується з симетричним шифром (DEM) для шифрування реальних даних.

6.4 Інтуїтивний приклад: KEM з Діффі-Геллмана

До ML-KEM найбільш використовуваним KEM був побудований на основі Діффі-Геллмана. Цей приклад допомагає зрозуміти структуру.

Публічні параметри: просте число \(p\), генератор \(g\) групи \(\mathbb{Z}_p^*\).

Аліса
  1. Обирає секретне \(a\)
  2. Обчислює \(A = g^a \bmod p\)
A → ← B
Боб
  1. Обирає секретне \(b\)
  2. Обчислює \(B = g^b \bmod p\)
\[ \begin{aligned} \text{Аліса обчислює: } & K = B^a \bmod p = g^{ab} \bmod p \\ \text{Боб обчислює: } & K = A^b \bmod p = g^{ab} \bmod p \end{aligned} \]

Числовий приклад: \(p = 17\), \(g = 3\), \(a = 5\).

  • \(ek = 3^5 \bmod 17 = 5\)
  • Боб обирає \(b = 7\): \(c = 3^7 \bmod 17 = 11\), \(K = H(5^7 \bmod 17) = H(10)\)
  • Аліса декапсулює: \(K = H(11^5 \bmod 17) = H(10)\) ✓

6.5 Перетворення Фуджісакі-Окамото (FO)

Проблема: від CPA до CCA2

Маючи PKE, безпечний лише в сенсі CPA, як побудувати KEM IND-CCA2? Відповідь — перетворення FO.

Центральна ідея

  • Детерміноване шифрування: випадковість, що використовується при шифруванні, детерміновано виводиться з повідомлення через хеш. Якщо шифртекст змінено, повторне шифрування дає щось інше.
  • Верифікація при розшифровці: замість прямого розшифровування, розшифроване повідомлення знову шифрується і порівнюється з отриманим шифртекстом. Якщо не збігаються → неявне відхилення.

Спрощена схема FO

\[ \begin{aligned} \text{Encaps}(ek): & \quad m \leftarrow \{0,1\}^\ell, \ (K, r) = G(m), \ c = \text{Enc}(ek, m; r) \\ \text{Decaps}(dk, c): & \quad m' = \text{Dec}(dk, c), \ (K', r') = G(m'), \ c' = \text{Enc}(ek, m'; r') \\ & \quad \text{return } \begin{cases} K' & \text{якщо } c' = c \\ K_{\text{reject}} & \text{інакше} \end{cases} \end{aligned} \]

Де \(K_{\text{reject}} = H(z \| c)\) з фіксованим секретним \(z\). Це "неявне відхилення" не дозволяє противнику використовувати помилки як оракул.

6.6 Від K-PKE (CPA) до ML-KEM (CCA2)

У ML-KEM дворівнева структура така:

ML-KEM (IND-CCA2)
└── K-PKE (IND-CPA) + перетворення FO
    └── задача MLWE

ML-KEM.Encaps(ek)

m ← Random(32)                  // випадкове 256-бітне повідомлення
(K̄, r) = G(m ‖ H(ek))          // SHA3-512: K̄ = перші 32 байти, r = останні 32 байти
c = K-PKE.Encrypt(ek, m, r)     // детерміноване шифрування з випадковістю r
K = KDF(K̄ ‖ H(c))              // фінальний ключ
return (K, c)

ML-KEM.Decaps(dk, c)

(dk_PKE, ek, h, z) = dk         // h = H(ek), z = запасний секрет
m' = K-PKE.Decrypt(dk_PKE, c)   // спроба розшифровки
(K̄', r') = G(m' ‖ h)           // перерахунок
c' = K-PKE.Encrypt(ek, m', r')  // верифікаційне повторне шифрування
якщо c' == c:
    K = KDF(K̄' ‖ H(c))         // розшифровка успішна
інакше:
    K = KDF(z ‖ H(c))           // запасний варіант: псевдовипадковий ключ
return K

Важливі деталі: Приватний ключ dk також містить ek, щоб можна було виконати повторне шифрування. Порівняння c' == c має виконуватися за постійний час.

6.7 KEM у реальному протоколі: TLS 1.3

Сервер (Аліса)
ClientHello (підтримує ML-KEM-768)
ServerHello + Сертифікат + KeyShare (ek)
KeyShare (c) + Finished (MAC з K)
Finished (MAC з K)

Гібрид X25519 + ML-KEM

На практиці TLS 1.3 використовує гібридний підхід:

\[ K_{\text{TLS}} = \text{HKDF}(K_{\text{X25519}} \,\|\, K_{\text{ML-KEM}}) \]

Це гарантує безпеку, якщо принаймні одна з двох схем зберігається. Група X25519MLKEM768 вже розгорнута в Chrome 131+.

6.8 Загальна структура потоку KEM

Повний потік Аліса (Отримувач) / Боб (Відправник)

  1. Аліса: KeyGen() генерує \((ek, dk)\). Публікує \(ek\).
  2. Боб: Отримує \(ek\). Виконує Encaps(ek):
    • Генерує випадкове \(m\)
    • \((\bar{K}, r) = G(m \| H(ek))\)
    • \(c = \text{K-PKE.Encrypt}(ek, m, r)\)
    • \(K = \text{KDF}(\bar{K} \| H(c))\)
  3. Боб: Шифрує дані за допомогою AES-256-GCM, використовуючи \(K\) та випадковий одноразовий номер.
  4. Боб: Надсилає \((c, \text{nonce}, \text{ciphertext}, \text{tag})\) Алісі.
  5. Аліса: Виконує Decaps(dk, c) для відновлення \(K\).
  6. Аліса: Розшифровує дані за допомогою AES-256-GCM. Якщо тег не збігається, відкидає повідомлення.

Подвійний захист: Якщо c змінено, Decaps повертає псевдовипадковий ключ (\(K_{\text{reject}}\)). Навіть якщо противник вгадає цей ключ, тег AEAD AES-GCM не зійдеться, гарантуючи цілісність.

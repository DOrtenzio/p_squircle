6.1 Formalna definicja KEM

Trójka algorytmów

Mechanizm enkapsulacji klucza (KEM) to trójka probabilistycznych algorytmów wielomianowych:

\[ \text{KEM} = (\text{KeyGen},\ \text{Encaps},\ \text{Decaps}) \]
  • KeyGen() → (ek, dk)
    Algorytm probabilistyczny (używa wewnętrznej losowości). Nie przyjmuje danych wejściowych.
    • ek: klucz enkapsulacji (klucz publiczny)
    • dk: klucz dekapsulacji (klucz prywatny)
  • Encaps(ek) → (K, c)
    Mając ek, produkuje:
    • \(K \in \{0,1\}^\ell\): tajny klucz symetryczny (zazwyczaj 256 bitów)
    • c: szyfrogram („kapsuła”)
  • Decaps(dk, c) → K
    Mając dk i c, odtwarza \(K\).

Uwaga terminologiczna FIPS 203: standard używa ek dla klucza enkapsulacji (nie pk) i dk dla klucza dekapsulacji (nie sk). Rozróżnienie jest celowe: podkreśla, że klucz publiczny służy do enkapsulacji, a nie do szyfrowania dowolnych wiadomości.

Poprawność

KEM jest poprawny, jeśli dla każdej ważnej pary kluczy:

\[ \Pr\bigl[\text{Decaps}(dk,\, c) = K \mid (K, c) \leftarrow \text{Encaps}(ek)\bigr] \geq 1 - \delta \]

gdzie \(\delta\) jest zaniedbywalnym prawdopodobieństwem błędu (zazwyczaj \(< 2^{-128}\)).
Dla ML-KEM-768: \(\delta < 2^{-142}\).

6.2 Właściwości bezpieczeństwa

IND-CPA (Nierozróżnialność przy wybranym ataku jawnym)

Gra bezpieczeństwa IND-CPA

Challenger Przeciwnik \(\mathcal{A}\)
\((ek, dk) \leftarrow \text{KeyGen}()\)
\(ek \longrightarrow\)
Wybiega wyzwanie (domyślnie w KEM)
\((K_0, c) \leftarrow \text{Encaps}(ek)\)
\(K_1 \leftarrow \text{Random}\)
\(b \leftarrow \{0, 1\}\)
\((c, K_b) \longrightarrow\)
Zwraca \(b'\)

Przewaga: \(\text{Adv}^{\text{IND-CPA}}_{\text{KEM}}(\mathcal{A}) = \left| \Pr[b' = b] - \frac{1}{2} \right|\)

KEM jest IND-CPA, jeśli przewaga jest zaniedbywalna dla każdego przeciwnika wielomianowego. Intuicyjnie: przeciwnik nie jest w stanie odróżnić prawdziwego klucza \(K\) od losowego, nawet widząc szyfrogram c.

IND-CCA2 (Nierozróżnialność przy adaptacyjnym wybranym ataku szyfrogramem)

Jak CPA, ale przeciwnik ma również dostęp do wyroczni dekapsulacji:

Faza Akcja
Inicjalizacja \((ek, dk) \leftarrow \text{KeyGen}()\), wyślij \(ek\)
Faza 1 (Zapytania) \(c_i \to K_i = \text{Decaps}(dk, c_i)\)
Wyzwanie \((K_0, c^*) \leftarrow \text{Encaps}(ek)\), \(K_1 \leftarrow \text{Random}\), \(b \leftarrow \{0,1\}\). Wyślij \((c^*, K_b)\).
Faza 2 (Zapytania) \(c_j \to K_j = \text{Decaps}(dk, c_j)\) z \(c_j \neq c^*\)
Zgadywanie Zwraca \(b'\)

IND-CCA2 to standard bezpieczeństwa wymagany dla KEM w rzeczywistym użyciu.

Dlaczego CCA2 jest konieczne? W rzeczywistym protokole (TLS, SSH) aktywny przeciwnik może wysyłać zmodyfikowane szyfrogramy i obserwować odpowiedzi serwera. Nawet w MLWE, przeciwnik, który zna dekapsulację szyfrogramów bliskich szyfrogramowi wyzwania, mógłby wydobyć informacje o sekrecie. ML-KEM jest IND-CCA2.

Dodatkowe pożądane właściwości

  • Solidność (Robustness): trudno skonstruować szyfrogram, który dekapsuluje do tego samego klucza z dwoma różnymi kluczami prywatnymi.
  • Tajność przyszłości (Forward secrecy): jeśli klucz prywatny dk zostanie skompromitowany w przyszłości, poprzednie sesje pozostają bezpieczne (wymaga kluczy efemerycznych).

6.3 KEM vs PKE: dlaczego KEM

PKE (Szyfrowanie z kluczem publicznym)

PKE szyfruje dowolne wiadomości: \(\text{Enc}(ek, m) \to c\). Problem polega na tym, że jeśli wiadomość \(m\) ma przewidywalną strukturę (krótkie hasło, numer karty), przeciwnik może wykorzystać ataki o niskiej entropii lub wyrocznię dopełnienia (Bleichenbacher).

KEM: separacja ról

KEM nie szyfruje wiadomości użytkownika. Generuje symetryczny klucz o wysokiej entropii i enkapsuluje go:

\[ \text{System} = \underbrace{\text{KEM}}_{\text{wymiana } K} + \underbrace{\text{AES-GCM}}_{\text{szyfrowanie danych } K} \]

Zalety:

  • Klucz \(K\) jest zawsze pseudolosowy → brak ataków o niskiej entropii.
  • Nie potrzeba złożonego dopełniania dla wiadomości użytkownika.
  • \(K\) jest używany z szyfrem symetrycznym (DEM) do szyfrowania rzeczywistych danych.

6.4 Przykład intuicyjny: KEM z Diffie-Hellmana

Przed ML-KEM, najczęściej używanym KEM był ten zbudowany na Diffie-Hellmanie. Ten przykład pomaga zrozumieć strukturę.

Parametry publiczne: liczba pierwsza \(p\), generator \(g\) grupy \(\mathbb{Z}_p^*\).

Alice
  1. Wybiega tajne \(a\)
  2. Oblicza \(A = g^a \bmod p\)
A → ← B
Bob
  1. Wybiega tajne \(b\)
  2. Oblicza \(B = g^b \bmod p\)
\[ \begin{aligned} \text{Alice oblicza: } & K = B^a \bmod p = g^{ab} \bmod p \\ \text{Bob oblicza: } & K = A^b \bmod p = g^{ab} \bmod p \end{aligned} \]

Przykład liczbowy: \(p = 17\), \(g = 3\), \(a = 5\).

  • \(ek = 3^5 \bmod 17 = 5\)
  • Bob wybiega \(b = 7\): \(c = 3^7 \bmod 17 = 11\), \(K = H(5^7 \bmod 17) = H(10)\)
  • Alice dekapsuluje: \(K = H(11^5 \bmod 17) = H(10)\) ✓

6.5 Transformacja Fujisaki-Okamoto (FO)

Problem: od CPA do CCA2

Mając PKE tylko CPA-bezpieczny, jak zbudować KEM IND-CCA2? Odpowiedzią jest transformacja FO.

Centralna idea

  • Deterministyczne szyfrowanie: losowość używana w szyfrowaniu jest deterministycznie wyprowadzana z wiadomości przez hash. Jeśli szyfrogram zostanie zmodyfikowany, ponowne zaszyfrowanie da coś innego.
  • Weryfikacja w deszyfrowaniu: zamiast bezpośredniego deszyfrowania, odszyfrowana wiadomość jest ponownie szyfrowana i porównywana z otrzymanym szyfrogramem. Jeśli nie pasują → domyślne odrzucenie.

Uproszczony schemat FO

\[ \begin{aligned} \text{Encaps}(ek): & \quad m \leftarrow \{0,1\}^\ell, \ (K, r) = G(m), \ c = \text{Enc}(ek, m; r) \\ \text{Decaps}(dk, c): & \quad m' = \text{Dec}(dk, c), \ (K', r') = G(m'), \ c' = \text{Enc}(ek, m'; r') \\ & \quad \text{return } \begin{cases} K' & \text{jeśli } c' = c \\ K_{\text{reject}} & \text{w przeciwnym razie} \end{cases} \end{aligned} \]

Gdzie \(K_{\text{reject}} = H(z \| c)\) z \(z\) stałym tajnym. To "domyślne odrzucenie" uniemożliwia przeciwnikowi używanie błędów jako wyroczni.

6.6 Od K-PKE (CPA) do ML-KEM (CCA2)

W ML-KEM struktura dwupoziomowa to:

ML-KEM (IND-CCA2)
└── K-PKE (IND-CPA) + transformacja FO
    └── problem MLWE

ML-KEM.Encaps(ek)

m ← Random(32)                  // losowa wiadomość 256-bitowa
(K̄, r) = G(m ‖ H(ek))          // SHA3-512: K̄ = pierwsze 32 bajty, r = ostatnie 32 bajty
c = K-PKE.Encrypt(ek, m, r)     // deterministyczne szyfrowanie z losowością r
K = KDF(K̄ ‖ H(c))              // końcowy klucz
return (K, c)

ML-KEM.Decaps(dk, c)

(dk_PKE, ek, h, z) = dk         // h = H(ek), z = zapasowy sekret
m' = K-PKE.Decrypt(dk_PKE, c)   // próba deszyfrowania
(K̄', r') = G(m' ‖ h)           // ponowne obliczenie
c' = K-PKE.Encrypt(ek, m', r')  // weryfikacyjne ponowne szyfrowanie
jeśli c' == c:
    K = KDF(K̄' ‖ H(c))         // deszyfrowanie udane
w przeciwnym razie:
    K = KDF(z ‖ H(c))           // zapasowy: pseudolosowy klucz
return K

Ważne szczegóły: Klucz prywatny dk zawiera również ek, aby umożliwić ponowne szyfrowanie. Porównanie c' == c musi być stałoczasowe.

6.7 KEM w rzeczywistym protokole: TLS 1.3

Klient (Bob)
Serwer (Alice)
ClientHello (obsługa ML-KEM-768)
ServerHello + Certyfikat + KeyShare (ek)
KeyShare (c) + Finished (MAC z K)
Finished (MAC z K)

Hybryda X25519 + ML-KEM

W praktyce TLS 1.3 używa podejścia hybrydowego:

\[ K_{\text{TLS}} = \text{HKDF}(K_{\text{X25519}} \,\|\, K_{\text{ML-KEM}}) \]

To gwarantuje bezpieczeństwo, jeśli przynajmniej jeden z dwóch schematów się utrzyma. Grupa X25519MLKEM768 jest już wdrożona w Chrome 131+.

6.8 Ogólna struktura przepływu KEM

Pełny przepływ Alice (Odbiorca) / Bob (Nadawca)

  1. Alice: KeyGen() generuje \((ek, dk)\). Publikuje \(ek\).
  2. Bob: Otrzymuje \(ek\). Wykonuje Encaps(ek):
    • Generuje losowe \(m\)
    • \((\bar{K}, r) = G(m \| H(ek))\)
    • \(c = \text{K-PKE.Encrypt}(ek, m, r)\)
    • \(K = \text{KDF}(\bar{K} \| H(c))\)
  3. Bob: Szyfruje dane AES-256-GCM używając \(K\) i losowego nonce.
  4. Bob: Wysyła \((c, \text{nonce}, \text{ciphertext}, \text{tag})\) do Alice.
  5. Alice: Wykonuje Decaps(dk, c) aby odzyskać \(K\).
  6. Alice: Deszyfruje dane AES-256-GCM. Jeśli tag zawiedzie, odrzuca wiadomość.

Podwójna ochrona: Jeśli c zostanie zmodyfikowane, Decaps zwraca pseudolosowy klucz (\(K_{\text{reject}}\)). Nawet jeśli przeciwnik zgadnie ten klucz, tag AEAD AES-GCM zawiedzie, gwarantując integralność.

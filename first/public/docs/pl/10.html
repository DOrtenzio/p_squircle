10.1 liboqs: referencyjna biblioteka C

liboqs to referencyjna biblioteka C dla kryptografii post-kwantowej, rozwijana przez projekt Open Quantum Safe (OQS). Dostarcza zoptymalizowane i stałoczasowe implementacje ML-KEM oraz innych algorytmów PQC znormalizowanych przez NIST.

Instalacja ze źródeł

# Zależności (Ubuntu/Debian)
sudo apt-get install cmake gcc libssl-dev

# Klonowanie i kompilacja
git clone https://github.com/open-quantum-safe/liboqs.git
cd liboqs
mkdir build && cd build
cmake -DCMAKE_INSTALL_PREFIX=/usr/local ..
make -j$(nproc)
sudo make install

10.2 Kompletny przykład: KEM z ML-KEM-768 w C

#include <stdio.h>
#include <string.h>
#include <oqs/oqs.h>

int main() {
    OQS_STATUS rc;
    const char *kem_alg = OQS_KEM_alg_ml_kem_768;

    // Inicjalizacja algorytmu
    OQS_KEM *kem = OQS_KEM_new(kem_alg);
    if (kem == NULL) {
        fprintf(stderr, "KEM nieobsługiwany\n");
        return 1;
    }

    printf("Algorytm: %s\n", kem->method_name);
    printf("Klucz publiczny: %zu bajtów\n", kem->length_public_key);
    printf("Klucz prywatny: %zu bajtów\n", kem->length_secret_key);
    printf("Szyfrogram: %zu bajtów\n", kem->length_ciphertext);
    printf("Wspólny sekret: %zu bajtów\n\n", kem->length_shared_secret);

    // Alokacja pamięci
    uint8_t *pk = malloc(kem->length_public_key);
    uint8_t *sk = malloc(kem->length_secret_key);
    uint8_t *ct = malloc(kem->length_ciphertext);
    uint8_t *ss_enc = malloc(kem->length_shared_secret);
    uint8_t *ss_dec = malloc(kem->length_shared_secret);

    // 1. KeyGen (Alice)
    rc = OQS_KEM_keypair(kem, pk, sk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "KeyGen nieudany\n"); return 1; }
    printf("✓ KeyGen zakończony\n");

    // 2. Encaps (Bob: zna tylko pk)
    rc = OQS_KEM_encaps(kem, ct, ss_enc, pk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "Encaps nieudany\n"); return 1; }
    printf("✓ Encaps zakończony\n");

    // 3. Decaps (Alice: używa sk do otwarcia ct)
    rc = OQS_KEM_decaps(kem, ss_dec, ct, sk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "Decaps nieudany\n"); return 1; }
    printf("✓ Decaps zakończony\n\n");

    // 4. Weryfikacja
    if (memcmp(ss_enc, ss_dec, kem->length_shared_secret) == 0) {
        printf("✅ Wspólne sekrety są zgodne!\n");
        printf("   Pierwsze bajty: ");
        for (int i = 0; i < 8; i++) printf("%02x", ss_enc[i]);
        printf("...\n");
    } else {
        printf("❌ BŁĄD: wspólne sekrety są różne!\n");
    }

    // Bezpieczne czyszczenie pamięci
    OQS_MEM_cleanse(sk, kem->length_secret_key);
    OQS_MEM_cleanse(ss_enc, kem->length_shared_secret);
    OQS_MEM_cleanse(ss_dec, kem->length_shared_secret);
    free(pk); free(ct);
    OQS_KEM_free(kem);

    return 0;
}

Kompilacja:

gcc -o kem_example kem_example.c -loqs -lcrypto
./kem_example

10.3 Użycie wyprowadzonego klucza z AES-256-GCM

Po uzyskaniu wspólnego sekretu z ML-KEM, można go użyć jako klucza dla szyfru symetrycznego. W produkcji zaleca się użycie HKDF do wyprowadzenia oddzielnych kluczy.

#include <openssl/evp.h>
#include <oqs/oqs.h>

// Po uzyskaniu ss (32 bajty) z ML-KEM:
void encrypt_with_kem_key(const uint8_t *ss, const uint8_t *plaintext,
                           size_t pt_len, uint8_t *ciphertext, uint8_t *tag,
                           const uint8_t *nonce) {
    EVP_CIPHER_CTX *ctx = EVP_CIPHER_CTX_new();
    int len;

    // Inicjalizacja AES-256-GCM
    EVP_EncryptInit_ex(ctx, EVP_aes_256_gcm(), NULL, NULL, NULL);
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_IVLEN, 12, NULL);

    // Użycie wspólnego sekretu jako klucza
    EVP_EncryptInit_ex(ctx, NULL, NULL, ss, nonce);

    // Szyfrowanie
    EVP_EncryptUpdate(ctx, ciphertext, &len, plaintext, pt_len);
    EVP_EncryptFinal_ex(ctx, ciphertext + len, &len);

    // Pobranie tagu uwierzytelniającego
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_GET_TAG, 16, tag);

    EVP_CIPHER_CTX_free(ctx);
}

10.4 Python: wiązanie liboqs

Liboqs dostarcza oficjalne wiązania dla Pythona do szybkich testów i prototypowania.

pip install liboqs-python
import oqs

# Dostępny algorytm
kem = oqs.KeyEncapsulation("ML-KEM-768")

# KeyGen
public_key = kem.generate_keypair()

# Encaps (strona Boba)
kem_bob = oqs.KeyEncapsulation("ML-KEM-768")
ciphertext, shared_secret_enc = kem_bob.encap_secret(public_key)

# Decaps (strona Alice)
shared_secret_dec = kem.decap_secret(ciphertext)

assert shared_secret_enc == shared_secret_dec
print(f"✓ Wspólny sekret: {shared_secret_enc.hex()[:16]}...")

kem.free()
kem_bob.free()

10.5 Python: kyber-py (tylko edukacyjny)

Do celów czysto edukacyjnych istnieje implementacja w czystym Pythonie, która nie wymaga zewnętrznych bibliotek C.

Uwaga: kyber-py nie jest stałoczasowy i nie powinien być używany w produkcji.

                    
                        from kyber import Kyber768
                        kem = Kyber768()
                        pk, sk = kem.keygen()

                        _key = kem.dec(sk, ciphertext)
                        assert key == _key

10.6 Testy wydajnościowe

Testy wydajnościowe na Intel Core i7-12700K (jeden rdzeń, bez instrukcji SIMD):

Operacja ML-KEM-512 ML-KEM-768 ML-KEM-1024
KeyGen 24 µs 37 µs 54 µs
Encaps 28 µs 43 µs 62 µs
Decaps 32 µs 48 µs 70 µs

Z optymalizacjami AVX2

Operacja ML-KEM-768 (bez SIMD) ML-KEM-768 (AVX2) Przyspieszenie
KeyGen 37 µs ~10 µs ~3.7×
Encaps 43 µs ~12 µs ~3.6×
Decaps 48 µs ~13 µs ~3.7×

Porównanie z ECDH X25519

X25519 ML-KEM-768
KeyGen ~14 µs ~37 µs
Wymiana ~30 µs ~48 µs
Klucz publiczny 32 B 1184 B

ML-KEM jest około 2 razy wolniejszy niż X25519, ale narzut na opóźnienie uzgodnienia TLS jest pomijalny (< 1 ms) w większości rzeczywistych połączeń.

10.7 OpenSSL: instalacja dostawcy OQS

OpenSSL 3.x obsługuje ML-KEM poprzez dostawcę oqsprovider. Od wersji 3.4 obsługa jest natywna lub łatwo integrowalna.

# Kompilacja oqs-provider
git clone https://github.com/open-quantum-safe/oqs-provider.git
cd oqs-provider
cmake -DOPENSSL_ROOT_DIR=/usr/local/ssl .
make
sudo make install

# Weryfikacja
openssl list -providers
# powinien pokazać: oqsprovider

10.8 Generowanie kluczy ML-KEM za pomocą OpenSSL CLI

# Generowanie pary kluczy ML-KEM-768
openssl genpkey -algorithm mlkem768 -out private.pem
openssl pkey -in private.pem -pubout -out public.pem

# Wyświetlenie szczegółów klucza
openssl pkey -in private.pem -text -noout

10.9 TLS 1.3 z ML-KEM-768

Test lokalny (serwer + klient)

# Serwer
openssl s_server -accept 4433 -cert server.crt -key server.key \
    -groups mlkem768

# Klient (w innym terminalu)
openssl s_client -connect localhost:4433 -groups mlkem768

Sprawdzenie obsługiwanych grup

openssl list -key-exchange-algorithms | grep -i kem

10.10 Strategia hybrydowa: X25519 + ML-KEM-768

Zalecanym podejściem do migracji jest hybrydyzacja: połączenie ECDH (X25519) z ML-KEM-768. Klucz końcowy jest wyprowadzany z obu:

\[ K = \text{HKDF}(K_{\text{X25519}} \| K_{\text{ML-KEM}}) \]

Zaleta: bezpieczne, jeśli przynajmniej jeden z dwóch schematów się utrzyma. Jeśli komputer kwantowy złamie X25519, ML-KEM chroni. Jeśli ML-KEM miałby nieznaną wadę, X25519 chroni.

10.11 Hybrydowe suites szyfrów w TLS 1.3

Nazwa grupy Skład
X25519MLKEM768 X25519 + ML-KEM-768
SecP256r1MLKEM768 P-256 + ML-KEM-768

Od Chrome 131 (koniec 2024), X25519MLKEM768 jest domyślną grupą. Firefox 128+ obsługuje tę samą grupę.

Konfiguracja OpenSSL

# Serwer akceptujący zarówno klasyczny X25519, jak i grupę hybrydową
openssl s_server -accept 4433 -cert server.crt -key server.key \
    -groups X25519MLKEM768:x25519:P-256

# Klient preferujący grupę hybrydową
openssl s_client -connect localhost:4433 \
    -groups X25519MLKEM768:x25519

10.12 Integracja w aplikacjach C z OpenSSL

#include <openssl/ssl.h>
#include <openssl/err.h>

SSL_CTX *create_pqc_context(void) {
    SSL_CTX *ctx = SSL_CTX_new(TLS_server_method());
    if (!ctx) {
        ERR_print_errors_fp(stderr);
        return NULL;
    }

    // Ustaw preferowane grupy: hybrydowa jako pierwsza, klasyczne jako awaryjne
    if (SSL_CTX_set1_groups_list(ctx, "X25519MLKEM768:x25519:P-256") != 1) {
        fprintf(stderr, "Błąd konfiguracji grup\n");
        SSL_CTX_free(ctx);
        return NULL;
    }

    return ctx;
}

10.13 Lista kontrolna migracji

Dla deweloperów aplikacji

  • Inwentaryzacja miejsc użycia kryptografii asymetrycznej (wymiana kluczy, podpisy, KEM).
  • Identyfikacja danych, które muszą pozostać tajne przez ponad 5 lat.
  • Aktualizacja zależności: OpenSSL ≥ 3.2, liboqs ≥ 0.10.
  • Przyjęcie podejścia hybrydowego: X25519 + ML-KEM-768 dla TLS.
  • Dla podpisów cyfrowych: migracja do ML-DSA (FIPS 204) lub SLH-DSA (FIPS 205).
  • Testowanie zwiększonego rozmiaru kluczy i szyfrogramów w protokołach.
  • Weryfikacja, czy limity czasowe i rozmiary buforów nie zakładają małych kluczy.

Dla administratorów infrastruktury

  • Aktualizacja stosu TLS do wersji z obsługą ML-KEM.
  • Włączenie X25519MLKEM768 na serwerach TLS.
  • Monitorowanie kompatybilności klientów (Chrome 131+, Firefox 128+ obsługują hybrydowe PQC).
  • Planowanie długoterminowej rotacji kluczy.

Standardy odniesienia

Standard Zawartość
FIPS 203 ML-KEM (enkapsulacja klucza)
FIPS 204 ML-DSA (podpis cyfrowy oparty na kratach)
FIPS 205 SLH-DSA (podpis oparty na haszu, konserwatywny)

10.14 Scenariusz: migracja API REST

Sytuacja obecna (przed migracją)

Klient → TLS 1.3 z X25519 → Serwer API

Faza 1: hybrydowa (dziś, zalecana)

Klient → TLS 1.3 z X25519MLKEM768 → Serwer API

# Konfiguracja nginx
ssl_ecdh_curve X25519MLKEM768:x25519:P-256;

# Konfiguracja Apache
SSLOpenSSLConfCmd Curves X25519MLKEM768:x25519:P-256;

Faza 2: czysto post-kwantowa (przyszłość)

Klient → TLS 1.3 z ML-KEM-768 + ML-DSA → Serwer API

Do wdrożenia, gdy większość klientów będzie obsługiwać natywny ML-KEM, a certyfikaty serwera będą używać ML-DSA do podpisu.

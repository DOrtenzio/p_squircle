6.1 KEM 的形式化定义

三个算法的三元组

密钥封装机制（KEM）是三个概率性多项式算法的三元组：

\[ \text{KEM} = (\text{KeyGen},\ \text{Encaps},\ \text{Decaps}) \]
  • KeyGen() → (ek, dk)
    概率性算法（使用内部随机性）。不接收输入。
    • ek：封装密钥（公钥）
    • dk：解封装密钥（私钥）
  • Encaps(ek) → (K, c)
    给定 ek，产生：
    • \(K \in \{0,1\}^\ell\)：秘密对称密钥（通常为 256 位）
    • c：密文（"胶囊"）
  • Decaps(dk, c) → K
    给定 dk 和 c，恢复 \(K\)。

FIPS 203 术语说明：标准使用 ek 表示封装密钥（而非 pk）和 dk 表示解封装密钥（而非 sk）。这种区分是刻意的：强调公钥用于封装，而非加密任意消息。

正确性

如果对于每个有效的密钥对：

\[ \Pr\bigl[\text{Decaps}(dk,\, c) = K \mid (K, c) \leftarrow \text{Encaps}(ek)\bigr] \geq 1 - \delta \]

其中 \(\delta\) 是可忽略的错误概率（通常 \(< 2^{-128}\)）。
对于 ML-KEM-768：\(\delta < 2^{-142}\)。

6.2 安全性质

IND-CPA（选择明文攻击下的不可区分性）

IND-CPA 安全游戏

挑战者 攻击者 \(\mathcal{A}\)
\((ek, dk) \leftarrow \text{KeyGen}()\)
\(ek \longrightarrow\)
选择挑战（在 KEM 中隐含）
\((K_0, c) \leftarrow \text{Encaps}(ek)\)
\(K_1 \leftarrow \text{Random}\)
\(b \leftarrow \{0, 1\}\)
\((c, K_b) \longrightarrow\)
返回 \(b'\)

优势：\(\text{Adv}^{\text{IND-CPA}}_{\text{KEM}}(\mathcal{A}) = \left| \Pr[b' = b] - \frac{1}{2} \right|\)

如果对于任何多项式攻击者，优势都是可忽略的，则 KEM 是 IND-CPA 的。直观地说：攻击者即使看到密文 c，也无法区分真实密钥 \(K\) 和随机密钥。

IND-CCA2（自适应选择密文攻击下的不可区分性）

与 CPA 类似，但攻击者还可以访问解封装预言机：

阶段 动作
初始化 \((ek, dk) \leftarrow \text{KeyGen}()\)，发送 \(ek\)
阶段 1（查询） \(c_i \to K_i = \text{Decaps}(dk, c_i)\)
挑战 \((K_0, c^*) \leftarrow \text{Encaps}(ek)\)，\(K_1 \leftarrow \text{Random}\)，\(b \leftarrow \{0,1\}\)。发送 \((c^*, K_b)\)。
阶段 2（查询） \(c_j \to K_j = \text{Decaps}(dk, c_j)\)，其中 \(c_j \neq c^*\)
猜测 返回 \(b'\)

IND-CCA2 是实际使用中 KEM 所需的安全标准。

为什么需要 CCA2？在实际协议（TLS、SSH）中，主动攻击者可以发送修改过的密文并观察服务器的响应。即使在 MLWE 中，知道接近挑战密文的解封装的攻击者也可能会提取关于秘密的信息。ML-KEM 是 IND-CCA2 的。

额外的理想性质

  • 健壮性（Robustness）：难以构造一个密文，使其用两个不同的私钥解封装到同一个密钥。
  • 前向保密性（Forward secrecy）：如果 dk 私钥在未来被泄露，过去的会话仍然安全（需要临时密钥）。

6.3 KEM vs PKE：为什么是 KEM

PKE（公钥加密）

PKE 加密任意消息：\(\text{Enc}(ek, m) \to c\)。问题是，如果消息 \(m\) 具有可预测的结构（短密码、卡号），攻击者可以利用低熵攻击或填充预言机攻击（Bleichenbacher）。

KEM：角色分离

KEM 不加密用户消息。它生成一个高熵的对称密钥并将其封装：

\[ \text{系统} = \underbrace{\text{KEM}}_{交换 K} + \underbrace{\text{AES-GCM}}_{使用 K 加密数据} \]

优点：

  • 密钥 \(K\) 始终是伪随机的 → 没有低熵攻击。
  • 用户消息不需要复杂的填充。
  • \(K\) 与对称密码（DEM）一起使用来加密实际数据。

6.4 直观示例：来自 Diffie-Hellman 的 KEM

在 ML-KEM 之前，最常用的 KEM 是基于 Diffie-Hellman 构建的。这个例子有助于理解其结构。

公共参数：素数 \(p\)，\(\mathbb{Z}_p^*\) 的生成元 \(g\)。

Alice
  1. 选择秘密 \(a\)
  2. 计算 \(A = g^a \bmod p\)
A → ← B
Bob
  1. 选择秘密 \(b\)
  2. 计算 \(B = g^b \bmod p\)
\[ \begin{aligned} \text{Alice 计算： } & K = B^a \bmod p = g^{ab} \bmod p \\ \text{Bob 计算： } & K = A^b \bmod p = g^{ab} \bmod p \end{aligned} \]

数值示例：\(p = 17\)，\(g = 3\)，\(a = 5\)。

  • \(ek = 3^5 \bmod 17 = 5\)
  • Bob 选择 \(b = 7\)：\(c = 3^7 \bmod 17 = 11\)，\(K = H(5^7 \bmod 17) = H(10)\)
  • Alice 解封装：\(K = H(11^5 \bmod 17) = H(10)\) ✓

6.5 Fujisaki-Okamoto（FO）变换

问题：从 CPA 到 CCA2

从仅 CPA 安全的 PKE 出发，如何构建 IND-CCA2 KEM？答案是 FO 变换。

核心思想

  • 确定性加密：加密中使用的随机性通过哈希从消息中确定性派生。如果密文被修改，重新加密会生成不同的结果。
  • 解密时的验证：不是直接解密，而是将解密后的消息重新加密并与收到的密文进行比较。如果不匹配 → 隐式拒绝。

简化的 FO 方案

\[ \begin{aligned} \text{Encaps}(ek): & \quad m \leftarrow \{0,1\}^\ell, \ (K, r) = G(m), \ c = \text{Enc}(ek, m; r) \\ \text{Decaps}(dk, c): & \quad m' = \text{Dec}(dk, c), \ (K', r') = G(m'), \ c' = \text{Enc}(ek, m'; r') \\ & \quad \text{return } \begin{cases} K' & \text{如果 } c' = c \\ K_{\text{reject}} & \text{否则} \end{cases} \end{aligned} \]

其中 \(K_{\text{reject}} = H(z \| c)\)，\(z\) 是固定的秘密。这种"隐式拒绝"防止攻击者将错误用作预言机。

6.6 从 K-PKE（CPA）到 ML-KEM（CCA2）

在 ML-KEM 中，两层结构是：

ML-KEM (IND-CCA2)
└── K-PKE (IND-CPA) + FO 变换
    └── MLWE 问题

ML-KEM.Encaps(ek)

m ← Random(32)                  // 256 位随机消息
(K̄, r) = G(m ‖ H(ek))          // SHA3-512：K̄ = 前 32 字节，r = 后 32 字节
c = K-PKE.Encrypt(ek, m, r)     // 使用随机性 r 进行确定性加密
K = KDF(K̄ ‖ H(c))              // 最终密钥
return (K, c)

ML-KEM.Decaps(dk, c)

(dk_PKE, ek, h, z) = dk         // h = H(ek)，z = 后备秘密
m' = K-PKE.Decrypt(dk_PKE, c)   // 尝试解密
(K̄', r') = G(m' ‖ h)           // 重新计算
c' = K-PKE.Encrypt(ek, m', r')  // 验证性重新加密
如果 c' == c：
    K = KDF(K̄' ‖ H(c))         // 解密成功
否则：
    K = KDF(z ‖ H(c))           // 后备：伪随机密钥
return K

重要细节：私钥 dk 还包含 ek，以便能够进行重新加密。比较 c' == c 必须以恒定时间执行。

6.7 实际协议中的 KEM：TLS 1.3

客户端（Bob）
服务器（Alice）
ClientHello（支持 ML-KEM-768）
ServerHello + 证书 + KeyShare (ek)
KeyShare (c) + Finished（使用 K 的 MAC）
Finished（使用 K 的 MAC）

X25519 + ML-KEM 混合

在实践中，TLS 1.3 使用混合方法：

\[ K_{\text{TLS}} = \text{HKDF}(K_{\text{X25519}} \,\|\, K_{\text{ML-KEM}}) \]

这保证了如果两种方案中至少有一种保持安全，则通信安全。组 X25519MLKEM768 已经在 Chrome 131+ 中部署。

6.8 KEM 流程的通用结构

完整流程 Alice（接收方）/ Bob（发送方）

  1. Alice：KeyGen() 生成 \((ek, dk)\)。发布 \(ek\)。
  2. Bob：接收 \(ek\)。执行 Encaps(ek)：
    • 生成随机 \(m\)
    • \((\bar{K}, r) = G(m \| H(ek))\)
    • \(c = \text{K-PKE.Encrypt}(ek, m, r)\)
    • \(K = \text{KDF}(\bar{K} \| H(c))\)
  3. Bob：使用 \(K\) 和随机 nonce 通过 AES-256-GCM 加密数据。
  4. Bob：发送 \((c, \text{nonce}, \text{ciphertext}, \text{tag})\) 给 Alice。
  5. Alice：执行 Decaps(dk, c) 以恢复 \(K\)。
  6. Alice：使用 AES-256-GCM 解密数据。如果标签失败，丢弃消息。

双重保护：如果 c 被篡改，Decaps 返回伪随机密钥（\(K_{\text{reject}}\)）。即使攻击者猜出这个密钥，AES-GCM 的 AEAD 标签也会失败，从而保证完整性。

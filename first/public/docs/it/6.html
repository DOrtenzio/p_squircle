6.1 Definizione formale di KEM

Tripla di algoritmi

Un Key Encapsulation Mechanism (KEM) è una tripla di algoritmi probabilistici polinomiali:

\[ \text{KEM} = (\text{KeyGen},\ \text{Encaps},\ \text{Decaps}) \]
  • KeyGen() → (ek, dk)
    Algoritmo probabilistico (usa randomness interna). Non prende input.
    • ek: encapsulation key (chiave pubblica)
    • dk: decapsulation key (chiave privata)
  • Encaps(ek) → (K, c)
    Dato ek, produce:
    • \(K \in \{0,1\}^\ell\): chiave simmetrica segreta (tipicamente 256 bit)
    • c: ciphertext (la "capsula")
  • Decaps(dk, c) → K
    Dato dk e c, recupera \(K\).

Nota terminologica FIPS 203: lo standard usa ek per encapsulation key (non pk) e dk per decapsulation key (non sk). La distinzione è intenzionale: sottolinea che la chiave pubblica serve per incapsulare, non per cifrare messaggi arbitrari.

Correttezza

Un KEM è corretto se per ogni coppia di chiavi valida:

\[ \Pr\bigl[\text{Decaps}(dk,\, c) = K \mid (K, c) \leftarrow \text{Encaps}(ek)\bigr] \geq 1 - \delta \]

dove \(\delta\) è una probabilità di errore negligibile (tipicamente \(< 2^{-128}\)).
Per ML-KEM-768: \(\delta < 2^{-142}\).

6.2 Proprietà di sicurezza

IND-CPA (Indistinguishability under Chosen Plaintext Attack)

Gioco di sicurezza IND-CPA

Challenger Avversario \(\mathcal{A}\)
\((ek, dk) \leftarrow \text{KeyGen}()\)
\(ek \longrightarrow\)
Sceglie challenge (implicita nel KEM)
\((K_0, c) \leftarrow \text{Encaps}(ek)\)
\(K_1 \leftarrow \text{Random}\)
\(b \leftarrow \{0, 1\}\)
\((c, K_b) \longrightarrow\)
Restituisce \(b'\)

Vantaggio: \(\text{Adv}^{\text{IND-CPA}}_{\text{KEM}}(\mathcal{A}) = \left| \Pr[b' = b] - \frac{1}{2} \right|\)

Il KEM è IND-CPA se il vantaggio è negligibile per ogni avversario polinomiale. Intuitivamente: l'avversario non riesce a distinguere la chiave \(K\) reale da una casuale, anche vedendo il ciphertext c.

IND-CCA2 (Indistinguishability under Adaptive Chosen Ciphertext Attack)

Come CPA, ma l'avversario ha anche accesso a un oracolo di decapsulazione:

Fase Azione
Inizializzazione \((ek, dk) \leftarrow \text{KeyGen}()\), invia \(ek\)
Fase 1 (Query) \(c_i \to K_i = \text{Decaps}(dk, c_i)\)
Challenge \((K_0, c^*) \leftarrow \text{Encaps}(ek)\), \(K_1 \leftarrow \text{Random}\), \(b \leftarrow \{0,1\}\). Invia \((c^*, K_b)\).
Fase 2 (Query) \(c_j \to K_j = \text{Decaps}(dk, c_j)\) con \(c_j \neq c^*\)
Guess Restituisce \(b'\)

IND-CCA2 è lo standard di sicurezza richiesto per i KEM in uso reale.

Perché è necessario CCA2? In un protocollo reale (TLS, SSH), un avversario attivo può inviare ciphertext manipolati e osservare le risposte del server. Anche in MLWE, un avversario che conosce la decapsulazione di ciphertext vicini al ciphertext sfida potrebbe estrarre informazioni sul segreto. ML-KEM è IND-CCA2.

Proprietà aggiuntive desiderabili

  • Robustezza (Robustness): difficile costruire ciphertext che decapsulino alla stessa chiave con due chiavi private diverse.
  • Forward secrecy: se la chiave privata dk viene compromessa in futuro, le sessioni passate rimangono sicure (richiede chiavi effimere).

6.3 KEM vs PKE: perché i KEM

PKE (Public Key Encryption)

Un PKE cifra messaggi arbitrari: \(\text{Enc}(ek, m) \to c\). Il problema è che se il messaggio \(m\) ha struttura prevedibile (password corta, numero di carta), un avversario può sfruttare attacchi a bassa entropia o padding oracle (Bleichenbacher).

KEM: separazione dei ruoli

Il KEM non cifra messaggi utente. Genera una chiave simmetrica di alta entropia e la incapsula:

\[ \text{Sistema} = \underbrace{\text{KEM}}_{\text{scambia } K} + \underbrace{\text{AES-GCM}}_{\text{cifra dati con } K} \]

Vantaggi:

  • La chiave \(K\) è sempre pseudocasuale → nessun attacco a bassa entropia.
  • Non serve padding complesso per messaggi utente.
  • \(K\) viene usata con un cifrario simmetrico (DEM) per cifrare i dati reali.

6.4 Esempio intuitivo: KEM da Diffie-Hellman

Prima di ML-KEM, il KEM più usato era costruito su Diffie-Hellman. Questo esempio aiuta a capire la struttura.

Parametri pubblici: primo \(p\), generatore \(g\) di \(\mathbb{Z}_p^*\).

Alice
  1. Sceglie \(a\) segreto
  2. Calcola \(A = g^a \bmod p\)
A → ← B
Bob
  1. Sceglie \(b\) segreto
  2. Calcola \(B = g^b \bmod p\)
\[ \begin{aligned} \text{Alice calcola: } & K = B^a \bmod p = g^{ab} \bmod p \\ \text{Bob calcola: } & K = A^b \bmod p = g^{ab} \bmod p \end{aligned} \]

Esempio numerico: \(p = 17\), \(g = 3\), \(a = 5\).

  • \(ek = 3^5 \bmod 17 = 5\)
  • Bob sceglie \(b = 7\): \(c = 3^7 \bmod 17 = 11\), \(K = H(5^7 \bmod 17) = H(10)\)
  • Alice decapsula: \(K = H(11^5 \bmod 17) = H(10)\) ✓

6.5 La trasformazione Fujisaki-Okamoto (FO)

Il problema: da CPA a CCA2

Partendo da un PKE solo CPA-sicuro, come costruire un KEM IND-CCA2? La risposta è la trasformazione FO.

Idea centrale

  • Cifratura deterministica: la randomness usata in cifratura è derivata deterministicamente dal messaggio tramite hash. Se il ciphertext è modificato, la ricifratura produce qualcosa di diverso.
  • Verifica in decifratura: invece di decifrare direttamente, si ricifratura il messaggio decifrato e si confronta con il ciphertext ricevuto. Se non corrispondono → rifiuto implicito.

Schema FO semplificato

\[ \begin{aligned} \text{Encaps}(ek): & \quad m \leftarrow \{0,1\}^\ell, \ (K, r) = G(m), \ c = \text{Enc}(ek, m; r) \\ \text{Decaps}(dk, c): & \quad m' = \text{Dec}(dk, c), \ (K', r') = G(m'), \ c' = \text{Enc}(ek, m'; r') \\ & \quad \text{return } \begin{cases} K' & \text{se } c' = c \\ K_{\text{reject}} & \text{altrimenti} \end{cases} \end{aligned} \]

Dove \(K_{\text{reject}} = H(z \| c)\) con \(z\) segreto fisso. Questo "implicit reject" impedisce all'avversario di usare gli errori come oracolo.

6.6 Da K-PKE (CPA) a ML-KEM (CCA2)

In ML-KEM, la struttura a due livelli è:

ML-KEM (IND-CCA2)
└── K-PKE (IND-CPA) + trasformazione FO
    └── problema MLWE

ML-KEM.Encaps(ek)

m ← Random(32)                  // messaggio casuale 256 bit
(K̄, r) = G(m ‖ H(ek))          // SHA3-512: K̄ = primi 32 byte, r = ultimi 32 byte
c = K-PKE.Encrypt(ek, m, r)     // cifratura deterministica con randomness r
K = KDF(K̄ ‖ H(c))              // chiave finale
return (K, c)

ML-KEM.Decaps(dk, c)

(dk_PKE, ek, h, z) = dk         // h = H(ek), z = segreto fallback
m' = K-PKE.Decrypt(dk_PKE, c)   // tentativo di decifratura
(K̄', r') = G(m' ‖ h)           // ricalcola
c' = K-PKE.Encrypt(ek, m', r')  // ricifratura di verifica
se c' == c:
    K = KDF(K̄' ‖ H(c))         // decifratura riuscita
altrimenti:
    K = KDF(z ‖ H(c))           // fallback: chiave pseudocasuale
return K

Dettagli importanti: La chiave privata dk contiene anche ek per poter fare la ricifratura. Il confronto c' == c deve essere constant-time.

6.7 KEM in un protocollo reale: TLS 1.3

Client (Bob)
Server (Alice)
ClientHello (supporta ML-KEM-768)
ServerHello + Certificato + KeyShare (ek)
KeyShare (c) + Finished (MAC con K)
Finished (MAC con K)

Ibrido X25519 + ML-KEM

In pratica, TLS 1.3 usa un approccio ibrido:

\[ K_{\text{TLS}} = \text{HKDF}(K_{\text{X25519}} \,\|\, K_{\text{ML-KEM}}) \]

Questo garantisce sicurezza se almeno uno dei due schemi regge. Il gruppo X25519MLKEM768 è già deployato da Chrome 131+.

6.8 Struttura generica del flusso KEM

Flusso completo Alice (Destinatario) / Bob (Mittente)

  1. Alice: KeyGen() genera \((ek, dk)\). Pubblica \(ek\).
  2. Bob: Riceve \(ek\). Esegue Encaps(ek):
    • Genera \(m\) casuale
    • \((\bar{K}, r) = G(m \| H(ek))\)
    • \(c = \text{K-PKE.Encrypt}(ek, m, r)\)
    • \(K = \text{KDF}(\bar{K} \| H(c))\)
  3. Bob: Cifra i dati con AES-256-GCM usando \(K\) e un nonce casuale.
  4. Bob: Invia \((c, \text{nonce}, \text{ciphertext}, \text{tag})\) ad Alice.
  5. Alice: Esegue Decaps(dk, c) per recuperare \(K\).
  6. Alice: Decifra i dati con AES-256-GCM. Se il tag fallisce, scarta il messaggio.

Doppia protezione: Se c è manomesso, Decaps restituisce una chiave pseudocasuale (\(K_{\text{reject}}\)). Anche se l'avversario indovinasse questa chiave, il tag AEAD di AES-GCM fallirebbe, garantendo l'integrità.

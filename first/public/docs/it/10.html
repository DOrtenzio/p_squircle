10.1 liboqs: la libreria C di riferimento

liboqs è la libreria C di riferimento per la crittografia post-quantum, sviluppata dal progetto Open Quantum Safe (OQS). Fornisce implementazioni ottimizzate e constant-time di ML-KEM e altri algoritmi PQC standardizzati NIST.

Installazione da sorgenti

# Dipendenze (Ubuntu/Debian)
sudo apt-get install cmake gcc libssl-dev

# Clone e build
git clone https://github.com/open-quantum-safe/liboqs.git
cd liboqs
mkdir build && cd build
cmake -DCMAKE_INSTALL_PREFIX=/usr/local ..
make -j$(nproc)
sudo make install

10.2 Esempio completo: KEM con ML-KEM-768 in C

#include <stdio.h>
#include <string.h>
#include <oqs/oqs.h>

int main() {
    OQS_STATUS rc;
    const char *kem_alg = OQS_KEM_alg_ml_kem_768;

    // Inizializza l'algoritmo
    OQS_KEM *kem = OQS_KEM_new(kem_alg);
    if (kem == NULL) {
        fprintf(stderr, "KEM non supportato\n");
        return 1;
    }

    printf("Algoritmo: %s\n", kem->method_name);
    printf("Chiave pubblica: %zu byte\n", kem->length_public_key);
    printf("Chiave privata: %zu byte\n", kem->length_secret_key);
    printf("Ciphertext: %zu byte\n", kem->length_ciphertext);
    printf("Shared secret: %zu byte\n\n", kem->length_shared_secret);

    // Allocazione memoria
    uint8_t *pk = malloc(kem->length_public_key);
    uint8_t *sk = malloc(kem->length_secret_key);
    uint8_t *ct = malloc(kem->length_ciphertext);
    uint8_t *ss_enc = malloc(kem->length_shared_secret);
    uint8_t *ss_dec = malloc(kem->length_shared_secret);

    // 1. KeyGen (Alice)
    rc = OQS_KEM_keypair(kem, pk, sk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "KeyGen fallita\n"); return 1; }
    printf("✓ KeyGen completata\n");

    // 2. Encaps (Bob: conosce solo pk)
    rc = OQS_KEM_encaps(kem, ct, ss_enc, pk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "Encaps fallita\n"); return 1; }
    printf("✓ Encaps completata\n");

    // 3. Decaps (Alice: usa sk per aprire ct)
    rc = OQS_KEM_decaps(kem, ss_dec, ct, sk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "Decaps fallita\n"); return 1; }
    printf("✓ Decaps completata\n\n");

    // 4. Verifica
    if (memcmp(ss_enc, ss_dec, kem->length_shared_secret) == 0) {
        printf("✅ Shared secret coincidono!\n");
        printf("   Primissimi byte: ");
        for (int i = 0; i < 8; i++) printf("%02x", ss_enc[i]);
        printf("...\n");
    } else {
        printf("❌ ERRORE: shared secret diversi!\n");
    }

    // Cleanup sicuro della memoria
    OQS_MEM_cleanse(sk, kem->length_secret_key);
    OQS_MEM_cleanse(ss_enc, kem->length_shared_secret);
    OQS_MEM_cleanse(ss_dec, kem->length_shared_secret);
    free(pk); free(ct);
    OQS_KEM_free(kem);
    
    return 0;
}

Compilazione:

gcc -o kem_example kem_example.c -loqs -lcrypto
./kem_example

10.3 Usare la chiave derivata con AES-256-GCM

Dopo aver ottenuto lo shared secret da ML-KEM, è possibile usarlo come chiave per un cifrario simmetrico. In produzione, si consiglia di usare HKDF per derivare chiavi separate.

#include <openssl/evp.h>
#include <oqs/oqs.h>

// Dopo aver ottenuto ss (32 byte) da ML-KEM:
void encrypt_with_kem_key(const uint8_t *ss, const uint8_t *plaintext,
                           size_t pt_len, uint8_t *ciphertext, uint8_t *tag,
                           const uint8_t *nonce) {
    EVP_CIPHER_CTX *ctx = EVP_CIPHER_CTX_new();
    int len;

    // Inizializza AES-256-GCM
    EVP_EncryptInit_ex(ctx, EVP_aes_256_gcm(), NULL, NULL, NULL);
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_IVLEN, 12, NULL);
    
    // Usa lo shared secret come chiave
    EVP_EncryptInit_ex(ctx, NULL, NULL, ss, nonce);
    
    // Cifratura
    EVP_EncryptUpdate(ctx, ciphertext, &len, plaintext, pt_len);
    EVP_EncryptFinal_ex(ctx, ciphertext + len, &len);
    
    // Recupera il tag di autenticazione
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_GET_TAG, 16, tag);
    
    EVP_CIPHER_CTX_free(ctx);
}

10.4 Python: binding liboqs

Liboqs fornisce binding Python ufficiali per test rapidi e prototipazione.

pip install liboqs-python
import oqs

# Algoritmo disponibile
kem = oqs.KeyEncapsulation("ML-KEM-768")

# KeyGen
public_key = kem.generate_keypair()

# Encaps (lato Bob)
kem_bob = oqs.KeyEncapsulation("ML-KEM-768")
ciphertext, shared_secret_enc = kem_bob.encap_secret(public_key)

# Decaps (lato Alice)
shared_secret_dec = kem.decap_secret(ciphertext)

assert shared_secret_enc == shared_secret_dec
print(f"✓ Shared secret: {shared_secret_enc.hex()[:16]}...")

kem.free()
kem_bob.free()

10.5 Python: kyber-py (solo didattica)

Per scopi puramente educativi esiste un'implementazione Python pura che non richiede librerie C esterne.

Attenzione: kyber-py non è constant-time e non deve essere usato in produzione.

                    
                        from kyber import Kyber768
                        kem = Kyber768()
                        pk, sk = kem.keygen()
                        key, ciphertext = kem.enc(pk)
                        _key = kem.dec(sk, ciphertext)
                        assert key == _key

10.6 Performance benchmarks

Benchmark su Intel Core i7-12700K (un core, senza istruzioni SIMD):

Operazione ML-KEM-512 ML-KEM-768 ML-KEM-1024
KeyGen 24 µs 37 µs 54 µs
Encaps 28 µs 43 µs 62 µs
Decaps 32 µs 48 µs 70 µs

Con ottimizzazioni AVX2

Operazione ML-KEM-768 (no SIMD) ML-KEM-768 (AVX2) Speedup
KeyGen 37 µs ~10 µs ~3.7×
Encaps 43 µs ~12 µs ~3.6×
Decaps 48 µs ~13 µs ~3.7×

Confronto con ECDH X25519

X25519 ML-KEM-768
KeyGen ~14 µs ~37 µs
Scambio ~30 µs ~48 µs
Chiave pubblica 32 B 1184 B

ML-KEM è circa 2× più lento di X25519, ma l'overhead sulla latenza di handshake TLS è trascurabile (< 1 ms) sulla maggior parte delle connessioni reali.

10.7 OpenSSL: installazione del provider OQS

OpenSSL 3.x supporta ML-KEM tramite il provider oqsprovider. Dalla versione 3.4 il supporto è nativo o facilmente integrabile.

# Build oqs-provider
git clone https://github.com/open-quantum-safe/oqs-provider.git
cd oqs-provider
cmake -DOPENSSL_ROOT_DIR=/usr/local/ssl .
make
sudo make install

# Verifica
openssl list -providers
# dovrebbe elencare: oqsprovider

10.8 Generazione chiavi ML-KEM con OpenSSL CLI

# Genera coppia di chiavi ML-KEM-768
openssl genpkey -algorithm mlkem768 -out private.pem
openssl pkey -in private.pem -pubout -out public.pem

# Visualizza i dettagli della chiave
openssl pkey -in private.pem -text -noout

10.9 TLS 1.3 con ML-KEM-768

Test locale (server + client)

# Server
openssl s_server -accept 4433 -cert server.crt -key server.key \
    -groups mlkem768

# Client (in un altro terminale)
openssl s_client -connect localhost:4433 -groups mlkem768

Verificare i gruppi supportati

openssl list -key-exchange-algorithms | grep -i kem

10.10 Strategia ibrida: X25519 + ML-KEM-768

L'approccio raccomandato per la migrazione è l'ibridizzazione: combinare ECDH (X25519) con ML-KEM-768. La chiave finale è derivata da entrambe:

\[ K = \text{HKDF}(K_{\text{X25519}} \| K_{\text{ML-KEM}}) \]

Vantaggio: sicuro se almeno uno dei due schemi regge. Se un computer quantistico rompe X25519, ML-KEM protegge. Se ML-KEM avesse un difetto sconosciuto, X25519 protegge.

10.11 Cipher suite ibride in TLS 1.3

Nome Gruppo Composizione
X25519MLKEM768 X25519 + ML-KEM-768
SecP256r1MLKEM768 P-256 + ML-KEM-768

A partire da Chrome 131 (fine 2024), X25519MLKEM768 è il gruppo di default. Firefox 128+ supporta lo stesso gruppo.

Configurazione OpenSSL

# Server che accetta sia X25519 classico sia il gruppo ibrido
openssl s_server -accept 4433 -cert server.crt -key server.key \
    -groups X25519MLKEM768:x25519:P-256

# Client che preferisce il gruppo ibrido
openssl s_client -connect localhost:4433 \
    -groups X25519MLKEM768:x25519

10.12 Integrazione in applicazioni C con OpenSSL

#include <openssl/ssl.h>
#include <openssl/err.h>

SSL_CTX *create_pqc_context(void) {
    SSL_CTX *ctx = SSL_CTX_new(TLS_server_method());
    if (!ctx) {
        ERR_print_errors_fp(stderr);
        return NULL;
    }

    // Imposta i gruppi preferiti: ibrido prima, poi classici come fallback
    if (SSL_CTX_set1_groups_list(ctx, "X25519MLKEM768:x25519:P-256") != 1) {
        fprintf(stderr, "Errore nella configurazione dei gruppi\n");
        SSL_CTX_free(ctx);
        return NULL;
    }

    return ctx;
}

10.13 Checklist di migrazione

Per chi sviluppa applicazioni

  • Inventariare dove viene usata crittografia asimmetrica (key exchange, firma, KEM).
  • Identificare quali dati devono rimanere segreti per più di 5 anni.
  • Aggiornare le dipendenze: OpenSSL ≥ 3.2, liboqs ≥ 0.10.
  • Adottare approccio ibrido: X25519 + ML-KEM-768 per TLS.
  • Per firma digitale: migrare a ML-DSA (FIPS 204) o SLH-DSA (FIPS 205).
  • Testare la dimensione aumentata di chiavi e ciphertext nei protocolli.
  • Verificare che timeout e buffer size non assumano chiavi di piccole dimensioni.

Per chi gestisce infrastruttura

  • Aggiornare TLS stack a versioni con supporto ML-KEM.
  • Abilitare X25519MLKEM768 nei server TLS.
  • Monitorare la compatibilità client (Chrome 131+, Firefox 128+ supportano PQC ibrido).
  • Pianificare la rotazione delle chiavi long-term.

Standard di riferimento

Standard Contenuto
FIPS 203 ML-KEM (Key Encapsulation)
FIPS 204 ML-DSA (firma digitale lattice-based)
FIPS 205 SLH-DSA (firma hash-based, conservativa)

10.14 Scenario: migrazione di un'API REST

Situazione attuale (pre-migrazione)

Client → TLS 1.3 con X25519 → Server API

Fase 1: ibrido (oggi, raccomandato)

Client → TLS 1.3 con X25519MLKEM768 → Server API

# Configurazione nginx
ssl_ecdh_curve X25519MLKEM768:x25519:P-256;

# Configurazione Apache
SSLOpenSSLConfCmd Curves X25519MLKEM768:x25519:P-256;

Fase 2: puro post-quantum (futuro)

Client → TLS 1.3 con ML-KEM-768 + ML-DSA → Server API

Da adottare quando la maggioranza dei client supporta ML-KEM nativo e i certificati server usano ML-DSA per la firma.

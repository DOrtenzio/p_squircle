6.1 KEM の形式的定義

3つのアルゴリズム

鍵カプセル化メカニズム（KEM）は、確率的多項式時間アルゴリズムの3つ組です。

\[ \text{KEM} = (\text{KeyGen},\ \text{Encaps},\ \text{Decaps}) \]
  • KeyGen() → (ek, dk)
    確率的アルゴリズム（内部乱数を使用）。入力は取りません。
    • ek：カプセル化鍵（公開鍵）
    • dk：デカプセル化鍵（秘密鍵）
  • Encaps(ek) → (K, c)
    ek が与えられると、以下を生成します。
    • \(K \in \{0,1\}^\ell\)：秘密の対称鍵（通常 256 ビット）
    • c：暗号文（「カプセル」）
  • Decaps(dk, c) → K
    dk と c が与えられると、\(K\) を回復します。

FIPS 203 の用語に関する注意： 標準では、カプセル化鍵に ek（pk ではない）、デカプセル化鍵に dk（sk ではない）を使用します。この区別は意図的です。公開鍵が任意のメッセージを暗号化するためではなく、カプセル化するためのものであることを強調しています。

正当性

KEM は、有効な鍵ペアごとに次が成り立つ場合に正当です。

\[ \Pr\bigl[\text{Decaps}(dk,\, c) = K \mid (K, c) \leftarrow \text{Encaps}(ek)\bigr] \geq 1 - \delta \]

ここで \(\delta\) は無視できる確率です（通常 \(< 2^{-128}\)）。
ML-KEM-768 の場合：\(\delta < 2^{-142}\)。

6.2 セキュリティ特性

IND-CPA（選択平文攻撃に対する識別不可能性）

IND-CPA セキュリティゲーム

挑戦者 攻撃者 \(\mathcal{A}\)
\((ek, dk) \leftarrow \text{KeyGen}()\)
\(ek \longrightarrow\)
チャレンジを選択（KEM では暗黙的）
\((K_0, c) \leftarrow \text{Encaps}(ek)\)
\(K_1 \leftarrow \text{Random}\)
\(b \leftarrow \{0, 1\}\)
\((c, K_b) \longrightarrow\)
\(b'\) を返す

アドバンテージ： \(\text{Adv}^{\text{IND-CPA}}_{\text{KEM}}(\mathcal{A}) = \left| \Pr[b' = b] - \frac{1}{2} \right|\)

すべての多項式時間攻撃者に対してアドバンテージが無視できる場合、KEM は IND-CPA です。直感的には、攻撃者は暗号文 c を見ても、実際の鍵 \(K\) とランダムな鍵を区別できません。

IND-CCA2（適応的選択暗号文攻撃に対する識別不可能性）

CPA と同様ですが、攻撃者はデカプセル化オラクルにもアクセスできます。

フェーズ アクション
初期化 \((ek, dk) \leftarrow \text{KeyGen}()\)、\(ek\) を送信
フェーズ1（問い合わせ） \(c_i \to K_i = \text{Decaps}(dk, c_i)\)
チャレンジ \((K_0, c^*) \leftarrow \text{Encaps}(ek)\)、\(K_1 \leftarrow \text{Random}\)、\(b \leftarrow \{0,1\}\)。\((c^*, K_b)\) を送信
フェーズ2（問い合わせ） \(c_j \to K_j = \text{Decaps}(dk, c_j)\)（\(c_j \neq c^*\)）
推測 \(b'\) を返す

IND-CCA2 は、実際の使用において KEM に要求されるセキュリティの標準です。

なぜ CCA2 が必要なのか？ 実際のプロトコル（TLS、SSH）では、能動的攻撃者が操作された暗号文を送信し、サーバーの応答を観察できます。MLWE においても、チャレンジ暗号文に近い暗号文のデカプセル化を知っている攻撃者は、秘密に関する情報を抽出できる可能性があります。ML-KEM は IND-CCA2 です。

追加の望ましい特性

  • ロバスト性： 異なる秘密鍵で同じ鍵にデカプセル化される暗号文を構築することが困難であること。
  • 前方秘匿性： 将来 dk が漏洩しても、過去のセッションは安全であること（エフェメラル鍵が必要）。

6.3 KEM vs PKE：なぜ KEM なのか

PKE（公開鍵暗号）

PKE は任意のメッセージを暗号化します：\(\text{Enc}(ek, m) \to c\)。問題は、メッセージ \(m\) が予測可能な構造を持つ場合（短いパスワード、クレジットカード番号）、攻撃者が低エントロピー攻撃やパディングオラクル攻撃（Bleichenbacher）を悪用できることです。

KEM：役割の分離

KEM はユーザーメッセージを暗号化しません。高エントロピーの対称鍵を生成し、それをカプセル化します。

\[ \text{システム} = \underbrace{\text{KEM}}_{K \text{ を交換}} + \underbrace{\text{AES-GCM}}_{K \text{ でデータを暗号化}} \]

利点：

  • 鍵 \(K\) は常に擬似ランダム → 低エントロピー攻撃がない
  • ユーザーメッセージに複雑なパディングは不要
  • \(K\) は対称暗号（DEM）と共に使用され、実際のデータを暗号化する

6.4 直感的な例：Diffie-Hellman からの KEM

ML-KEM 以前は、最も広く使われていた KEM は Diffie-Hellman 上に構築されていました。この例は構造の理解に役立ちます。

公開パラメータ： 素数 \(p\)、\(\mathbb{Z}_p^*\) の生成元 \(g\)。

アリス
  1. 秘密の \(a\) を選択
  2. \(A = g^a \bmod p\) を計算
A → ← B
ボブ
  1. 秘密の \(b\) を選択
  2. \(B = g^b \bmod p\) を計算
\[ \begin{aligned} \text{アリスが計算： } & K = B^a \bmod p = g^{ab} \bmod p \\ \text{ボブが計算： } & K = A^b \bmod p = g^{ab} \bmod p \end{aligned} \]

数値例： \(p = 17\)、\(g = 3\)、\(a = 5\)。

  • \(ek = 3^5 \bmod 17 = 5\)
  • ボブが \(b = 7\) を選択：\(c = 3^7 \bmod 17 = 11\)、\(K = H(5^7 \bmod 17) = H(10)\)
  • アリスがデカプセル化：\(K = H(11^5 \bmod 17) = H(10)\) ✓

6.5 Fujisaki-Okamoto（FO）変換

問題：CPA から CCA2 へ

CPA 安全なだけの PKE から、どのように IND-CCA2 KEM を構築するのでしょうか？答えは FO 変換です。

中心的なアイデア

  • 決定論的暗号化： 暗号化で使用されるランダム性は、ハッシュによってメッセージから決定論的に導出されます。暗号文が変更されると、再暗号化によって異なる結果が得られます。
  • 復号時の検証： 直接復号する代わりに、復号されたメッセージを再暗号化し、受信した暗号文と比較します。一致しない場合 → 暗黙的な拒否。

簡略化された FO スキーム

\[ \begin{aligned} \text{Encaps}(ek): & \quad m \leftarrow \{0,1\}^\ell, \ (K, r) = G(m), \ c = \text{Enc}(ek, m; r) \\ \text{Decaps}(dk, c): & \quad m' = \text{Dec}(dk, c), \ (K', r') = G(m'), \ c' = \text{Enc}(ek, m'; r') \\ & \quad \text{return } \begin{cases} K' & \text{if } c' = c \\ K_{\text{reject}} & \text{otherwise} \end{cases} \end{aligned} \]

ここで \(K_{\text{reject}} = H(z \| c)\)（\(z\) は固定秘密）。この「暗黙的拒否」は、攻撃者がエラーをオラクルとして使用することを防ぎます。

6.6 K-PKE（CPA）から ML-KEM（CCA2）へ

ML-KEM では、2レベルの構造は次の通りです。

ML-KEM（IND-CCA2）
└── K-PKE（IND-CPA）+ FO 変換
    └── MLWE 問題

ML-KEM.Encaps(ek)

m ← Random(32)                  // 256 ビットのランダムメッセージ
(K̄, r) = G(m ‖ H(ek))          // SHA3-512：K̄ = 最初の32バイト、r = 最後の32バイト
c = K-PKE.Encrypt(ek, m, r)     // ランダム性 r による決定論的暗号化
K = KDF(K̄ ‖ H(c))              // 最終鍵
return (K, c)

ML-KEM.Decaps(dk, c)

(dk_PKE, ek, h, z) = dk         // h = H(ek)、z = バックアップ秘密
m' = K-PKE.Decrypt(dk_PKE, c)   // 復号を試行
(K̄', r') = G(m' ‖ h)           // 再計算
c' = K-PKE.Encrypt(ek, m', r')  // 検証のための再暗号化
if c' == c:
    K = KDF(K̄' ‖ H(c))         // 復号成功
else:
    K = KDF(z ‖ H(c))           // バックアップ：擬似ランダム鍵
return K

重要な詳細： 秘密鍵 dk には再暗号化を行うための ek も含まれます。比較 c' == c は定数時間で実行されなければなりません。

6.7 実際のプロトコルにおける KEM：TLS 1.3

クライアント（ボブ）
サーバー（アリス）
ClientHello（ML-KEM-768 をサポート）
ServerHello + 証明書 + KeyShare（ek）
KeyShare（c）+ Finished（K による MAC）
Finished（K による MAC）

ハイブリッド X25519 + ML-KEM

実際には、TLS 1.3 はハイブリッドアプローチを使用します。

\[ K_{\text{TLS}} = \text{HKDF}(K_{\text{X25519}} \,\|\, K_{\text{ML-KEM}}) \]

これにより、2つのスキームの少なくとも1つが安全であればセキュリティが保証されます。グループ X25519MLKEM768 は Chrome 131+ ですでに展開されています。

6.8 KEM フローの汎用的構造

完全なフロー アリス（受信者）/ ボブ（送信者）

  1. アリス： KeyGen() で \((ek, dk)\) を生成。\(ek\) を公開。
  2. ボブ： \(ek\) を受信。Encaps(ek) を実行：
    • ランダムな \(m\) を生成
    • \((\bar{K}, r) = G(m \| H(ek))\)
    • \(c = \text{K-PKE.Encrypt}(ek, m, r)\)
    • \(K = \text{KDF}(\bar{K} \| H(c))\)
  3. ボブ： AES-256-GCM と \(K\)、ランダムなノンスを使用してデータを暗号化。
  4. ボブ： \((c, \text{nonce}, \text{暗号文}, \text{tag})\) をアリスに送信。
  5. アリス： Decaps(dk, c) を実行して \(K\) を回復。
  6. アリス： AES-256-GCM でデータを復号。タグが失敗した場合はメッセージを破棄。

二重保護： c が操作された場合、Decaps は擬似ランダム鍵（\(K_{\text{reject}}\)）を返します。たとえ攻撃者がこの鍵を推測できたとしても、AES-GCM の AEAD タグが失敗し、完全性が保証されます。

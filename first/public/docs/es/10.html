10.1 liboqs: la librería C de referencia

liboqs es la librería C de referencia para criptografía post-cuántica, desarrollada por el proyecto Open Quantum Safe (OQS). Proporciona implementaciones optimizadas y de tiempo constante de ML-KEM y otros algoritmos PQC estandarizados por el NIST.

Instalación desde fuentes

# Dependencias (Ubuntu/Debian)
sudo apt-get install cmake gcc libssl-dev

# Clonar y compilar
git clone https://github.com/open-quantum-safe/liboqs.git
cd liboqs
mkdir build && cd build
cmake -DCMAKE_INSTALL_PREFIX=/usr/local ..
make -j$(nproc)
sudo make install

10.2 Ejemplo completo: KEM con ML-KEM-768 en C

#include <stdio.h>
#include <string.h>
#include <oqs/oqs.h>

int main() {
    OQS_STATUS rc;
    const char *kem_alg = OQS_KEM_alg_ml_kem_768;

    // Inicializar el algoritmo
    OQS_KEM *kem = OQS_KEM_new(kem_alg);
    if (kem == NULL) {
        fprintf(stderr, "KEM no soportado\n");
        return 1;
    }

    printf("Algoritmo: %s\n", kem->method_name);
    printf("Clave pública: %zu bytes\n", kem->length_public_key);
    printf("Clave privada: %zu bytes\n", kem->length_secret_key);
    printf("Texto cifrado: %zu bytes\n", kem->length_ciphertext);
    printf("Secreto compartido: %zu bytes\n\n", kem->length_shared_secret);

    // Asignación de memoria
    uint8_t *pk = malloc(kem->length_public_key);
    uint8_t *sk = malloc(kem->length_secret_key);
    uint8_t *ct = malloc(kem->length_ciphertext);
    uint8_t *ss_enc = malloc(kem->length_shared_secret);
    uint8_t *ss_dec = malloc(kem->length_shared_secret);

    // 1. KeyGen (Alice)
    rc = OQS_KEM_keypair(kem, pk, sk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "KeyGen falló\n"); return 1; }
    printf("✓ KeyGen completada\n");

    // 2. Encaps (Bob: solo conoce pk)
    rc = OQS_KEM_encaps(kem, ct, ss_enc, pk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "Encaps falló\n"); return 1; }
    printf("✓ Encaps completada\n");

    // 3. Decaps (Alice: usa sk para abrir ct)
    rc = OQS_KEM_decaps(kem, ss_dec, ct, sk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "Decaps falló\n"); return 1; }
    printf("✓ Decaps completada\n\n");

    // 4. Verificación
    if (memcmp(ss_enc, ss_dec, kem->length_shared_secret) == 0) {
        printf("✅ ¡Los secretos compartidos coinciden!\n");
        printf("   Primeros bytes: ");
        for (int i = 0; i < 8; i++) printf("%02x", ss_enc[i]);
        printf("...\n");
    } else {
        printf("❌ ERROR: ¡los secretos compartidos son diferentes!\n");
    }

    // Limpieza segura de memoria
    OQS_MEM_cleanse(sk, kem->length_secret_key);
    OQS_MEM_cleanse(ss_enc, kem->length_shared_secret);
    OQS_MEM_cleanse(ss_dec, kem->length_shared_secret);
    free(pk); free(ct);
    OQS_KEM_free(kem);

    return 0;
}

Compilación:

gcc -o kem_example kem_example.c -loqs -lcrypto
./kem_example

10.3 Usar la clave derivada con AES-256-GCM

Después de obtener el secreto compartido de ML-KEM, se puede usar como clave para un cifrador simétrico. En producción, se recomienda usar HKDF para derivar claves separadas.

#include <openssl/evp.h>
#include <oqs/oqs.h>

// Después de obtener ss (32 bytes) de ML-KEM:
void encrypt_with_kem_key(const uint8_t *ss, const uint8_t *plaintext,
                           size_t pt_len, uint8_t *ciphertext, uint8_t *tag,
                           const uint8_t *nonce) {
    EVP_CIPHER_CTX *ctx = EVP_CIPHER_CTX_new();
    int len;

    // Inicializar AES-256-GCM
    EVP_EncryptInit_ex(ctx, EVP_aes_256_gcm(), NULL, NULL, NULL);
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_IVLEN, 12, NULL);

    // Usar el secreto compartido como clave
    EVP_EncryptInit_ex(ctx, NULL, NULL, ss, nonce);

    // Cifrado
    EVP_EncryptUpdate(ctx, ciphertext, &len, plaintext, pt_len);
    EVP_EncryptFinal_ex(ctx, ciphertext + len, &len);

    // Recuperar la etiqueta de autenticación
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_GET_TAG, 16, tag);

    EVP_CIPHER_CTX_free(ctx);
}

10.4 Python: binding liboqs

Liboqs proporciona bindings oficiales para Python para pruebas rápidas y creación de prototipos.

pip install liboqs-python
import oqs

# Algoritmo disponible
kem = oqs.KeyEncapsulation("ML-KEM-768")

# KeyGen
public_key = kem.generate_keypair()

# Encaps (lado de Bob)
kem_bob = oqs.KeyEncapsulation("ML-KEM-768")
ciphertext, shared_secret_enc = kem_bob.encap_secret(public_key)

# Decaps (lado de Alice)
shared_secret_dec = kem.decap_secret(ciphertext)

assert shared_secret_enc == shared_secret_dec
print(f"✓ Secreto compartido: {shared_secret_enc.hex()[:16]}...")

kem.free()
kem_bob.free()

10.5 Python: kyber-py (solo didáctico)

Para propósitos puramente educativos, existe una implementación en Python puro que no requiere librerías C externas.

Atención: kyber-py no es de tiempo constante y no debe usarse en producción.

                    
                        from kyber import Kyber768
                        kem = Kyber768()
                        pk, sk = kem.keygen()
                        key, ciphertext = kem.enc(pk)
                        _key = kem.dec(sk, ciphertext)
                        assert key == _key

10.6 Benchmarks de rendimiento

Benchmarks en Intel Core i7-12700K (un núcleo, sin instrucciones SIMD):

Operación ML-KEM-512 ML-KEM-768 ML-KEM-1024
KeyGen 24 µs 37 µs 54 µs
Encaps 28 µs 43 µs 62 µs
Decaps 32 µs 48 µs 70 µs

Con optimizaciones AVX2

Operación ML-KEM-768 (sin SIMD) ML-KEM-768 (AVX2) Speedup
KeyGen 37 µs ~10 µs ~3.7×
Encaps 43 µs ~12 µs ~3.6×
Decaps 48 µs ~13 µs ~3.7×

Comparación con ECDH X25519

X25519 ML-KEM-768
KeyGen ~14 µs ~37 µs
Intercambio ~30 µs ~48 µs
Clave pública 32 B 1184 B

ML-KEM es aproximadamente 2 veces más lento que X25519, pero la sobrecarga en la latencia del handshake TLS es insignificante (< 1 ms) en la mayoría de las conexiones reales.

10.7 OpenSSL: instalación del provider OQS

OpenSSL 3.x soporta ML-KEM a través del provider oqsprovider. A partir de la versión 3.4, el soporte es nativo o fácilmente integrable.

# Compilar oqs-provider
git clone https://github.com/open-quantum-safe/oqs-provider.git
cd oqs-provider
cmake -DOPENSSL_ROOT_DIR=/usr/local/ssl .
make
sudo make install

# Verificar
openssl list -providers
# debería mostrar: oqsprovider

10.8 Generación de claves ML-KEM con OpenSSL CLI

# Generar par de claves ML-KEM-768
openssl genpkey -algorithm mlkem768 -out private.pem
openssl pkey -in private.pem -pubout -out public.pem

# Ver los detalles de la clave
openssl pkey -in private.pem -text -noout

10.9 TLS 1.3 con ML-KEM-768

Prueba local (servidor + cliente)

# Servidor
openssl s_server -accept 4433 -cert server.crt -key server.key \
    -groups mlkem768

# Cliente (en otra terminal)
openssl s_client -connect localhost:4433 -groups mlkem768

Verificar los grupos soportados

openssl list -key-exchange-algorithms | grep -i kem

10.10 Estrategia híbrida: X25519 + ML-KEM-768

El enfoque recomendado para la migración es la hibridización: combinar ECDH (X25519) con ML-KEM-768. La clave final se deriva de ambas:

\[ K = \text{HKDF}(K_{\text{X25519}} \| K_{\text{ML-KEM}}) \]

Ventaja: seguro si al menos uno de los dos esquemas se mantiene. Si una computadora cuántica rompe X25519, ML-KEM protege. Si ML-KEM tuviera un defecto desconocido, X25519 protege.

10.11 Cipher suites híbridas en TLS 1.3

Nombre del Grupo Composición
X25519MLKEM768 X25519 + ML-KEM-768
SecP256r1MLKEM768 P-256 + ML-KEM-768

A partir de Chrome 131 (finales de 2024), X25519MLKEM768 es el grupo por defecto. Firefox 128+ soporta el mismo grupo.

Configuración OpenSSL

# Servidor que acepta tanto X25519 clásico como el grupo híbrido
openssl s_server -accept 4433 -cert server.crt -key server.key \
    -groups X25519MLKEM768:x25519:P-256

# Cliente que prefiere el grupo híbrido
openssl s_client -connect localhost:4433 \
    -groups X25519MLKEM768:x25519

10.12 Integración en aplicaciones C con OpenSSL

#include <openssl/ssl.h>
#include <openssl/err.h>

SSL_CTX *create_pqc_context(void) {
    SSL_CTX *ctx = SSL_CTX_new(TLS_server_method());
    if (!ctx) {
        ERR_print_errors_fp(stderr);
        return NULL;
    }

    // Establecer los grupos preferidos: híbrido primero, luego clásicos como fallback
    if (SSL_CTX_set1_groups_list(ctx, "X25519MLKEM768:x25519:P-256") != 1) {
        fprintf(stderr, "Error en la configuración de grupos\n");
        SSL_CTX_free(ctx);
        return NULL;
    }

    return ctx;
}

10.13 Lista de verificación para la migración

Para quienes desarrollan aplicaciones

  • Inventariar dónde se usa criptografía asimétrica (intercambio de claves, firma, KEM).
  • Identificar qué datos deben permanecer secretos durante más de 5 años.
  • Actualizar las dependencias: OpenSSL ≥ 3.2, liboqs ≥ 0.10.
  • Adoptar el enfoque híbrido: X25519 + ML-KEM-768 para TLS.
  • Para firma digital: migrar a ML-DSA (FIPS 204) o SLH-DSA (FIPS 205).
  • Probar el aumento de tamaño de claves y textos cifrados en los protocolos.
  • Verificar que los timeouts y tamaños de búfer no asuman claves de pequeño tamaño.

Para quienes gestionan infraestructura

  • Actualizar la pila TLS a versiones con soporte ML-KEM.
  • Habilitar X25519MLKEM768 en los servidores TLS.
  • Monitorear la compatibilidad de los clientes (Chrome 131+, Firefox 128+ soportan PQC híbrido).
  • Planificar la rotación de claves a largo plazo.

Estándares de referencia

Estándar Contenido
FIPS 203 ML-KEM (Key Encapsulation)
FIPS 204 ML-DSA (firma digital basada en retículos)
FIPS 205 SLH-DSA (firma basada en hash, conservadora)

10.14 Escenario: migración de una API REST

Situación actual (pre-migración)

Cliente → TLS 1.3 con X25519 → Servidor API

Fase 1: híbrido (hoy, recomendado)

Cliente → TLS 1.3 con X25519MLKEM768 → Servidor API

# Configuración nginx
ssl_ecdh_curve X25519MLKEM768:x25519:P-256;

# Configuración Apache
SSLOpenSSLConfCmd Curves X25519MLKEM768:x25519:P-256;

Fase 2: puramente post-cuántico (futuro)

Cliente → TLS 1.3 con ML-KEM-768 + ML-DSA → Servidor API

Para adoptar cuando la mayoría de los clientes soporten ML-KEM nativo y los certificados del servidor usen ML-DSA para la firma.

6.1 Definición formal de KEM

Tripleta de algoritmos

Un Key Encapsulation Mechanism (KEM) es una tripleta de algoritmos probabilísticos polinomiales:

\[ \text{KEM} = (\text{KeyGen},\ \text{Encaps},\ \text{Decaps}) \]
  • KeyGen() → (ek, dk)
    Algoritmo probabilístico (usa aleatoriedad interna). No toma entrada.
    • ek: encapsulation key (clave pública)
    • dk: decapsulation key (clave privada)
  • Encaps(ek) → (K, c)
    Dado ek, produce:
    • \(K \in \{0,1\}^\ell\): clave simétrica secreta (típicamente 256 bits)
    • c: texto cifrado (la "cápsula")
  • Decaps(dk, c) → K
    Dado dk y c, recupera \(K\).

Nota terminológica FIPS 203: el estándar usa ek para encapsulation key (no pk) y dk para decapsulation key (no sk). La distinción es intencional: subraya que la clave pública sirve para encapsular, no para cifrar mensajes arbitrarios.

Corrección

Un KEM es correcto si para cada par de claves válido:

\[ \Pr\bigl[\text{Decaps}(dk,\, c) = K \mid (K, c) \leftarrow \text{Encaps}(ek)\bigr] \geq 1 - \delta \]

donde \(\delta\) es una probabilidad de error despreciable (típicamente \(< 2^{-128}\)).
Para ML-KEM-768: \(\delta < 2^{-142}\).

6.2 Propiedades de seguridad

IND-CPA (Indistinguishability under Chosen Plaintext Attack)

Juego de seguridad IND-CPA

Desafiante Atacante \(\mathcal{A}\)
\((ek, dk) \leftarrow \text{KeyGen}()\)
\(ek \longrightarrow\)
Elige el desafío (implícito en el KEM)
\((K_0, c) \leftarrow \text{Encaps}(ek)\)
\(K_1 \leftarrow \text{Random}\)
\(b \leftarrow \{0, 1\}\)
\((c, K_b) \longrightarrow\)
Devuelve \(b'\)

Ventaja: \(\text{Adv}^{\text{IND-CPA}}_{\text{KEM}}(\mathcal{A}) = \left| \Pr[b' = b] - \frac{1}{2} \right|\)

El KEM es IND-CPA si la ventaja es despreciable para todo atacante polinomial. Intuitivamente: el atacante no puede distinguir la clave \(K\) real de una aleatoria, incluso viendo el texto cifrado c.

IND-CCA2 (Indistinguishability under Adaptive Chosen Ciphertext Attack)

Como CPA, pero el atacante también tiene acceso a un oráculo de desencapsulación:

Fase Acción
Inicialización \((ek, dk) \leftarrow \text{KeyGen}()\), envía \(ek\)
Fase 1 (Consulta) \(c_i \to K_i = \text{Decaps}(dk, c_i)\)
Desafío \((K_0, c^*) \leftarrow \text{Encaps}(ek)\), \(K_1 \leftarrow \text{Random}\), \(b \leftarrow \{0,1\}\). Envía \((c^*, K_b)\).
Fase 2 (Consulta) \(c_j \to K_j = \text{Decaps}(dk, c_j)\) con \(c_j \neq c^*\)
Suposición Devuelve \(b'\)

IND-CCA2 es el estándar de seguridad requerido para los KEM en uso real.

¿Por qué es necesario CCA2? En un protocolo real (TLS, SSH), un atacante activo puede enviar textos cifrados manipulados y observar las respuestas del servidor. Incluso en MLWE, un atacante que conoce la desencapsulación de textos cifrados cercanos al texto cifrado desafío podría extraer información sobre el secreto. ML-KEM es IND-CCA2.

Propiedades adicionales deseables

  • Robustez (Robustness): difícil construir textos cifrados que se desencapsulen a la misma clave con dos claves privadas diferentes.
  • Secreto hacia adelante (Forward secrecy): si la clave privada dk se ve comprometida en el futuro, las sesiones pasadas permanecen seguras (requiere claves efímeras).

6.3 KEM vs PKE: por qué los KEM

PKE (Public Key Encryption)

Un PKE cifra mensajes arbitrarios: \(\text{Enc}(ek, m) \to c\). El problema es que si el mensaje \(m\) tiene una estructura predecible (contraseña corta, número de tarjeta), un atacante puede explotar ataques de baja entropía o de oráculo de relleno (Bleichenbacher).

KEM: separación de roles

El KEM no cifra mensajes de usuario. Genera una clave simétrica de alta entropía y la encapsula:

\[ \text{Sistema} = \underbrace{\text{KEM}}_{\text{intercambia } K} + \underbrace{\text{AES-GCM}}_{\text{cifra datos con } K} \]

Ventajas:

  • La clave \(K\) es siempre pseudoaleatoria → sin ataques de baja entropía.
  • No se necesita un relleno complejo para mensajes de usuario.
  • \(K\) se usa con un cifrador simétrico (DEM) para cifrar los datos reales.

6.4 Ejemplo intuitivo: KEM desde Diffie-Hellman

Antes de ML-KEM, el KEM más usado se construía sobre Diffie-Hellman. Este ejemplo ayuda a comprender la estructura.

Parámetros públicos: primo \(p\), generador \(g\) de \(\mathbb{Z}_p^*\).

Alice
  1. Elige \(a\) secreto
  2. Calcula \(A = g^a \bmod p\)
A → ← B
Bob
  1. Elige \(b\) secreto
  2. Calcula \(B = g^b \bmod p\)
\[ \begin{aligned} \text{Alice calcula: } & K = B^a \bmod p = g^{ab} \bmod p \\ \text{Bob calcula: } & K = A^b \bmod p = g^{ab} \bmod p \end{aligned} \]

Ejemplo numérico: \(p = 17\), \(g = 3\), \(a = 5\).

  • \(ek = 3^5 \bmod 17 = 5\)
  • Bob elige \(b = 7\): \(c = 3^7 \bmod 17 = 11\), \(K = H(5^7 \bmod 17) = H(10)\)
  • Alice desencapsula: \(K = H(11^5 \bmod 17) = H(10)\) ✓

6.5 La transformación Fujisaki-Okamoto (FO)

El problema: de CPA a CCA2

Partiendo de un PKE solo CPA-seguro, ¿cómo construir un KEM IND-CCA2? La respuesta es la transformación FO.

Idea central

  • Cifrado determinista: la aleatoriedad usada en el cifrado se deriva deterministamente del mensaje mediante un hash. Si el texto cifrado se modifica, el recifrado produce algo diferente.
  • Verificación en el descifrado: en lugar de descifrar directamente, se recifra el mensaje descifrado y se compara con el texto cifrado recibido. Si no coinciden → rechazo implícito.

Esquema FO simplificado

\[ \begin{aligned} \text{Encaps}(ek): & \quad m \leftarrow \{0,1\}^\ell, \ (K, r) = G(m), \ c = \text{Enc}(ek, m; r) \\ \text{Decaps}(dk, c): & \quad m' = \text{Dec}(dk, c), \ (K', r') = G(m'), \ c' = \text{Enc}(ek, m'; r') \\ & \quad \text{return } \begin{cases} K' & \text{si } c' = c \\ K_{\text{reject}} & \text{en caso contrario} \end{cases} \end{aligned} \]

Donde \(K_{\text{reject}} = H(z \| c)\) con \(z\) secreto fijo. Este "rechazo implícito" impide al atacante usar los errores como oráculo.

6.6 De K-PKE (CPA) a ML-KEM (CCA2)

En ML-KEM, la estructura de dos niveles es:

ML-KEM (IND-CCA2)
└── K-PKE (IND-CPA) + transformación FO
    └── problema MLWE

ML-KEM.Encaps(ek)

m ← Random(32)                  // mensaje aleatorio de 256 bits
(K̄, r) = G(m ‖ H(ek))          // SHA3-512: K̄ = primeros 32 bytes, r = últimos 32 bytes
c = K-PKE.Encrypt(ek, m, r)     // cifrado determinista con aleatoriedad r
K = KDF(K̄ ‖ H(c))              // clave final
return (K, c)

ML-KEM.Decaps(dk, c)

(dk_PKE, ek, h, z) = dk         // h = H(ek), z = secreto de respaldo
m' = K-PKE.Decrypt(dk_PKE, c)   // intento de descifrado
(K̄', r') = G(m' ‖ h)           // recalcular
c' = K-PKE.Encrypt(ek, m', r')  // recifrado de verificación
si c' == c:
    K = KDF(K̄' ‖ H(c))         // descifrado exitoso
en caso contrario:
    K = KDF(z ‖ H(c))           // respaldo: clave pseudoaleatoria
return K

Detalles importantes: La clave privada dk también contiene ek para poder hacer el recifrado. La comparación c' == c debe ser de tiempo constante.

6.7 KEM en un protocolo real: TLS 1.3

Cliente (Bob)
Servidor (Alice)
ClientHello (soporta ML-KEM-768)
ServerHello + Certificado + KeyShare (ek)
KeyShare (c) + Finished (MAC con K)
Finished (MAC con K)

Híbrido X25519 + ML-KEM

En la práctica, TLS 1.3 usa un enfoque híbrido:

\[ K_{\text{TLS}} = \text{HKDF}(K_{\text{X25519}} \,\|\, K_{\text{ML-KEM}}) \]

Esto garantiza la seguridad si al menos uno de los dos esquemas se mantiene. El grupo X25519MLKEM768 ya está desplegado en Chrome 131+.

6.8 Estructura genérica del flujo KEM

Flujo completo Alice (Destinatario) / Bob (Remitente)

  1. Alice: KeyGen() genera \((ek, dk)\). Publica \(ek\).
  2. Bob: Recibe \(ek\). Ejecuta Encaps(ek):
    • Genera \(m\) aleatorio
    • \((\bar{K}, r) = G(m \| H(ek))\)
    • \(c = \text{K-PKE.Encrypt}(ek, m, r)\)
    • \(K = \text{KDF}(\bar{K} \| H(c))\)
  3. Bob: Cifra los datos con AES-256-GCM usando \(K\) y un nonce aleatorio.
  4. Bob: Envía \((c, \text{nonce}, \text{texto cifrado}, \text{tag})\) a Alice.
  5. Alice: Ejecuta Decaps(dk, c) para recuperar \(K\).
  6. Alice: Descifra los datos con AES-256-GCM. Si el tag falla, descarta el mensaje.

Doble protección: Si c es manipulado, Decaps devuelve una clave pseudoaleatoria (\(K_{\text{reject}}\)). Incluso si el atacante adivinara esta clave, el tag AEAD de AES-GCM fallaría, garantizando la integridad.

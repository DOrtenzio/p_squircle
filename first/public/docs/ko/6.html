6.1 KEM의 형식적 정의

알고리즘 삼중항

키 캡슐화 메커니즘(KEM)은 확률적 다항식 알고리즘의 삼중항입니다:

\[ \text{KEM} = (\text{KeyGen},\ \text{Encaps},\ \text{Decaps}) \]
  • KeyGen() → (ek, dk)
    확률적 알고리즘(내부 난수성 사용). 입력을 받지 않습니다.
    • ek: 캡슐화 키 (공개 키)
    • dk: 역캡슐화 키 (개인 키)
  • Encaps(ek) → (K, c)
    ek가 주어지면 다음을 생성합니다:
    • \(K \in \{0,1\}^\ell\): 비밀 대칭 키 (일반적으로 256비트)
    • c: 암호문 ("캡슐")
  • Decaps(dk, c) → K
    dk와 c가 주어지면 \(K\)를 복구합니다.

FIPS 203 용어 참고: 표준은 pk 대신 ek(캡슐화 키), sk 대신 dk(역캡슐화 키)를 사용합니다. 이 구분은 의도적입니다: 공개 키가 임의의 메시지를 암호화하는 것이 아니라 캡슐화하는 역할임을 강조합니다.

정확성

KEM은 유효한 각 키 쌍에 대해 다음이 성립하면 정확합니다:

\[ \Pr\bigl[\text{Decaps}(dk,\, c) = K \mid (K, c) \leftarrow \text{Encaps}(ek)\bigr] \geq 1 - \delta \]

여기서 \(\delta\)는 무시할 수 있는 오류 확률입니다(일반적으로 \(< 2^{-128}\)).
ML-KEM-768의 경우: \(\delta < 2^{-142}\).

6.2 보안 속성

IND-CPA (선택 평문 공격 아래 구별 불가능성)

IND-CPA 보안 게임

도전자 공격자 \(\mathcal{A}\)
\((ek, dk) \leftarrow \text{KeyGen}()\)
\(ek \longrightarrow\)
도전 선택 (KEM에서 암시적)
\((K_0, c) \leftarrow \text{Encaps}(ek)\)
\(K_1 \leftarrow \text{Random}\)
\(b \leftarrow \{0, 1\}\)
\((c, K_b) \longrightarrow\)
\(b'\) 반환

이점: \(\text{Adv}^{\text{IND-CPA}}_{\text{KEM}}(\mathcal{A}) = \left| \Pr[b' = b] - \frac{1}{2} \right|\)

KEM은 모든 다항식 시간 공격자에 대해 이점이 무시할 수 있으면 IND-CPA입니다. 직관적으로: 공격자는 암호문 c를 보더라도 실제 키 \(K\)와 무작위 키를 구별할 수 없습니다.

IND-CCA2 (적응적 선택 암호문 공격 아래 구별 불가능성)

CPA와 같지만, 공격자는 역캡슐화 오라클에 접근할 수 있습니다:

단계 동작
초기화 \((ek, dk) \leftarrow \text{KeyGen}()\), \(ek\) 전송
1단계 (질의) \(c_i \to K_i = \text{Decaps}(dk, c_i)\)
도전 \((K_0, c^*) \leftarrow \text{Encaps}(ek)\), \(K_1 \leftarrow \text{Random}\), \(b \leftarrow \{0,1\}\). \((c^*, K_b)\) 전송.
2단계 (질의) \(c_j \to K_j = \text{Decaps}(dk, c_j)\) (단, \(c_j \neq c^*\))
추측 \(b'\) 반환

IND-CCA2는 실제 사용되는 KEM에 요구되는 보안 표준입니다.

CCA2가 필요한 이유는? 실제 프로토콜(TLS, SSH)에서 능동적 공격자는 조작된 암호문을 전송하고 서버의 응답을 관찰할 수 있습니다. MLWE에서도, 도전 암호문에 가까운 암호문의 역캡슐화를 아는 공격자는 비밀에 대한 정보를 추출할 수 있습니다. ML-KEM은 IND-CCA2입니다.

추가 바람직한 속성

  • 강건성 (Robustness): 두 개의 다른 개인 키로 동일한 키로 역캡슐화되는 암호문을 구성하기 어려움.
  • 순방향 비밀성 (Forward secrecy): 개인 키 dk가 미래에 손상되더라도 과거 세션은 안전함(임시 키 필요).

6.3 KEM vs PKE: KEM의 이유

PKE (공개 키 암호화)

PKE는 임의의 메시지를 암호화합니다: \(\text{Enc}(ek, m) \to c\). 문제는 메시지 \(m\)이 예측 가능한 구조를 가지면(짧은 암호, 카드 번호), 공격자가 낮은 엔트로피 공격이나 패딩 오라클 공격(Bleichenbacher)을 악용할 수 있다는 것입니다.

KEM: 역할 분리

KEM은 사용자 메시지를 암호화하지 않습니다. 높은 엔트로피의 대칭 키를 생성하고 캡슐화합니다:

\[ \text{시스템} = \underbrace{\text{KEM}}_{K \text{ 교환}} + \underbrace{\text{AES-GCM}}_{K \text{로 데이터 암호화}} \]

장점:

  • 키 \(K\)는 항상 의사 난수 → 낮은 엔트로피 공격 없음.
  • 사용자 메시지에 대한 복잡한 패딩이 필요 없음.
  • \(K\)는 실제 데이터를 암호화하기 위해 대칭 암호(DEM)와 함께 사용됨.

6.4 직관적 예제: 디피-헬만으로부터의 KEM

ML-KEM 이전에 가장 많이 사용된 KEM은 디피-헬만 위에 구축되었습니다. 이 예제는 구조를 이해하는 데 도움이 됩니다.

공개 매개변수: 소수 \(p\), \(\mathbb{Z}_p^*\)의 생성자 \(g\).

앨리스
  1. 비밀 \(a\) 선택
  2. \(A = g^a \bmod p\) 계산
A → ← B
밥
  1. 비밀 \(b\) 선택
  2. \(B = g^b \bmod p\) 계산
\[ \begin{aligned} \text{앨리스 계산: } & K = B^a \bmod p = g^{ab} \bmod p \\ \text{밥 계산: } & K = A^b \bmod p = g^{ab} \bmod p \end{aligned} \]

수치 예제: \(p = 17\), \(g = 3\), \(a = 5\).

  • \(ek = 3^5 \bmod 17 = 5\)
  • 밥이 \(b = 7\) 선택: \(c = 3^7 \bmod 17 = 11\), \(K = H(5^7 \bmod 17) = H(10)\)
  • 앨리스 역캡슐화: \(K = H(11^5 \bmod 17) = H(10)\) ✓

6.5 후지사키-오카모토 변환 (FO)

문제: CPA에서 CCA2로

CPA-안전한 PKE만으로부터 IND-CCA2 KEM을 어떻게 구축할까요? 답은 FO 변환입니다.

핵심 아이디어

  • 결정론적 암호화: 암호화에 사용되는 난수성은 해시를 통해 메시지에서 결정론적으로 파생됩니다. 암호문이 수정되면 재암호화 결과가 달라집니다.
  • 복호화 시 검증: 직접 복호화하는 대신, 복호화된 메시지를 재암호화하고 받은 암호문과 비교합니다. 일치하지 않으면 → 암시적 거부.

간략화된 FO 방식

\[ \begin{aligned} \text{Encaps}(ek): & \quad m \leftarrow \{0,1\}^\ell, \ (K, r) = G(m), \ c = \text{Enc}(ek, m; r) \\ \text{Decaps}(dk, c): & \quad m' = \text{Dec}(dk, c), \ (K', r') = G(m'), \ c' = \text{Enc}(ek, m'; r') \\ & \quad \text{return } \begin{cases} K' & \text{if } c' = c \\ K_{\text{reject}} & \text{otherwise} \end{cases} \end{aligned} \]

여기서 \(K_{\text{reject}} = H(z \| c)\) (\(z\)는 고정 비밀). 이 "암시적 거부"는 공격자가 오류를 오라클로 사용하는 것을 방지합니다.

6.6 K-PKE (CPA)에서 ML-KEM (CCA2)으로

ML-KEM에서 2단계 구조는 다음과 같습니다:

ML-KEM (IND-CCA2)
└── K-PKE (IND-CPA) + FO 변환
    └── MLWE 문제

ML-KEM.Encaps(ek)

m ← Random(32)                  // 256비트 무작위 메시지
(K̄, r) = G(m ‖ H(ek))          // SHA3-512: K̄ = 처음 32바이트, r = 마지막 32바이트
c = K-PKE.Encrypt(ek, m, r)     // 난수성 r로 결정론적 암호화
K = KDF(K̄ ‖ H(c))              // 최종 키
return (K, c)

ML-KEM.Decaps(dk, c)

(dk_PKE, ek, h, z) = dk         // h = H(ek), z = 백업 비밀
m' = K-PKE.Decrypt(dk_PKE, c)   // 복호화 시도
(K̄', r') = G(m' ‖ h)           // 재계산
c' = K-PKE.Encrypt(ek, m', r')  // 검증 재암호화
if c' == c:
    K = KDF(K̄' ‖ H(c))         // 복호화 성공
else:
    K = KDF(z ‖ H(c))           // 백업: 의사 난수 키
return K

중요 세부사항: 개인 키 dk는 재암호화를 위해 ek도 포함합니다. 비교 c' == c는 일정 시간에 실행되어야 합니다.

6.7 실제 프로토콜에서의 KEM: TLS 1.3

클라이언트 (밥)
서버 (앨리스)
ClientHello (ML-KEM-768 지원)
ServerHello + 인증서 + KeyShare (ek)
KeyShare (c) + Finished (K로 MAC)
Finished (K로 MAC)

하이브리드 X25519 + ML-KEM

실제로 TLS 1.3은 하이브리드 접근법을 사용합니다:

\[ K_{\text{TLS}} = \text{HKDF}(K_{\text{X25519}} \,\|\, K_{\text{ML-KEM}}) \]

이는 두 방식 중 적어도 하나가 안전하게 유지되면 보안을 보장합니다. X25519MLKEM768 그룹은 이미 Chrome 131+에 배포되었습니다.

6.8 KEM 흐름의 일반적 구조

전체 흐름: 앨리스 (수신자) / 밥 (송신자)

  1. 앨리스: KeyGen()으로 \((ek, dk)\) 생성. \(ek\) 공개.
  2. 밥: \(ek\) 수신. Encaps(ek) 실행:
    • 무작위 \(m\) 생성
    • \((\bar{K}, r) = G(m \| H(ek))\)
    • \(c = \text{K-PKE.Encrypt}(ek, m, r)\)
    • \(K = \text{KDF}(\bar{K} \| H(c))\)
  3. 밥: \(K\)와 무작위 논스로 AES-256-GCM을 사용하여 데이터 암호화.
  4. 밥: \((c, \text{논스}, \text{암호문}, \text{태그})\)를 앨리스에게 전송.
  5. 앨리스: Decaps(dk, c) 실행하여 \(K\) 복구.
  6. 앨리스: AES-256-GCM으로 데이터 복호화. 태그가 실패하면 메시지 폐기.

이중 보호: c가 조작되면 Decaps는 의사 난수 키(\(K_{\text{reject}}\))를 반환합니다. 공격자가 이 키를 추측하더라도 AES-GCM의 AEAD 태그가 실패하여 무결성을 보장합니다.

6.1 Formele definitie van KEM

Drietal algoritmen

Een Key Encapsulation Mechanism (KEM) is een drietal probabilistische polynomiale algoritmen:

\[ \text{KEM} = (\text{KeyGen},\ \text{Encaps},\ \text{Decaps}) \]
  • KeyGen() → (ek, dk)
    Probabilistisch algoritme (gebruikt interne willekeur). Geen invoer.
    • ek: encapsulation key (publieke sleutel)
    • dk: decapsulation key (private sleutel)
  • Encaps(ek) → (K, c)
    Gegeven ek, produceert:
    • \(K \in \{0,1\}^\ell\): geheime symmetrische sleutel (doorgaans 256 bits)
    • c: versleutelde tekst (de "capsule")
  • Decaps(dk, c) → K
    Gegeven dk en c, herstelt \(K\).

Terminologische opmerking FIPS 203: de standaard gebruikt ek voor encapsulation key (niet pk) en dk voor decapsulation key (niet sk). Het onderscheid is intentioneel: het benadrukt dat de publieke sleutel dient om te encapsuleren, niet om willekeurige berichten te versleutelen.

Correctheid

Een KEM is correct als voor elk geldig sleutelpaar:

\[ \Pr\bigl[\text{Decaps}(dk,\, c) = K \mid (K, c) \leftarrow \text{Encaps}(ek)\bigr] \geq 1 - \delta \]

waarbij \(\delta\) een verwaarloosbare foutkans is (doorgaans \(< 2^{-128}\)).
Voor ML-KEM-768: \(\delta < 2^{-142}\).

6.2 Veiligheidseigenschappen

IND-CPA (Indistinguishability under Chosen Plaintext Attack)

Veiligheidsspel IND-CPA

Uitdager Aanvaller \(\mathcal{A}\)
\((ek, dk) \leftarrow \text{KeyGen}()\)
\(ek \longrightarrow\)
Kiest de uitdaging (impliciet in de KEM)
\((K_0, c) \leftarrow \text{Encaps}(ek)\)
\(K_1 \leftarrow \text{Random}\)
\(b \leftarrow \{0, 1\}\)
\((c, K_b) \longrightarrow\)
Geeft \(b'\) terug

Voordeel: \(\text{Adv}^{\text{IND-CPA}}_{\text{KEM}}(\mathcal{A}) = \left| \Pr[b' = b] - \frac{1}{2} \right|\)

De KEM is IND-CPA als het voordeel verwaarloosbaar is voor elke polynomiale aanvaller. Intuïtief: de aanvaller kan de echte sleutel \(K\) niet onderscheiden van een willekeurige, zelfs niet met de versleutelde tekst c.

IND-CCA2 (Indistinguishability under Adaptive Chosen Ciphertext Attack)

Zoals CPA, maar de aanvaller heeft ook toegang tot een decapsulatie-orakel:

Fase Actie
Initialisatie \((ek, dk) \leftarrow \text{KeyGen}()\), stuurt \(ek\)
Fase 1 (Query) \(c_i \to K_i = \text{Decaps}(dk, c_i)\)
Uitdaging \((K_0, c^*) \leftarrow \text{Encaps}(ek)\), \(K_1 \leftarrow \text{Random}\), \(b \leftarrow \{0,1\}\). Stuurt \((c^*, K_b)\).
Fase 2 (Query) \(c_j \to K_j = \text{Decaps}(dk, c_j)\) met \(c_j \neq c^*\)
Gissing Geeft \(b'\) terug

IND-CCA2 is de veiligheidsstandaard die vereist is voor KEM's in reëel gebruik.

Waarom is CCA2 nodig? In een echt protocol (TLS, SSH) kan een actieve aanvaller gemanipuleerde versleutelde teksten sturen en de reacties van de server observeren. Zelfs in MLWE zou een aanvaller die de decapsulatie van nabijgelegen versleutelde teksten kent, informatie over het geheim kunnen extraheren. ML-KEM is IND-CCA2.

Extra wenselijke eigenschappen

  • Robuustheid (Robustness): moeilijk om versleutelde teksten te construeren die met twee verschillende private sleutels naar dezelfde sleutel decapsuleren.
  • Forward secrecy: als de private sleutel dk in de toekomst wordt gecompromitteerd, blijven eerdere sessies veilig (vereist efemere sleutels).

6.3 KEM vs PKE: waarom KEM's

PKE (Public Key Encryption)

Een PKE versleutelt willekeurige berichten: \(\text{Enc}(ek, m) \to c\). Het probleem is dat als het bericht \(m\) een voorspelbare structuur heeft (kort wachtwoord, creditcardnummer), een aanvaller aanvallen met lage entropie of padding-orakel (Bleichenbacher) kan misbruiken.

KEM: scheiding van rollen

De KEM versleutelt geen gebruikersberichten. Het genereert een symmetrische sleutel met hoge entropie en encapsuleert deze:

\[ \text{Systeem} = \underbrace{\text{KEM}}_{\text{wisselt } K \text{ uit}} + \underbrace{\text{AES-GCM}}_{\text{versleutelt gegevens met } K} \]

Voordelen:

  • De sleutel \(K\) is altijd pseudo-willekeurig → geen aanvallen met lage entropie.
  • Er is geen complexe padding nodig voor gebruikersberichten.
  • \(K\) wordt gebruikt met een symmetrische versleuteling (DEM) om de werkelijke gegevens te versleutelen.

6.4 Intuïtief voorbeeld: KEM van Diffie-Hellman

Voordat ML-KEM bestond, werd de meest gebruikte KEM gebouwd op Diffie-Hellman. Dit voorbeeld helpt de structuur te begrijpen.

Publieke parameters: priemgetal \(p\), generator \(g\) van \(\mathbb{Z}_p^*\).

Alice
  1. Kiest geheime \(a\)
  2. Berekent \(A = g^a \bmod p\)
A → ← B
Bob
  1. Kiest geheime \(b\)
  2. Berekent \(B = g^b \bmod p\)
\[ \begin{aligned} \text{Alice berekent: } & K = B^a \bmod p = g^{ab} \bmod p \\ \text{Bob berekent: } & K = A^b \bmod p = g^{ab} \bmod p \end{aligned} \]

Numeriek voorbeeld: \(p = 17\), \(g = 3\), \(a = 5\).

  • \(ek = 3^5 \bmod 17 = 5\)
  • Bob kiest \(b = 7\): \(c = 3^7 \bmod 17 = 11\), \(K = H(5^7 \bmod 17) = H(10)\)
  • Alice decapsuleert: \(K = H(11^5 \bmod 17) = H(10)\) ✓

6.5 De Fujisaki-Okamoto (FO) transformatie

Het probleem: van CPA naar CCA2

Uitgaande van een PKE die alleen CPA-veilig is, hoe bouw je een IND-CCA2 KEM? Het antwoord is de FO-transformatie.

Centraal idee

  • Deterministische versleuteling: de willekeur die bij de versleuteling wordt gebruikt, wordt deterministisch afgeleid uit het bericht via een hash. Als de versleutelde tekst wordt gewijzigd, produceert de herversleuteling iets anders.
  • Verificatie bij ontsleuteling: in plaats van direct te ontsleutelen, wordt het ontsleutelde bericht opnieuw versleuteld en vergeleken met de ontvangen versleutelde tekst. Als ze niet overeenkomen → impliciete afwijzing.

Vereenvoudigd FO-schema

\[ \begin{aligned} \text{Encaps}(ek): & \quad m \leftarrow \{0,1\}^\ell, \ (K, r) = G(m), \ c = \text{Enc}(ek, m; r) \\ \text{Decaps}(dk, c): & \quad m' = \text{Dec}(dk, c), \ (K', r') = G(m'), \ c' = \text{Enc}(ek, m'; r') \\ & \quad \text{return } \begin{cases} K' & \text{als } c' = c \\ K_{\text{reject}} & \text{anders} \end{cases} \end{aligned} \]

Waarbij \(K_{\text{reject}} = H(z \| c)\) met \(z\) een vast geheim. Deze "impliciete afwijzing" voorkomt dat de aanvaller de fouten als orakel kan gebruiken.

6.6 Van K-PKE (CPA) naar ML-KEM (CCA2)

In ML-KEM is de tweeledige structuur:

ML-KEM (IND-CCA2)
└── K-PKE (IND-CPA) + FO-transformatie
    └── MLWE-probleem

ML-KEM.Encaps(ek)

m ← Random(32)                  // willekeurig bericht van 256 bits
(K̄, r) = G(m ‖ H(ek))          // SHA3-512: K̄ = eerste 32 bytes, r = laatste 32 bytes
c = K-PKE.Encrypt(ek, m, r)     // deterministische versleuteling met willekeur r
K = KDF(K̄ ‖ H(c))              // definitieve sleutel
return (K, c)

ML-KEM.Decaps(dk, c)

(dk_PKE, ek, h, z) = dk         // h = H(ek), z = back-up geheim
m' = K-PKE.Decrypt(dk_PKE, c)   // ontsleutelingspoging
(K̄', r') = G(m' ‖ h)           // herberekenen
c' = K-PKE.Encrypt(ek, m', r')  // herversleuteling ter verificatie
als c' == c:
    K = KDF(K̄' ‖ H(c))         // succesvolle ontsleuteling
anders:
    K = KDF(z ‖ H(c))           // back-up: pseudo-willekeurige sleutel
return K

Belangrijke details: De private sleutel dk bevat ook ek om de herversleuteling mogelijk te maken. De vergelijking c' == c moet tijdconstant worden uitgevoerd.

6.7 KEM in een echt protocol: TLS 1.3

Client (Bob)
Server (Alice)
ClientHello (ondersteunt ML-KEM-768)
ServerHello + Certificaat + KeyShare (ek)
KeyShare (c) + Finished (MAC met K)
Finished (MAC met K)

Hybride X25519 + ML-KEM

In de praktijk gebruikt TLS 1.3 een hybride benadering:

\[ K_{\text{TLS}} = \text{HKDF}(K_{\text{X25519}} \,\|\, K_{\text{ML-KEM}}) \]

Dit garandeert veiligheid als ten minste één van de twee schema's standhoudt. De groep X25519MLKEM768 is al uitgerold in Chrome 131+.

6.8 Generieke structuur van de KEM-stroom

Volledige stroom Alice (Ontvanger) / Bob (Verzender)

  1. Alice: KeyGen() genereert \((ek, dk)\). Publiceert \(ek\).
  2. Bob: Ontvangt \(ek\). Voert Encaps(ek) uit:
    • Genereert \(m\) willekeurig
    • \((\bar{K}, r) = G(m \| H(ek))\)
    • \(c = \text{K-PKE.Encrypt}(ek, m, r)\)
    • \(K = \text{KDF}(\bar{K} \| H(c))\)
  3. Bob: Versleutelt de gegevens met AES-256-GCM met \(K\) en een willekeurige nonce.
  4. Bob: Stuurt \((c, \text{nonce}, \text{versleutelde tekst}, \text{tag})\) naar Alice.
  5. Alice: Voert Decaps(dk, c) uit om \(K\) te herstellen.
  6. Alice: Ontsleutelt de gegevens met AES-256-GCM. Als de tag faalt, verwerpt ze het bericht.

Dubbele bescherming: Als c wordt gemanipuleerd, geeft Decaps een pseudo-willekeurige sleutel terug (\(K_{\text{reject}}\)). Zelfs als de aanvaller deze sleutel zou raden, zou de AEAD-tag van AES-GCM falen, wat de integriteit garandeert.

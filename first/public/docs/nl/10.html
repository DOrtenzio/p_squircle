10.1 liboqs: de C-referentiebibliotheek

liboqs is de C-referentiebibliotheek voor post-kwantumcryptografie, ontwikkeld door het Open Quantum Safe (OQS)-project. Het biedt geoptimaliseerde en tijdconstante implementaties van ML-KEM en andere door NIST gestandaardiseerde PQC-algoritmen.

Installatie vanuit bron

# Afhankelijkheden (Ubuntu/Debian)
sudo apt-get install cmake gcc libssl-dev

# Klonen en compileren
git clone https://github.com/open-quantum-safe/liboqs.git
cd liboqs
mkdir build && cd build
cmake -DCMAKE_INSTALL_PREFIX=/usr/local ..
make -j$(nproc)
sudo make install

10.2 Volledig voorbeeld: KEM met ML-KEM-768 in C

#include <stdio.h>
#include <string.h>
#include <oqs/oqs.h>

int main() {
    OQS_STATUS rc;
    const char *kem_alg = OQS_KEM_alg_ml_kem_768;

    // Initialiseer het algoritme
    OQS_KEM *kem = OQS_KEM_new(kem_alg);
    if (kem == NULL) {
        fprintf(stderr, "KEM niet ondersteund\n");
        return 1;
    }

    printf("Algoritme: %s\n", kem->method_name);
    printf("Publieke sleutel: %zu bytes\n", kem->length_public_key);
    printf("Private sleutel: %zu bytes\n", kem->length_secret_key);
    printf("Versleutelde tekst: %zu bytes\n", kem->length_ciphertext);
    printf("Gedeeld geheim: %zu bytes\n\n", kem->length_shared_secret);

    // Geheugentoewijzing
    uint8_t *pk = malloc(kem->length_public_key);
    uint8_t *sk = malloc(kem->length_secret_key);
    uint8_t *ct = malloc(kem->length_ciphertext);
    uint8_t *ss_enc = malloc(kem->length_shared_secret);
    uint8_t *ss_dec = malloc(kem->length_shared_secret);

    // 1. KeyGen (Alice)
    rc = OQS_KEM_keypair(kem, pk, sk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "KeyGen mislukt\n"); return 1; }
    printf("✓ KeyGen voltooid\n");

    // 2. Encaps (Bob: kent alleen pk)
    rc = OQS_KEM_encaps(kem, ct, ss_enc, pk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "Encaps mislukt\n"); return 1; }
    printf("✓ Encaps voltooid\n");

    // 3. Decaps (Alice: gebruikt sk om ct te openen)
    rc = OQS_KEM_decaps(kem, ss_dec, ct, sk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "Decaps mislukt\n"); return 1; }
    printf("✓ Decaps voltooid\n\n");

    // 4. Verificatie
    if (memcmp(ss_enc, ss_dec, kem->length_shared_secret) == 0) {
        printf("✅ De gedeelde geheimen komen overeen!\n");
        printf("   Eerste bytes: ");
        for (int i = 0; i < 8; i++) printf("%02x", ss_enc[i]);
        printf("...\n");
    } else {
        printf("❌ FOUT: de gedeelde geheimen zijn verschillend!\n");
    }

    // Veilige geheugenopschoning
    OQS_MEM_cleanse(sk, kem->length_secret_key);
    OQS_MEM_cleanse(ss_enc, kem->length_shared_secret);
    OQS_MEM_cleanse(ss_dec, kem->length_shared_secret);
    free(pk); free(ct);
    OQS_KEM_free(kem);

    return 0;
}

Compileren:

gcc -o kem_example kem_example.c -loqs -lcrypto
./kem_example

10.3 De afgeleide sleutel gebruiken met AES-256-GCM

Na het verkrijgen van het gedeelde geheim van ML-KEM kan dit worden gebruikt als sleutel voor een symmetrische versleuteling. In productie wordt aanbevolen om HKDF te gebruiken om afzonderlijke sleutels af te leiden.

#include <openssl/evp.h>
#include <oqs/oqs.h>

// Na het verkrijgen van ss (32 bytes) van ML-KEM:
void encrypt_with_kem_key(const uint8_t *ss, const uint8_t *plaintext,
                           size_t pt_len, uint8_t *ciphertext, uint8_t *tag,
                           const uint8_t *nonce) {
    EVP_CIPHER_CTX *ctx = EVP_CIPHER_CTX_new();
    int len;

    // Initialiseer AES-256-GCM
    EVP_EncryptInit_ex(ctx, EVP_aes_256_gcm(), NULL, NULL, NULL);
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_IVLEN, 12, NULL);

    // Gebruik het gedeelde geheim als sleutel
    EVP_EncryptInit_ex(ctx, NULL, NULL, ss, nonce);

    // Versleuteling
    EVP_EncryptUpdate(ctx, ciphertext, &len, plaintext, pt_len);
    EVP_EncryptFinal_ex(ctx, ciphertext + len, &len);

    // Haal de authenticatietag op
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_GET_TAG, 16, tag);

    EVP_CIPHER_CTX_free(ctx);
}

10.4 Python: liboqs-binding

Liboqs biedt officiële bindings voor Python voor snelle tests en prototyping.

pip install liboqs-python
import oqs

# Beschikbaar algoritme
kem = oqs.KeyEncapsulation("ML-KEM-768")

# KeyGen
public_key = kem.generate_keypair()

# Encaps (Bob's kant)
kem_bob = oqs.KeyEncapsulation("ML-KEM-768")
ciphertext, shared_secret_enc = kem_bob.encap_secret(public_key)

# Decaps (Alice's kant)
shared_secret_dec = kem.decap_secret(ciphertext)

assert shared_secret_enc == shared_secret_dec
print(f"✓ Gedeeld geheim: {shared_secret_enc.hex()[:16]}...")

kem.free()
kem_bob.free()

10.5 Python: kyber-py (alleen educatief)

Voor puur educatieve doeleinden bestaat er een implementatie in pure Python die geen externe C-bibliotheken vereist.

Let op: kyber-py is niet tijdconstant en mag niet in productie worden gebruikt.

                    
                        from kyber import Kyber768
                        kem = Kyber768()
                        pk, sk = kem.keygen()
                        key, ciphertext = kem.enc(pk)
                        _key = kem.dec(sk, ciphertext)
                        assert key == _key

10.6 Prestatiebenchmarks

Benchmarks op Intel Core i7-12700K (één kern, zonder SIMD-instructies):

Bewerking ML-KEM-512 ML-KEM-768 ML-KEM-1024
KeyGen 24 µs 37 µs 54 µs
Encaps 28 µs 43 µs 62 µs
Decaps 32 µs 48 µs 70 µs

Met AVX2-optimalisaties

Bewerking ML-KEM-768 (zonder SIMD) ML-KEM-768 (AVX2) Versnelling
KeyGen 37 µs ~10 µs ~3,7×
Encaps 43 µs ~12 µs ~3,6×
Decaps 48 µs ~13 µs ~3,7×

Vergelijking met ECDH X25519

X25519 ML-KEM-768
KeyGen ~14 µs ~37 µs
Uitwisseling ~30 µs ~48 µs
Publieke sleutel 32 B 1184 B

ML-KEM is ongeveer 2 keer langzamer dan X25519, maar de overhead in de TLS-handshake-latentie is in de meeste echte verbindingen verwaarloosbaar (< 1 ms).

10.7 OpenSSL: installatie van de OQS-provider

OpenSSL 3.x ondersteunt ML-KEM via de provider oqsprovider. Vanaf versie 3.4 is de ondersteuning native of eenvoudig integreerbaar.

# oqs-provider compileren
git clone https://github.com/open-quantum-safe/oqs-provider.git
cd oqs-provider
cmake -DOPENSSL_ROOT_DIR=/usr/local/ssl .
make
sudo make install

# Verifiëren
openssl list -providers
# zou moeten tonen: oqsprovider

10.8 ML-KEM-sleutels genereren met OpenSSL CLI

# ML-KEM-768 sleutelpaar genereren
openssl genpkey -algorithm mlkem768 -out private.pem
openssl pkey -in private.pem -pubout -out public.pem

# Sleuteldetails bekijken
openssl pkey -in private.pem -text -noout

10.9 TLS 1.3 met ML-KEM-768

Lokale test (server + client)

# Server
openssl s_server -accept 4433 -cert server.crt -key server.key \
    -groups mlkem768

# Client (in een andere terminal)
openssl s_client -connect localhost:4433 -groups mlkem768

Ondersteunde groepen controleren

openssl list -key-exchange-algorithms | grep -i kem

10.10 Hybride strategie: X25519 + ML-KEM-768

De aanbevolen aanpak voor migratie is hybridisatie: combineer ECDH (X25519) met ML-KEM-768. De uiteindelijke sleutel wordt van beide afgeleid:

\[ K = \text{HKDF}(K_{\text{X25519}} \| K_{\text{ML-KEM}}) \]

Voordeel: veilig als ten minste één van de twee schema's standhoudt. Als een kwantumcomputer X25519 breekt, beschermt ML-KEM. Als ML-KEM een onbekend defect heeft, beschermt X25519.

10.11 Hybride cipher suites in TLS 1.3

Groepsnaam Samenstelling
X25519MLKEM768 X25519 + ML-KEM-768
SecP256r1MLKEM768 P-256 + ML-KEM-768

Vanaf Chrome 131 (eind 2024) is X25519MLKEM768 de standaardgroep. Firefox 128+ ondersteunt dezelfde groep.

OpenSSL-configuratie

# Server die zowel klassieke X25519 als de hybride groep accepteert
openssl s_server -accept 4433 -cert server.crt -key server.key \
    -groups X25519MLKEM768:x25519:P-256

# Client die de hybride groep prefereert
openssl s_client -connect localhost:4433 \
    -groups X25519MLKEM768:x25519

10.12 Integratie in C-applicaties met OpenSSL

#include <openssl/ssl.h>
#include <openssl/err.h>

SSL_CTX *create_pqc_context(void) {
    SSL_CTX *ctx = SSL_CTX_new(TLS_server_method());
    if (!ctx) {
        ERR_print_errors_fp(stderr);
        return NULL;
    }

    // Stel de voorkeursgroepen in: hybride eerst, daarna klassiek als fallback
    if (SSL_CTX_set1_groups_list(ctx, "X25519MLKEM768:x25519:P-256") != 1) {
        fprintf(stderr, "Fout bij configuratie van groepen\n");
        SSL_CTX_free(ctx);
        return NULL;
    }

    return ctx;
}

10.13 Checklist voor migratie

Voor ontwikkelaars van applicaties

  • Inventariseer waar asymmetrische cryptografie wordt gebruikt (sleuteluitwisseling, handtekening, KEM).
  • Identificeer welke gegevens langer dan 5 jaar geheim moeten blijven.
  • Werk afhankelijkheden bij: OpenSSL ≥ 3.2, liboqs ≥ 0.10.
  • Adopteer de hybride aanpak: X25519 + ML-KEM-768 voor TLS.
  • Voor digitale handtekeningen: migreer naar ML-DSA (FIPS 204) of SLH-DSA (FIPS 205).
  • Test de toename van sleutel- en ciphertextgrootte in protocollen.
  • Controleer of time-outs en buffergroottes geen kleine sleutels aannemen.

Voor infrastructuurbeheerders

  • Werk de TLS-stack bij naar versies met ML-KEM-ondersteuning.
  • Schakel X25519MLKEM768 in op TLS-servers.
  • Monitor de compatibiliteit van clients (Chrome 131+, Firefox 128+ ondersteunen hybride PQC).
  • Plan rotatie van sleutels op lange termijn.

Referentiestandaarden

Standaard Inhoud
FIPS 203 ML-KEM (Key Encapsulation)
FIPS 204 ML-DSA (digitale handtekening op basis van roosters)
FIPS 205 SLH-DSA (handtekening op basis van hash, conservatief)

10.14 Scenario: migratie van een REST-API

Huidige situatie (pre-migratie)

Client → TLS 1.3 met X25519 → API-server

Fase 1: hybride (vandaag, aanbevolen)

Client → TLS 1.3 met X25519MLKEM768 → API-server

# nginx-configuratie
ssl_ecdh_curve X25519MLKEM768:x25519:P-256;

# Apache-configuratie
SSLOpenSSLConfCmd Curves X25519MLKEM768:x25519:P-256;

Fase 2: puur post-kwantum (toekomst)

Client → TLS 1.3 met ML-KEM-768 + ML-DSA → API-server

Te implementeren wanneer de meeste clients ML-KEM native ondersteunen en servers certificaten met ML-DSA voor handtekeningen gebruiken.

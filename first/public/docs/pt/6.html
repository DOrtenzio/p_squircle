6.1 Definição formal de KEM

Tripla de algoritmos

Um Mecanismo de Encapçamento de Chave (KEM) é uma tripla de algoritmos probabilísticos polinomiais:

\[ \text{KEM} = (\text{KeyGen},\ \text{Encaps},\ \text{Decaps}) \]
  • KeyGen() → (ek, dk)
    Algoritmo probabilístico (usa aleatoriedade interna). Não recebe entrada.
    • ek: chave de encapçamento (chave pública)
    • dk: chave de desencapçamento (chave privada)
  • Encaps(ek) → (K, c)
    Dado ek, produz:
    • \(K \in \{0,1\}^\ell\): chave simétrica secreta (tipicamente 256 bits)
    • c: texto cifrado (a "cápsula")
  • Decaps(dk, c) → K
    Dado dk e c, recupera \(K\).

Nota terminológica FIPS 203: o padrão usa ek para chave de encapçamento (não pk) e dk para chave de desencapçamento (não sk). A distinção é intencional: sublinha que a chave pública serve para encapçular, não para cifrar mensagens arbitrárias.

Correção

Um KEM é correto se para cada par de chaves válido:

\[ \Pr\bigl[\text{Decaps}(dk,\, c) = K \mid (K, c) \leftarrow \text{Encaps}(ek)\bigr] \geq 1 - \delta \]

onde \(\delta\) é uma probabilidade de erro negligenciável (tipicamente \(< 2^{-128}\)).
Para ML-KEM-768: \(\delta < 2^{-142}\).

6.2 Propriedades de segurança

IND-CPA (Indistinguibilidade sob Ataque de Texto Claro Escolhido)

Jogo de segurança IND-CPA

Desafiante Adversário \(\mathcal{A}\)
\((ek, dk) \leftarrow \text{KeyGen}()\)
\(ek \longrightarrow\)
Escolhe o desafio (implícito no KEM)
\((K_0, c) \leftarrow \text{Encaps}(ek)\)
\(K_1 \leftarrow \text{Random}\)
\(b \leftarrow \{0, 1\}\)
\((c, K_b) \longrightarrow\)
Devolve \(b'\)

Vantagem: \(\text{Adv}^{\text{IND-CPA}}_{\text{KEM}}(\mathcal{A}) = \left| \Pr[b' = b] - \frac{1}{2} \right|\)

O KEM é IND-CPA se a vantagem for negligenciável para todo adversário polinomial. Intuitivamente: o adversário não consegue distinguir a chave \(K\) real de uma aleatória, mesmo vendo o texto cifrado c.

IND-CCA2 (Indistinguibilidade sob Ataque Adaptativo de Texto Cifrado Escolhido)

Como CPA, mas o adversário também tem acesso a um oráculo de desencapçamento:

Fase Ação
Inicialização \((ek, dk) \leftarrow \text{KeyGen}()\), envia \(ek\)
Fase 1 (Consultas) \(c_i \to K_i = \text{Decaps}(dk, c_i)\)
Desafio \((K_0, c^*) \leftarrow \text{Encaps}(ek)\), \(K_1 \leftarrow \text{Random}\), \(b \leftarrow \{0,1\}\). Envia \((c^*, K_b)\).
Fase 2 (Consultas) \(c_j \to K_j = \text{Decaps}(dk, c_j)\) com \(c_j \neq c^*\)
Palpite Devolve \(b'\)

IND-CCA2 é o padrão de segurança exigido para KEM em uso real.

Por que o CCA2 é necessário? Num protocolo real (TLS, SSH), um adversário ativo pode enviar textos cifrados manipulados e observar as respostas do servidor. Mesmo em MLWE, um adversário que conhece o desencapçamento de textos cifrados próximos do texto cifrado desafio pode extrair informações sobre o segredo. ML-KEM é IND-CCA2.

Propriedades adicionais desejáveis

  • Robustez (Robustness): difícil construir um texto cifrado que desencapçule para a mesma chave com duas chaves privadas diferentes.
  • Segurança futura (Forward secrecy): se a chave privada dk for comprometida no futuro, as sessões passadas permanecem seguras (requer chaves efémeras).

6.3 KEM vs PKE: por que os KEM

PKE (Cifra de Chave Pública)

Um PKE cifra mensagens arbitrárias: \(\text{Enc}(ek, m) \to c\). O problema é que se a mensagem \(m\) tiver estrutura previsível (palavra-passe curta, número de cartão), um adversário pode explorar ataques de baixa entropia ou de oráculo de preenchimento (Bleichenbacher).

KEM: separação de papéis

O KEM não cifra mensagens de utilizador. Gera uma chave simétrica de alta entropia e encapçula-a:

\[ \text{Sistema} = \underbrace{\text{KEM}}_{\text{troca } K} + \underbrace{\text{AES-GCM}}_{\text{cifra dados com } K} \]

Vantagens:

  • A chave \(K\) é sempre pseudoaleatória → nenhum ataque de baixa entropia.
  • Não é necessário preenchimento complexo para mensagens de utilizador.
  • \(K\) é usada com uma cifra simétrica (DEM) para cifrar os dados reais.

6.4 Exemplo intuitivo: KEM a partir de Diffie-Hellman

Antes do ML-KEM, o KEM mais usado era construído sobre Diffie-Hellman. Este exemplo ajuda a compreender a estrutura.

Parâmetros públicos: primo \(p\), gerador \(g\) de \(\mathbb{Z}_p^*\).

Alice
  1. Escolhe \(a\) secreto
  2. Calcula \(A = g^a \bmod p\)
A → ← B
Bob
  1. Escolhe \(b\) secreto
  2. Calcula \(B = g^b \bmod p\)
\[ \begin{aligned} \text{Alice calcula: } & K = B^a \bmod p = g^{ab} \bmod p \\ \text{Bob calcula: } & K = A^b \bmod p = g^{ab} \bmod p \end{aligned} \]

Exemplo numérico: \(p = 17\), \(g = 3\), \(a = 5\).

  • \(ek = 3^5 \bmod 17 = 5\)
  • Bob escolhe \(b = 7\): \(c = 3^7 \bmod 17 = 11\), \(K = H(5^7 \bmod 17) = H(10)\)
  • Alice desencapçula: \(K = H(11^5 \bmod 17) = H(10)\) ✓

6.5 A transformação Fujisaki-Okamoto (FO)

O problema: de CPA para CCA2

A partir de um PKE apenas CPA-seguro, como construir um KEM IND-CCA2? A resposta é a transformação FO.

Ideia central

  • Cifra determinística: a aleatoriedade usada na cifra é derivada deterministicamente da mensagem via hash. Se o texto cifrado for modificado, a recifra produz algo diferente.
  • Verificação na decifra: em vez de decifrar diretamente, recifra-se a mensagem decifrada e compara-se com o texto cifrado recebido. Se não corresponderem → rejeição implícita.

Esquema FO simplificado

\[ \begin{aligned} \text{Encaps}(ek): & \quad m \leftarrow \{0,1\}^\ell, \ (K, r) = G(m), \ c = \text{Enc}(ek, m; r) \\ \text{Decaps}(dk, c): & \quad m' = \text{Dec}(dk, c), \ (K', r') = G(m'), \ c' = \text{Enc}(ek, m'; r') \\ & \quad \text{return } \begin{cases} K' & \text{se } c' = c \\ K_{\text{reject}} & \text{caso contrário} \end{cases} \end{aligned} \]

Onde \(K_{\text{reject}} = H(z \| c)\) com \(z\) secreto fixo. Esta "rejeição implícita" impede o adversário de usar os erros como oráculo.

6.6 De K-PKE (CPA) a ML-KEM (CCA2)

Em ML-KEM, a estrutura de dois níveis é:

ML-KEM (IND-CCA2)
└── K-PKE (IND-CPA) + transformação FO
    └── problema MLWE

ML-KEM.Encaps(ek)

m ← Random(32)                  // mensagem aleatória de 256 bits
(K̄, r) = G(m ‖ H(ek))          // SHA3-512: K̄ = primeiros 32 bytes, r = últimos 32 bytes
c = K-PKE.Encrypt(ek, m, r)     // cifra determinística com aleatoriedade r
K = KDF(K̄ ‖ H(c))              // chave final
return (K, c)

ML-KEM.Decaps(dk, c)

(dk_PKE, ek, h, z) = dk         // h = H(ek), z = segredo de fallback
m' = K-PKE.Decrypt(dk_PKE, c)   // tentativa de decifra
(K̄', r') = G(m' ‖ h)           // recalcula
c' = K-PKE.Encrypt(ek, m', r')  // recifra de verificação
se c' == c:
    K = KDF(K̄' ‖ H(c))         // decifra bem-sucedida
caso contrário:
    K = KDF(z ‖ H(c))           // fallback: chave pseudoaleatória
return K

Detalhes importantes: A chave privada dk também contém ek para poder fazer a recifra. A comparação c' == c deve ser de tempo constante.

6.7 KEM num protocolo real: TLS 1.3

Cliente (Bob)
Servidor (Alice)
ClientHello (suporta ML-KEM-768)
ServerHello + Certificado + KeyShare (ek)
KeyShare (c) + Finished (MAC com K)
Finished (MAC com K)

Híbrido X25519 + ML-KEM

Na prática, o TLS 1.3 usa uma abordagem híbrida:

\[ K_{\text{TLS}} = \text{HKDF}(K_{\text{X25519}} \,\|\, K_{\text{ML-KEM}}) \]

Isto garante segurança se pelo menos um dos dois esquemas se mantiver. O grupo X25519MLKEM768 já está implementado no Chrome 131+.

6.8 Estrutura genérica do fluxo KEM

Fluxo completo Alice (Destinatário) / Bob (Remetente)

  1. Alice: KeyGen() gera \((ek, dk)\). Publica \(ek\).
  2. Bob: Recebe \(ek\). Executa Encaps(ek):
    • Gera \(m\) aleatório
    • \((\bar{K}, r) = G(m \| H(ek))\)
    • \(c = \text{K-PKE.Encrypt}(ek, m, r)\)
    • \(K = \text{KDF}(\bar{K} \| H(c))\)
  3. Bob: Cifra os dados com AES-256-GCM usando \(K\) e um nonce aleatório.
  4. Bob: Envia \((c, \text{nonce}, \text{ciphertext}, \text{tag})\) para Alice.
  5. Alice: Executa Decaps(dk, c) para recuperar \(K\).
  6. Alice: Decifra os dados com AES-256-GCM. Se a tag falhar, descarta a mensagem.

Dupla proteção: Se c for adulterado, Decaps devolve uma chave pseudoaleatória (\(K_{\text{reject}}\)). Mesmo que o adversário adivinhe esta chave, a tag AEAD do AES-GCM falharia, garantindo a integridade.

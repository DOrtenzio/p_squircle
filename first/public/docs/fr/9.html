09 – Sécurité et Paramètres

Pourquoi ML-KEM est sécurisé et comment les nombres ont été choisis

9.1 Modèles de sécurité

IND-CPA (Indistinguishability under Chosen Plaintext Attack)

Dans ce modèle, un adversaire:

  1. Reçoit la clé publique \(ek\)
  2. Choisit deux messages \(m_0, m_1\)
  3. Reçoit le chiffré de l'un des deux (choisi aléatoirement)
  4. Doit deviner quel message a été chiffré

Le schéma est sécurisé si: \(\Pr[\text{devine}] \leq 1/2 + \text{negl}(\lambda)\).

K-PKE (la composante de chiffrement de base) est IND-CPA sous l'hypothèse MLWE.

IND-CCA2 (Indistinguishability under Adaptive Chosen Ciphertext Attack)

Comme CPA, mais l'adversaire peut aussi interroger un oracle de déchiffrement sur n'importe quel chiffré (sauf celui du défi). Ce modèle capture les attaques réelles (comme Bleichenbacher), où un adversaire actif envoie des messages construits ad hoc et observe les réponses.

ML-KEM est IND-CCA2. C'est le niveau requis pour un KEM sécurisé dans des protocoles réels comme TLS ou SSH.

ROM vs. QROM

Les preuves de sécurité utilisent des modèles idéalisés pour les fonctions de hachage:

  • ROM (Random Oracle Model): les hachages sont des oracles aléatoires parfaits.
  • QROM (Quantum Random Oracle Model): l'adversaire quantique peut interroger l'oracle en superposition.

Les preuves modernes pour la transformation FO (Fujisaki-Okamoto) utilisée dans ML-KEM garantissent la sécurité dans le QROM, essentiel contre les adversaires quantiques.

9.2 Comment mesure-t-on la difficulté de MLWE

Sécurité comme coût de l'attaque

Il n'existe pas de preuve absolue que MLWE soit difficile. La sécurité est estimée en calculant le coût du meilleur algorithme d'attaque connu. Une sécurité de \(\lambda\) bits signifie que l'attaque nécessite environ \(2^\lambda\) opérations.

Les paramètres

La difficulté dépend de:

  • \(n = 256\) (dimension du polynôme, fixe)
  • \(k \in \{2, 3, 4\}\) (dimension du module)
  • \(q = 3329\) (module premier)
  • \(\eta \in \{2, 3\}\) (largeur du bruit)

Lattice Estimator

L'outil standard est le Lattice Estimator d'Albrecht et al. Pour ML-KEM-768:

Attaque Coût estimé (bits)
Primal attack (BKZ) ~178 bits
Dual attack ~175 bits
Combinatoire > 200 bits

La marge de sécurité est large par rapport à la cible de 128 bits classique/quantique.

9.3 Attaques principales sur les treillis

BKZ (Block Korkine-Zolotarev)

C'est le meilleur algorithme général pour trouver des vecteurs courts. Il divise le treillis en blocs de taille \(\beta\) et résout SVP localement. Complexité: \(2^{O(\beta \log \beta)}\). Pour ML-KEM-768, \(\beta \approx 430\).

Attaque primale (uSVP)

Réduit MLWE à un problème de vecteur court dans un treillis augmenté contenant la clé publique et le chiffré. Le vecteur secret \((\mathbf{s}, \mathbf{e}, -1)\) devient un vecteur court que BKZ tente de trouver.

Attaque duale

Exploite le treillis dual pour distinguer les échantillons MLWE des échantillons uniformes via des statistiques. Construit de nombreux vecteurs courts dans le dual pour effectuer le distinguer.

Choix de q = 3329

Étant premier et dépourvu de structure algébrique spéciale, il prévient les attaques algébriques spécifiques. Il n'existe pas de petits facteurs ou de relations simples qui pourraient être exploités.

9.4 Niveaux de sécurité NIST

Le NIST a défini 5 niveaux. ML-KEM couvre les niveaux 1, 3 et 5:

Schéma Niveau NIST Sécurité Classique Sécurité Quantique
ML-KEM-512 1 (AES-128) ~118 bits ~100 bits
ML-KEM-768 3 (AES-192) ~178 bits ~164 bits
ML-KEM-1024 5 (AES-256) ~230 bits ~218 bits

Recommandation: ML-KEM-768 offre l'équilibre optimal sécurité/performance pour la plupart des usages. ML-KEM-1024 est réservé aux systèmes à très haute criticité.

Comparaison avec la Cryptographie Classique

Schéma Clé Publique Sécurité Quantique
RSA-3072 384 B ❌ Vulnérable

ML-KEM-768 1184 B ✅ 164+ bits

Le coût principal est la taille plus grande (~37× par rapport à ECDH), mais elle reste acceptable pour les handshakes TLS modernes.

9.6 Canaux auxiliaires et implémentations sécurisées

Une implémentation correcte peut être vulnérable si elle fuit des informations via le temps d'exécution (attaques temporelles) ou la consommation d'énergie.

Constant-Time (CT)

Toutes les opérations doivent avoir un temps constant indépendamment des données secrètes. Exemple critique dans Decaps:

// NON sécurisé (timing variable):
if (memcmp(c, c_prime, len) == 0) { 
    K = K_good; 
} else { 
    K = K_reject; 
}

// Sécurisé (constant-time):
uint8_t mask = ct_memcmp(c, c_prime, len); // 0xFF si égal, 0x00 si différent
K = ct_select(mask, K_good, K_reject);     // sélection CT sans branchement

Zones critiques pour CT dans ML-KEM

  • Échantillonnage \(B_\eta\): additions de bits sans branchement conditionnel.
  • NTT: les opérations butterfly doivent toujours être exécutées, même si le résultat ne change pas.
  • Vérification du chiffré: utilisation de ct_memcmp.

Implémentations de référence

  • pqclean: implémentations portables CT.
  • liboqs: optimisations AVX2 avec propriétés CT vérifiées.

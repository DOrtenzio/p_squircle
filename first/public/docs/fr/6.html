6.1 Définition formelle de KEM

Triplet d'algorithmes

Un Key Encapsulation Mechanism (KEM) est un triplet d'algorithmes probabilistes polynomiaux:

\[ \text{KEM} = (\text{KeyGen},\ \text{Encaps},\ \text{Decaps}) \]
  • KeyGen() → (ek, dk)
    Algorithme probabiliste (utilise de l'aléa interne). Ne prend pas d'entrée.
    • ek: encapsulation key (clé publique)
    • dk: decapsulation key (clé privée)
  • Encaps(ek) → (K, c)
    Étant donné ek, produit:
    • \(K \in \{0,1\}^\ell\): clé symétrique secrète (typiquement 256 bits)
    • c: chiffré (la "capsule")
  • Decaps(dk, c) → K
    Étant donné dk et c, récupère \(K\).

Note terminologique FIPS 203: la norme utilise ek pour encapsulation key (pas pk) et dk pour decapsulation key (pas sk). La distinction est intentionnelle: elle souligne que la clé publique sert à encapsuler, pas à chiffrer des messages arbitraires.

Correction

Un KEM est correct si pour chaque paire de clés valide:

\[ \Pr\bigl[\text{Decaps}(dk,\, c) = K \mid (K, c) \leftarrow \text{Encaps}(ek)\bigr] \geq 1 - \delta \]

où \(\delta\) est une probabilité d'erreur négligeable (typiquement \(< 2^{-128}\)).
Pour ML-KEM-768: \(\delta < 2^{-142}\).

6.2 Propriétés de sécurité

IND-CPA (Indistinguishability under Chosen Plaintext Attack)

Jeu de sécurité IND-CPA

Challenger Adversaire \(\mathcal{A}\)
\((ek, dk) \leftarrow \text{KeyGen}()\)
\(ek \longrightarrow\)
Choisit le défi (implicite dans le KEM)
\((K_0, c) \leftarrow \text{Encaps}(ek)\)
\(K_1 \leftarrow \text{Random}\)
\(b \leftarrow \{0, 1\}\)
\((c, K_b) \longrightarrow\)
Retourne \(b'\)

Avantage: \(\text{Adv}^{\text{IND-CPA}}_{\text{KEM}}(\mathcal{A}) = \left| \Pr[b' = b] - \frac{1}{2} \right|\)

Le KEM est IND-CPA si l'avantage est négligeable pour tout adversaire polynomial. Intuitivement: l'adversaire ne parvient pas à distinguer la clé \(K\) réelle d'une clé aléatoire, même en voyant le chiffré c.

IND-CCA2 (Indistinguishability under Adaptive Chosen Ciphertext Attack)

Comme CPA, mais l'adversaire a aussi accès à un oracle de décapsulation:

Phase Action
Initialisation \((ek, dk) \leftarrow \text{KeyGen}()\), envoie \(ek\)
Phase 1 (Requête) \(c_i \to K_i = \text{Decaps}(dk, c_i)\)
Défi \((K_0, c^*) \leftarrow \text{Encaps}(ek)\), \(K_1 \leftarrow \text{Random}\), \(b \leftarrow \{0,1\}\). Envoie \((c^*, K_b)\).
Phase 2 (Requête) \(c_j \to K_j = \text{Decaps}(dk, c_j)\) avec \(c_j \neq c^*\)
Devine Retourne \(b'\)

IND-CCA2 est le standard de sécurité requis pour les KEM en usage réel.

Pourquoi CCA2 est-il nécessaire? Dans un protocole réel (TLS, SSH), un adversaire actif peut envoyer des chiffrés manipulés et observer les réponses du serveur. Même dans MLWE, un adversaire qui connaît la décapsulation de chiffrés proches du chiffré défi pourrait extraire des informations sur le secret. ML-KEM est IND-CCA2.

Propriétés supplémentaires souhaitables

  • Robustesse: difficile de construire des chiffrés qui se décapsulent vers la même clé avec deux clés privées différentes.
  • Forward secrecy: si la clé privée dk est compromise dans le futur, les sessions passées restent sécurisées (nécessite des clés éphémères).

6.3 KEM vs PKE: pourquoi les KEM

PKE (Public Key Encryption)

Un PKE chiffre des messages arbitraires: \(\text{Enc}(ek, m) \to c\). Le problème est que si le message \(m\) a une structure prévisible (mot de passe court, numéro de carte), un adversaire peut exploiter des attaques à faible entropie ou des attaques par oracle de padding (Bleichenbacher).

KEM: séparation des rôles

Le KEM ne chiffre pas les messages utilisateur. Il génère une clé symétrique de haute entropie et l'encapsule:

\[ \text{Système} = \underbrace{\text{KEM}}_{\text{échange } K} + \underbrace{\text{AES-GCM}}_{\text{chiffre les données avec } K} \]

Avantages:

  • La clé \(K\) est toujours pseudo-aléatoire → pas d'attaque à faible entropie.
  • Pas besoin de padding complexe pour les messages utilisateur.
  • \(K\) est utilisée avec un chiffrement symétrique (DEM) pour chiffrer les données réelles.

6.4 Exemple intuitif: KEM à partir de Diffie-Hellman

Avant ML-KEM, le KEM le plus utilisé était construit sur Diffie-Hellman. Cet exemple aide à comprendre la structure.

Paramètres publics: premier \(p\), générateur \(g\) de \(\mathbb{Z}_p^*\).

Alice
  1. Choisit \(a\) secret
  2. Calcule \(A = g^a \bmod p\)
A → ← B
Bob
  1. Choisit \(b\) secret
  2. Calcule \(B = g^b \bmod p\)
\[ \begin{aligned} \text{Alice calcule: } & K = B^a \bmod p = g^{ab} \bmod p \\ \text{Bob calcule: } & K = A^b \bmod p = g^{ab} \bmod p \end{aligned} \]

Exemple numérique: \(p = 17\), \(g = 3\), \(a = 5\).

  • \(ek = 3^5 \bmod 17 = 5\)
  • Bob choisit \(b = 7\): \(c = 3^7 \bmod 17 = 11\), \(K = H(5^7 \bmod 17) = H(10)\)
  • Alice décapsule: \(K = H(11^5 \bmod 17) = H(10)\) ✓

6.5 La transformation Fujisaki-Okamoto (FO)

Le problème: de CPA à CCA2

À partir d'un PKE uniquement CPA-sécurisé, comment construire un KEM IND-CCA2? La réponse est la transformation FO.

Idée centrale

  • Chiffrement déterministe: l'aléa utilisé dans le chiffrement est dérivé de manière déterministe du message via un hachage. Si le chiffré est modifié, le rechiffrement produit quelque chose de différent.
  • Vérification lors du déchiffrement: au lieu de déchiffrer directement, on rechiffre le message déchiffré et on le compare avec le chiffré reçu. S'ils ne correspondent pas → rejet implicite.

Schéma FO simplifié

\[ \begin{aligned} \text{Encaps}(ek): & \quad m \leftarrow \{0,1\}^\ell, \ (K, r) = G(m), \ c = \text{Enc}(ek, m; r) \\ \text{Decaps}(dk, c): & \quad m' = \text{Dec}(dk, c), \ (K', r') = G(m'), \ c' = \text{Enc}(ek, m'; r') \\ & \quad \text{return } \begin{cases} K' & \text{si } c' = c \\ K_{\text{reject}} & \text{sinon} \end{cases} \end{aligned} \]

Où \(K_{\text{reject}} = H(z \| c)\) avec \(z\) secret fixe. Ce "rejet implicite" empêche l'adversaire d'utiliser les erreurs comme oracle.

6.6 De K-PKE (CPA) à ML-KEM (CCA2)

Dans ML-KEM, la structure à deux niveaux est:

ML-KEM (IND-CCA2)
└── K-PKE (IND-CPA) + transformation FO
    └── problème MLWE

ML-KEM.Encaps(ek)

m ← Random(32)                  // message aléatoire 256 bits
(K̄, r) = G(m ‖ H(ek))          // SHA3-512: K̄ = premiers 32 octets, r = derniers 32 octets
c = K-PKE.Encrypt(ek, m, r)     // chiffrement déterministe avec aléa r
K = KDF(K̄ ‖ H(c))              // clé finale
return (K, c)

ML-KEM.Decaps(dk, c)

(dk_PKE, ek, h, z) = dk         // h = H(ek), z = secret de repli
m' = K-PKE.Decrypt(dk_PKE, c)   // tentative de déchiffrement
(K̄', r') = G(m' ‖ h)           // recalcule
c' = K-PKE.Encrypt(ek, m', r')  // rechiffrement de vérification
si c' == c:
    K = KDF(K̄' ‖ H(c))         // déchiffrement réussi
sinon:
    K = KDF(z ‖ H(c))           // repli: clé pseudo-aléatoire
return K

Détails importants: La clé privée dk contient également ek pour pouvoir faire le rechiffrement. La comparaison c' == c doit être en temps constant.

6.7 KEM dans un protocole réel: TLS 1.3

Client (Bob)
Serveur (Alice)
ClientHello (supporte ML-KEM-768)
ServerHello + Certificat + KeyShare (ek)
KeyShare (c) + Finished (MAC avec K)
Finished (MAC avec K)

Hybride X25519 + ML-KEM

En pratique, TLS 1.3 utilise une approche hybride:

\[ K_{\text{TLS}} = \text{HKDF}(K_{\text{X25519}} \,\|\, K_{\text{ML-KEM}}) \]

Cela garantit la sécurité si au moins l'un des deux schémas tient. Le groupe X25519MLKEM768 est déjà déployé par Chrome 131+.

6.8 Structure générique du flux KEM

Flux complet Alice (Destinataire) / Bob (Expéditeur)

  1. Alice: KeyGen() génère \((ek, dk)\). Publie \(ek\).
  2. Bob: Reçoit \(ek\). Exécute Encaps(ek):
    • Génère \(m\) aléatoire
    • \((\bar{K}, r) = G(m \| H(ek))\)
    • \(c = \text{K-PKE.Encrypt}(ek, m, r)\)
    • \(K = \text{KDF}(\bar{K} \| H(c))\)
  3. Bob: Chiffre les données avec AES-256-GCM en utilisant \(K\) et un nonce aléatoire.
  4. Bob: Envoie \((c, \text{nonce}, \text{chiffré}, \text{tag})\) à Alice.
  5. Alice: Exécute Decaps(dk, c) pour récupérer \(K\).
  6. Alice: Déchiffre les données avec AES-256-GCM. Si le tag échoue, elle rejette le message.

Double protection: Si c est altéré, Decaps retourne une clé pseudo-aléatoire (\(K_{\text{reject}}\)). Même si l'adversaire devine cette clé, le tag AEAD d'AES-GCM échouerait, garantissant l'intégrité.

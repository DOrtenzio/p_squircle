6.1 Formale Definition eines KEM

Triple von Algorithmen

Ein Key Encapsulation Mechanism (KEM) ist ein Triple von probabilistischen polynomialen Algorithmen:

\[ \text{KEM} = (\text{KeyGen},\ \text{Encaps},\ \text{Decaps}) \]
  • KeyGen() → (ek, dk)
    Probabilistischer Algorithmus (verwendet interne Zufälligkeit). Hat keine Eingabe.
    • ek: Encapsulation Key (öffentlicher Schlüssel)
    • dk: Decapsulation Key (privater Schlüssel)
  • Encaps(ek) → (K, c)
    Gegeben ek, erzeugt:
    • \(K \in \{0,1\}^\ell\): geheimer symmetrischer Schlüssel (typischerweise 256 Bit)
    • c: Chiffrat (die "Kapsel")
  • Decaps(dk, c) → K
    Gegeben dk und c, stellt \(K\) wieder her.

Terminologie-Hinweis FIPS 203: Der Standard verwendet ek für den Encapsulation Key (nicht pk) und dk für den Decapsulation Key (nicht sk). Die Unterscheidung ist beabsichtigt: Sie unterstreicht, dass der öffentliche Schlüssel zum Einkapseln dient, nicht zum Verschlüsseln beliebiger Nachrichten.

Korrektheit

Ein KEM ist korrekt, wenn für jedes gültige Schlüsselpaar gilt:

\[ \Pr\bigl[\text{Decaps}(dk,\, c) = K \mid (K, c) \leftarrow \text{Encaps}(ek)\bigr] \geq 1 - \delta \]

wobei \(\delta\) eine vernachlässigbare Fehlerwahrscheinlichkeit ist (typischerweise \(< 2^{-128}\)).
Für ML-KEM-768: \(\delta < 2^{-142}\).

6.2 Sicherheitseigenschaften

IND-CPA (Indistinguishability under Chosen Plaintext Attack)

IND-CPA-Sicherheitsspiel

Herausforderer Angreifer \(\mathcal{A}\)
\((ek, dk) \leftarrow \text{KeyGen}()\)
\(ek \longrightarrow\)
Wählt Challenge (implizit im KEM)
\((K_0, c) \leftarrow \text{Encaps}(ek)\)
\(K_1 \leftarrow \text{Zufall}\)
\(b \leftarrow \{0, 1\}\)
\((c, K_b) \longrightarrow\)
Gibt \(b'\) zurück

Vorteil: \(\text{Adv}^{\text{IND-CPA}}_{\text{KEM}}(\mathcal{A}) = \left| \Pr[b' = b] - \frac{1}{2} \right|\)

Das KEM ist IND-CPA, wenn der Vorteil für jeden polynomialen Angreifer vernachlässigbar ist. Intuitiv: Der Angreifer kann den echten Schlüssel \(K\) nicht von einem zufälligen unterscheiden, selbst wenn er das Chiffrat c sieht.

IND-CCA2 (Indistinguishability under Adaptive Chosen Ciphertext Attack)

Wie CPA, aber der Angreifer hat zusätzlich Zugang zu einem Decapsulations-Orakel:

Phase Aktion
Initialisierung \((ek, dk) \leftarrow \text{KeyGen}()\), sende \(ek\)
Phase 1 (Abfragen) \(c_i \to K_i = \text{Decaps}(dk, c_i)\)
Challenge \((K_0, c^*) \leftarrow \text{Encaps}(ek)\), \(K_1 \leftarrow \text{Zufall}\), \(b \leftarrow \{0,1\}\). Sende \((c^*, K_b)\).
Phase 2 (Abfragen) \(c_j \to K_j = \text{Decaps}(dk, c_j)\) mit \(c_j \neq c^*\)
Schätzung Gibt \(b'\) zurück

IND-CCA2 ist der Sicherheitsstandard, der für KEMs im realen Einsatz erforderlich ist.

Warum ist CCA2 notwendig? In einem realen Protokoll (TLS, SSH) kann ein aktiver Angreifer manipulierte Chiffrate senden und die Antworten des Servers beobachten. Selbst bei MLWE könnte ein Angreifer, der die Decapsulation von Chiffraten kennt, die dem Challenge-Chiffrat nahe kommen, Informationen über das Geheimnis extrahieren. ML-KEM ist IND-CCA2.

Zusätzliche wünschenswerte Eigenschaften

  • Robustheit (Robustness): Es ist schwierig, Chiffrate zu konstruieren, die mit zwei verschiedenen privaten Schlüsseln zum gleichen Schlüssel decapsulieren.
  • Forward Secrecy: Wenn der private Schlüssel dk in Zukunft kompromittiert wird, bleiben vergangene Sitzungen sicher (erfordert ephemere Schlüssel).

6.3 KEM vs. PKE: warum KEMs

PKE (Public Key Encryption)

Ein PKE verschlüsselt beliebige Nachrichten: \(\text{Enc}(ek, m) \to c\). Das Problem ist, dass wenn die Nachricht \(m\) eine vorhersagbare Struktur hat (kurzes Passwort, Kreditkartennummer), ein Angreifer Angriffe mit geringer Entropie oder Padding-Orakel (Bleichenbacher) ausnutzen kann.

KEM: Trennung der Rollen

Das KEM verschlüsselt keine Benutzernachrichten. Es erzeugt einen symmetrischen Schlüssel hoher Entropie und kapselt ihn ein:

\[ \text{System} = \underbrace{\text{KEM}}_{\text{tauscht } K \text{ aus}} + \underbrace{\text{AES-GCM}}_{\text{verschlüsselt Daten mit } K} \]

Vorteile:

  • Der Schlüssel \(K\) ist immer pseudozufällig → keine Angriffe mit geringer Entropie.
  • Es wird kein komplexes Padding für Benutzernachrichten benötigt.
  • \(K\) wird mit einer symmetrischen Chiffre (DEM) zur Verschlüsselung der eigentlichen Daten verwendet.

6.4 Intuitives Beispiel: KEM aus Diffie-Hellman

Vor ML-KEM war das am häufigsten verwendete KEM auf Diffie-Hellman aufgebaut. Dieses Beispiel hilft, die Struktur zu verstehen.

Öffentliche Parameter: Primzahl \(p\), Generator \(g\) von \(\mathbb{Z}_p^*\).

Alice
  1. Wählt geheimes \(a\)
  2. Berechnet \(A = g^a \bmod p\)
A → ← B
Bob
  1. Wählt geheimes \(b\)
  2. Berechnet \(B = g^b \bmod p\)
\[ \begin{aligned} \text{Alice berechnet: } & K = B^a \bmod p = g^{ab} \bmod p \\ \text{Bob berechnet: } & K = A^b \bmod p = g^{ab} \bmod p \end{aligned} \]

Numerisches Beispiel: \(p = 17\), \(g = 3\), \(a = 5\).

  • \(ek = 3^5 \bmod 17 = 5\)
  • Bob wählt \(b = 7\): \(c = 3^7 \bmod 17 = 11\), \(K = H(5^7 \bmod 17) = H(10)\)
  • Alice decapsuliert: \(K = H(11^5 \bmod 17) = H(10)\) ✓

6.5 Die Fujisaki-Okamoto-Transformation (FO)

Das Problem: von CPA zu CCA2

Ausgehend von einem nur CPA-sicheren PKE, wie konstruiert man ein IND-CCA2-sicheres KEM? Die Antwort ist die FO-Transformation.

Zentrale Idee

  • Deterministische Verschlüsselung: Die bei der Verschlüsselung verwendete Zufälligkeit wird deterministisch aus der Nachricht durch eine Hash-Funktion abgeleitet. Wenn das Chiffrat modifiziert wird, erzeugt die erneute Verschlüsselung etwas anderes.
  • Verifikation bei der Entschlüsselung: Anstatt direkt zu entschlüsseln, wird die entschlüsselte Nachricht erneut verschlüsselt und mit dem empfangenen Chiffrat verglichen. Bei Nichtübereinstimmung → implizite Ablehnung.

Vereinfachtes FO-Schema

\[ \begin{aligned} \text{Encaps}(ek): & \quad m \leftarrow \{0,1\}^\ell, \ (K, r) = G(m), \ c = \text{Enc}(ek, m; r) \\ \text{Decaps}(dk, c): & \quad m' = \text{Dec}(dk, c), \ (K', r') = G(m'), \ c' = \text{Enc}(ek, m'; r') \\ & \quad \text{return } \begin{cases} K' & \text{falls } c' = c \\ K_{\text{reject}} & \text{sonst} \end{cases} \end{aligned} \]

Wobei \(K_{\text{reject}} = H(z \| c)\) mit festem geheimen \(z\). Diese "implizite Ablehnung" verhindert, dass der Angreifer Fehler als Orakel nutzen kann.

6.6 Von K-PKE (CPA) zu ML-KEM (CCA2)

In ML-KEM ist die zweistufige Struktur:

ML-KEM (IND-CCA2)
└── K-PKE (IND-CPA) + FO-Transformation
    └── MLWE-Problem

ML-KEM.Encaps(ek)

m ← Zufall(32)                  // zufällige Nachricht 256 Bit
(K̄, r) = G(m ‖ H(ek))          // SHA3-512: K̄ = erste 32 Byte, r = letzte 32 Byte
c = K-PKE.Encrypt(ek, m, r)     // deterministische Verschlüsselung mit Zufälligkeit r
K = KDF(K̄ ‖ H(c))              // finaler Schlüssel
return (K, c)

ML-KEM.Decaps(dk, c)

(dk_PKE, ek, h, z) = dk         // h = H(ek), z = Fallback-Geheimnis
m' = K-PKE.Decrypt(dk_PKE, c)   // Entschlüsselungsversuch
(K̄', r') = G(m' ‖ h)           // Neuberechnung
c' = K-PKE.Encrypt(ek, m', r')  // Verifikations-Wiederverschlüsselung
falls c' == c:
    K = KDF(K̄' ‖ H(c))         // Entschlüsselung erfolgreich
sonst:
    K = KDF(z ‖ H(c))           // Fallback: pseudozufälliger Schlüssel
return K

Wichtige Details: Der private Schlüssel dk enthält auch ek, um die Wiederverschlüsselung durchführen zu können. Der Vergleich c' == c muss zeitkonstant sein.

6.7 KEM in einem realen Protokoll: TLS 1.3

Client (Bob)
Server (Alice)
ClientHello (unterstützt ML-KEM-768)
ServerHello + Zertifikat + KeyShare (ek)
KeyShare (c) + Finished (MAC mit K)
Finished (MAC mit K)

Hybrid X25519 + ML-KEM

In der Praxis verwendet TLS 1.3 einen hybriden Ansatz:

\[ K_{\text{TLS}} = \text{HKDF}(K_{\text{X25519}} \,\|\, K_{\text{ML-KEM}}) \]

Dies garantiert Sicherheit, wenn mindestens eines der beiden Schemata standhält. Die Gruppe X25519MLKEM768 wird bereits seit Chrome 131+ eingesetzt.

6.8 Generische Struktur des KEM-Flusses

Vollständiger Fluss Alice (Empfänger) / Bob (Sender)

  1. Alice: KeyGen() erzeugt \((ek, dk)\). Veröffentlicht \(ek\).
  2. Bob: Empfängt \(ek\). Führt Encaps(ek) aus:
    • Erzeugt zufälliges \(m\)
    • \((\bar{K}, r) = G(m \| H(ek))\)
    • \(c = \text{K-PKE.Encrypt}(ek, m, r)\)
    • \(K = \text{KDF}(\bar{K} \| H(c))\)
  3. Bob: Verschlüsselt die Daten mit AES-256-GCM unter Verwendung von \(K\) und einer zufälligen Nonce.
  4. Bob: Sendet \((c, \text{Nonce}, \text{Chiffrat}, \text{Tag})\) an Alice.
  5. Alice: Führt Decaps(dk, c) aus, um \(K\) wiederherzustellen.
  6. Alice: Entschlüsselt die Daten mit AES-256-GCM. Wenn der Tag fehlschlägt, verwirft sie die Nachricht.

Doppelter Schutz: Wenn c manipuliert wird, gibt Decaps einen pseudozufälligen Schlüssel (\(K_{\text{reject}}\)) zurück. Selbst wenn der Angreifer diesen Schlüssel erraten würde, würde das AEAD-Tag von AES-GCM fehlschlagen, was die Integrität gewährleistet.

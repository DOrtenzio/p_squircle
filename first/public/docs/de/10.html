10.1 liboqs: die C-Referenzbibliothek

liboqs ist die C-Referenzbibliothek für Post-Quanten-Kryptographie, entwickelt vom Open Quantum Safe (OQS)-Projekt. Sie bietet optimierte und zeitkonstante Implementierungen von ML-KEM und anderen vom NIST standardisierten PQC-Algorithmen.

Installation aus den Quellen

# Abhängigkeiten (Ubuntu/Debian)
sudo apt-get install cmake gcc libssl-dev

# Klonen und Build
git clone https://github.com/open-quantum-safe/liboqs.git
cd liboqs
mkdir build && cd build
cmake -DCMAKE_INSTALL_PREFIX=/usr/local ..
make -j$(nproc)
sudo make install

10.2 Vollständiges Beispiel: KEM mit ML-KEM-768 in C

#include <stdio.h>
#include <string.h>
#include <oqs/oqs.h>

int main() {
    OQS_STATUS rc;
    const char *kem_alg = OQS_KEM_alg_ml_kem_768;

    // Initialisiere den Algorithmus
    OQS_KEM *kem = OQS_KEM_new(kem_alg);
    if (kem == NULL) {
        fprintf(stderr, "KEM nicht unterstützt\n");
        return 1;
    }

    printf("Algorithmus: %s\n", kem->method_name);
    printf("Öffentlicher Schlüssel: %zu Byte\n", kem->length_public_key);
    printf("Privater Schlüssel: %zu Byte\n", kem->length_secret_key);
    printf("Chiffrat: %zu Byte\n", kem->length_ciphertext);
    printf("Shared Secret: %zu Byte\n\n", kem->length_shared_secret);

    // Speicherzuweisung
    uint8_t *pk = malloc(kem->length_public_key);
    uint8_t *sk = malloc(kem->length_secret_key);
    uint8_t *ct = malloc(kem->length_ciphertext);
    uint8_t *ss_enc = malloc(kem->length_shared_secret);
    uint8_t *ss_dec = malloc(kem->length_shared_secret);

    // 1. KeyGen (Alice)
    rc = OQS_KEM_keypair(kem, pk, sk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "KeyGen fehlgeschlagen\n"); return 1; }
    printf("✓ KeyGen abgeschlossen\n");

    // 2. Encaps (Bob: kennt nur pk)
    rc = OQS_KEM_encaps(kem, ct, ss_enc, pk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "Encaps fehlgeschlagen\n"); return 1; }
    printf("✓ Encaps abgeschlossen\n");

    // 3. Decaps (Alice: verwendet sk, um ct zu öffnen)
    rc = OQS_KEM_decaps(kem, ss_dec, ct, sk);
    if (rc != OQS_SUCCESS) { fprintf(stderr, "Decaps fehlgeschlagen\n"); return 1; }
    printf("✓ Decaps abgeschlossen\n\n");

    // 4. Verifikation
    if (memcmp(ss_enc, ss_dec, kem->length_shared_secret) == 0) {
        printf("✅ Shared Secrets stimmen überein!\n");
        printf("   Erste Bytes: ");
        for (int i = 0; i < 8; i++) printf("%02x", ss_enc[i]);
        printf("...\n");
    } else {
        printf("❌ FEHLER: Shared Secrets unterschiedlich!\n");
    }

    // Sichere Speicherbereinigung
    OQS_MEM_cleanse(sk, kem->length_secret_key);
    OQS_MEM_cleanse(ss_enc, kem->length_shared_secret);
    OQS_MEM_cleanse(ss_dec, kem->length_shared_secret);
    free(pk); free(ct);
    OQS_KEM_free(kem);
    
    return 0;
}

Kompilierung:

gcc -o kem_example kem_example.c -loqs -lcrypto
./kem_example

10.3 Verwendung des abgeleiteten Schlüssels mit AES-256-GCM

Nachdem das Shared Secret von ML-KEM erhalten wurde, kann es als Schlüssel für eine symmetrische Chiffre verwendet werden. In der Produktion wird empfohlen, HKDF zur Ableitung separater Schlüssel zu verwenden.

#include <openssl/evp.h>
#include <oqs/oqs.h>

// Nachdem ss (32 Byte) von ML-KEM erhalten wurde:
void encrypt_with_kem_key(const uint8_t *ss, const uint8_t *plaintext,
                           size_t pt_len, uint8_t *ciphertext, uint8_t *tag,
                           const uint8_t *nonce) {
    EVP_CIPHER_CTX *ctx = EVP_CIPHER_CTX_new();
    int len;

    // Initialisiere AES-256-GCM
    EVP_EncryptInit_ex(ctx, EVP_aes_256_gcm(), NULL, NULL, NULL);
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_IVLEN, 12, NULL);
    
    // Verwende das Shared Secret als Schlüssel
    EVP_EncryptInit_ex(ctx, NULL, NULL, ss, nonce);
    
    // Verschlüsselung
    EVP_EncryptUpdate(ctx, ciphertext, &len, plaintext, pt_len);
    EVP_EncryptFinal_ex(ctx, ciphertext + len, &len);
    
    // Tag abrufen
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_GET_TAG, 16, tag);
    
    EVP_CIPHER_CTX_free(ctx);
}

10.4 Python: liboqs-Bindings

Liboqs bietet offizielle Python-Bindings für schnelle Tests und Prototypen.

pip install liboqs-python
import oqs

# Verfügbarer Algorithmus
kem = oqs.KeyEncapsulation("ML-KEM-768")

# KeyGen
public_key = kem.generate_keypair()

# Encaps (Bob-Seite)
kem_bob = oqs.KeyEncapsulation("ML-KEM-768")
ciphertext, shared_secret_enc = kem_bob.encap_secret(public_key)

# Decaps (Alice-Seite)
shared_secret_dec = kem.decap_secret(ciphertext)

assert shared_secret_enc == shared_secret_dec
print(f"✓ Shared Secret: {shared_secret_enc.hex()[:16]}...")

kem.free()
kem_bob.free()

10.5 Python: kyber-py (nur zu Lehrzwecken)

Für rein didaktische Zwecke gibt es eine reine Python-Implementierung, die keine externen C-Bibliotheken benötigt.

Achtung: kyber-py ist nicht zeitkonstant und darf nicht in der Produktion verwendet werden.

                    
                        from kyber import Kyber768
                        kem = Kyber768()
                        pk, sk = kem.keygen()
                        key, ciphertext = kem.enc(pk)
                        _key = kem.dec(sk, ciphertext)
                        assert key == _key

10.6 Leistungsbenchmarks

Benchmarks auf Intel Core i7-12700K (ein Kern, ohne SIMD-Instruktionen):

Operation ML-KEM-512 ML-KEM-768 ML-KEM-1024
KeyGen 24 µs 37 µs 54 µs
Encaps 28 µs 43 µs 62 µs
Decaps 32 µs 48 µs 70 µs

Mit AVX2-Optimierungen

Operation ML-KEM-768 (ohne SIMD) ML-KEM-768 (AVX2) Beschleunigung
KeyGen 37 µs ~10 µs ~3.7×
Encaps 43 µs ~12 µs ~3.6×
Decaps 48 µs ~13 µs ~3.7×

Vergleich mit ECDH X25519

X25519 ML-KEM-768
KeyGen ~14 µs ~37 µs
Austausch ~30 µs ~48 µs
Öffentlicher Schlüssel 32 B 1184 B

ML-KEM ist etwa 2× langsamer als X25519, aber der Overhead auf die TLS-Handshake-Latenz ist auf den meisten realen Verbindungen vernachlässigbar (< 1 ms).

10.7 OpenSSL: Installation des OQS-Providers

OpenSSL 3.x unterstützt ML-KEM über den Provider oqsprovider. Ab Version 3.4 ist die Unterstützung nativ oder leicht integrierbar.

# Build von oqs-provider
git clone https://github.com/open-quantum-safe/oqs-provider.git
cd oqs-provider
cmake -DOPENSSL_ROOT_DIR=/usr/local/ssl .
make
sudo make install

# Verifikation
openssl list -providers
# sollte anzeigen: oqsprovider

10.8 Generierung von ML-KEM-Schlüsseln mit OpenSSL CLI

# Generiere ML-KEM-768-Schlüsselpaar
openssl genpkey -algorithm mlkem768 -out private.pem
openssl pkey -in private.pem -pubout -out public.pem

# Zeige Schlüsseldetails an
openssl pkey -in private.pem -text -noout

10.9 TLS 1.3 mit ML-KEM-768

Lokaler Test (Server + Client)

# Server
openssl s_server -accept 4433 -cert server.crt -key server.key \
    -groups mlkem768

# Client (in einem anderen Terminal)
openssl s_client -connect localhost:4433 -groups mlkem768

Unterstützte Gruppen anzeigen

openssl list -key-exchange-algorithms | grep -i kem

10.10 Hybridstrategie: X25519 + ML-KEM-768

Der empfohlene Ansatz für die Migration ist die Hybridisierung: Kombination von ECDH (X25519) mit ML-KEM-768. Der finale Schlüssel wird aus beiden abgeleitet:

\[ K = \text{HKDF}(K_{\text{X25519}} \| K_{\text{ML-KEM}}) \]

Vorteil: Sicher, wenn mindestens eines der beiden Schemata standhält. Wenn ein Quantencomputer X25519 bricht, schützt ML-KEM. Wenn ML-KEM einen unbekannten Fehler hätte, schützt X25519.

10.11 Hybride Cipher Suites in TLS 1.3

Gruppenname Zusammensetzung
X25519MLKEM768 X25519 + ML-KEM-768
SecP256r1MLKEM768 P-256 + ML-KEM-768

Ab Chrome 131 (Ende 2024) ist X25519MLKEM768 die Standardgruppe. Firefox 128+ unterstützt dieselbe Gruppe.

OpenSSL-Konfiguration

# Server, der sowohl klassisches X25519 als auch die hybride Gruppe akzeptiert
openssl s_server -accept 4433 -cert server.crt -key server.key \
    -groups X25519MLKEM768:x25519:P-256

# Client, der die hybride Gruppe bevorzugt
openssl s_client -connect localhost:4433 \
    -groups X25519MLKEM768:x25519

10.12 Integration in C-Anwendungen mit OpenSSL

#include <openssl/ssl.h>
#include <openssl/err.h>

SSL_CTX *create_pqc_context(void) {
    SSL_CTX *ctx = SSL_CTX_new(TLS_server_method());
    if (!ctx) {
        ERR_print_errors_fp(stderr);
        return NULL;
    }

    // Setze bevorzugte Gruppen: hybrid zuerst, dann klassisch als Fallback
    if (SSL_CTX_set1_groups_list(ctx, "X25519MLKEM768:x25519:P-256") != 1) {
        fprintf(stderr, "Fehler bei der Gruppenkonfiguration\n");
        SSL_CTX_free(ctx);
        return NULL;
    }

    return ctx;
}

10.13 Migrations-Checkliste

Für Anwendungsentwickler

  • Inventarisieren, wo asymmetrische Kryptographie verwendet wird (Schlüsselaustausch, Signatur, KEM).
  • Identifizieren, welche Daten länger als 5 Jahre geheim bleiben müssen.
  • Abhängigkeiten aktualisieren: OpenSSL ≥ 3.2, liboqs ≥ 0.10.
  • Hybriden Ansatz übernehmen: X25519 + ML-KEM-768 für TLS.
  • Für digitale Signaturen: Migration zu ML-DSA (FIPS 204) oder SLH-DSA (FIPS 205).
  • Die vergrößerte Größe von Schlüsseln und Chiffraten in Protokollen testen.
  • Überprüfen, ob Timeouts und Puffergrößen nicht von kleinen Schlüsseln ausgehen.

Für Infrastrukturbetreiber

  • TLS-Stack auf Versionen mit ML-KEM-Unterstützung aktualisieren.
  • X25519MLKEM768 auf TLS-Servern aktivieren.
  • Client-Kompatibilität überwachen (Chrome 131+, Firefox 128+ unterstützen hybrides PQC).
  • Rotation von langfristigen Schlüsseln planen.

Referenzstandards

Standard Inhalt
FIPS 203 ML-KEM (Key Encapsulation)
FIPS 204 ML-DSA (gitterbasierte digitale Signatur)
FIPS 205 SLH-DSA (hashbasierte Signatur, konservativ)

10.14 Szenario: Migration einer REST-API

Aktuelle Situation (vor der Migration)

Client → TLS 1.3 mit X25519 → API-Server

Phase 1: Hybrid (heute, empfohlen)

Client → TLS 1.3 mit X25519MLKEM768 → API-Server

# nginx-Konfiguration
ssl_ecdh_curve X25519MLKEM768:x25519:P-256;

# Apache-Konfiguration
SSLOpenSSLConfCmd Curves X25519MLKEM768:x25519:P-256;

Phase 2: Rein post-quantum (Zukunft)

Client → TLS 1.3 mit ML-KEM-768 + ML-DSA → API-Server

Umzustellen, wenn die Mehrheit der Clients native ML-KEM-Unterstützung bietet und Serverzertifikate ML-DSA für die Signatur verwenden.

1.1 What is symmetric cryptography

In a symmetric cryptographic system, the sender and recipient use the same key \(K\) to encrypt and decrypt.

\(\text{Sender: } C = \text{Enc}(K, M)\)

\(\text{Recipient: } M = \text{Dec}(K, C)\)

Main advantage: efficiency. AES-256 on modern hardware reaches speeds of tens of GB/s.

Disadvantage: a secure channel is needed to exchange \(K\) before communicating. This is exactly the problem that KEMs solve.

Symmetric cryptography vs. quantum security

Quantum computers do not break AES. Grover's algorithm offers a quadratic speedup in key searching, but:

  • AES-128: effective security drops from 128 bits to ~64 bits → insufficient
  • AES-256: effective security drops from 256 bits to ~128 bits → still secure

For this reason, FIPS 203 (ML-KEM) produces 256-bit keys, intended to be used with AES-256.

1.2 AES: Advanced Encryption Standard

AES is a block cipher: it takes a 128-bit block and a key (\(K\)), and produces a 128-bit ciphertext.

Internal structure

AES organizes the 128-bit input as a \(4 \times 4\) matrix of bytes. It then applies \(r\) rounds (10, 12, or 14 depending on the key size), each consisting of four transformations:

Transformation Purpose
SubBytes Non-linear substitution via S-Box (resistance to differential cryptanalysis)
ShiftRows Cyclic row rotation (diffusion)
MixColumns Linear column combination (diffusion)
AddRoundKey XOR with the current round subkey

Key schedule

The original key (\(K\) of 128, 192, or 256 bits) is expanded into \(r+1\) subkeys, one for each round.

AES-128: 128-bit key, 10 rounds

AES-192: 192-bit key, 12 rounds

AES-256: 256-bit key, 14 rounds

Security

The best known attack on AES-128 requires \(2^{126.1}\) operations (Biryukov & Khovratovich, 2009) – substantially brute force.

1.3 Modes of operation

AES encrypts a 128-bit block. However, real-world messages are longer. Modes of operation define how to apply AES repeatedly.

ECB (Electronic Codebook) – do not use

Each block is encrypted independently. Identical blocks produce identical ciphertexts → leaks the plaintext structure.

CBC (Cipher Block Chaining)

Each plaintext block is XORed with the ciphertext of the previous block before being encrypted. Requires a random IV (Initialization Vector).

\[ C_i = E_K(P_i \oplus C_{i-1}) \]

More secure than ECB, but not parallelizable during encryption.

CTR (Counter Mode) – recommended

Generates a keystream by encrypting an incremental counter. The plaintext is XORed with the keystream.

\[ C_i = P_i \oplus E_K(\text{nonce} \| i) \]

Parallelizable in both encryption and decryption. Transforms AES into a stream cipher.

GCM (Galois/Counter Mode) – used in TLS 1.3

Combines CTR with a MAC based on Galois fields. Provides confidentiality and authenticity.

1.4 Authentication and AEAD

Confidentiality is not enough: an attacker could modify the ciphertext without the recipient noticing. Authenticity is required.

MAC (Message Authentication Code)

A MAC is a function \(\text{MAC}(K, M) \to \tau\) where \(\tau\) is the authenticity tag. Only those who know \(K\) can generate and verify \(\tau\).

AEAD (Authenticated Encryption with Associated Data)

Combines encryption and authentication into a single primitive:

\(\text{Enc: } (K, \text{nonce}, \text{AAD}, \text{plaintext}) \to (\text{ciphertext}, \text{tag})\)

\(\text{Dec: } (K, \text{nonce}, \text{AAD}, \text{ciphertext}, \text{tag}) \to \text{plaintext}\) or \(\perp\) (if tag is invalid)

AAD (Additional Authenticated Data) represents authenticated but unencrypted data (e.g., packet headers).

AES-256-GCM is the standard AEAD scheme used in TLS 1.3 and as a symmetric cipher following a KEM.

1.5 Role in the PQC context

A complete ML-KEM workflow in real-world use works as follows:

Alice Bob | | | KeyGen() → (pk, sk) | | | | ------------ pk ----------------->| | | | Encaps(pk) → (K, C) | | | | K_enc = HKDF(K, "enc") | | K_mac = HKDF(K, "mac") | | C_data = AES-256-GCM(K_enc, Message) | | | | <----- (C, C_data, nonce, tag) --| | | | Decaps(sk, C) → K | | K_enc = HKDF(K, "enc") | | Message = AES-256-GCM-Dec(K_enc, C_data) | | | | ✓ Secure communication |

The key \(K\) produced by ML-KEM (32 bytes) is not used directly as an AES key, but is derived using a KDF (Key Derivation Function) such as HKDF to separate different contexts.

Practical sizes (ML-KEM-768 + AES-256-GCM)

Component Size
ML-KEM Public Key 1184 bytes
ML-KEM Ciphertext 1088 bytes
Shared secret → AES key 32 bytes
AEAD Overhead (GCM tag) 16 bytes

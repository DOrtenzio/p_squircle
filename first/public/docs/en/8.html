08 – FIPS 203 / ML-KEM

The heart of the standard: KeyGen, Encaps and Decaps

8.1 Standard overview

FIPS 203 was published by NIST in August 2024 as the first post-quantum standard for protecting communications. It is based on the CRYSTALS-Kyber submission from the NIST PQC Competition.

What FIPS 203 standardizes:

  • An IND-CCA2-secure KEM (Key Encapsulation Mechanism)
  • Three security levels: ML-KEM-512, ML-KEM-768, ML-KEM-1024
  • All auxiliary functions: hashing, sampling, encoding, compression

What it does NOT standardize:

  • How to manage keys
  • Which symmetric cipher to use with the derived key
  • Handshake protocols (see TLS 1.3, SSH)

8.2 The K‑PKE primitives

ML-KEM is built on two levels. The inner level is K‑PKE, a CPA-secure PKE (but not CCA-secure). ML-KEM adds the FO transformation to achieve CCA2.

K‑PKE.KeyGen

  1. Input: 32-byte seed \(d\)
  2. \(\rho, \sigma = G(d)\) where \(G = \text{SHA3-512}\)
  3. \(\mathbf{A} = \text{SampleNTT}(\rho)\) (public matrix, already in NTT domain)
  4. For \(i = 0 \dots k-1\):
    • \(\mathbf{s}[i], \mathbf{e}[i] = \text{SamplePolyCBD}(\sigma, i)\)
  5. \(\hat{\mathbf{s}} = \text{NTT}(\mathbf{s})\), \(\hat{\mathbf{e}} = \text{NTT}(\mathbf{e})\)
  6. \(\hat{\mathbf{t}} = \mathbf{A} \circ \hat{\mathbf{s}} + \hat{\mathbf{e}}\)
  7. Output:
    • \(ek_{\text{PKE}} = \text{Encode}(\hat{\mathbf{t}}) \| \rho\)
    • \(dk_{\text{PKE}} = \text{Encode}(\hat{\mathbf{s}})\)

K‑PKE.Encrypt

  1. Input: \(ek_{\text{PKE}}\), message \(m\), randomness \(r\)
  2. Parse \(\hat{\mathbf{t}}\) and \(\rho\) from \(ek\)
  3. \(\mathbf{A} = \text{SampleNTT}(\rho)\)
  4. Sample small vectors \(\mathbf{r}, \mathbf{e}_1, e_2\) using \(r\) as seed (CBD)
  5. \(\hat{\mathbf{u}} = \text{NTT}^{-1}(\mathbf{A}^T \circ \text{NTT}(\mathbf{r})) + \mathbf{e}_1\)
  6. \(v = \text{NTT}^{-1}(\hat{\mathbf{t}}^T \circ \text{NTT}(\mathbf{r})) + e_2 + \text{Decode}(m)\)
  7. Compress \(\mathbf{u}\) and \(v\)
  8. Output: ciphertext \(c\)

K‑PKE.Decrypt

  1. Input: \(dk_{\text{PKE}}\), ciphertext \(c\)
  2. Decompress \(\mathbf{u}\) and \(v\) from \(c\)
  3. \(\hat{\mathbf{s}} = \text{Decode}(dk_{\text{PKE}})\)
  4. \(w = v - \text{NTT}^{-1}(\hat{\mathbf{s}}^T \circ \text{NTT}(\mathbf{u}))\)
  5. \(m = \text{Encode}(\text{Compress}(w))\) (decode the message from residual noise)
  6. Output: \(m\)

8.3 ML‑KEM (the complete scheme)

K‑PKE is only CPA‑secure. ML‑KEM uses the Fujisaki‑Okamoto (FO) transformation to elevate K‑PKE to IND‑CCA2. Decryption verifies that the received ciphertext matches what one would obtain by re-encrypting the decrypted message; if not, it returns a pseudorandom key (implicit reject).

8.3.1 ML‑KEM.KeyGen

\[ \begin{aligned} & z \leftarrow \{0,1\}^{256}, \quad d \leftarrow \{0,1\}^{256} \\ & (ek_{\text{PKE}}, dk_{\text{PKE}}) = \text{K-PKE.KeyGen}(d) \\ & ek = ek_{\text{PKE}} \\ & dk = dk_{\text{PKE}} \| ek \| H(ek) \| z \\ & \text{return } (ek, dk) \end{aligned} \]

The private key includes \(ek\) and precomputed hashes to optimize Decaps.

8.3.2 ML‑KEM.Encaps

\[ \begin{aligned} & m \leftarrow \{0,1\}^{256} \\ & (\bar{K}, r) = G(m \| H(ek)) \\ & c = \text{K-PKE.Encrypt}(ek, m, r) \\ & K = \text{KDF}(\bar{K} \| H(c)) \\ & \text{return } (K, c) \end{aligned} \]

8.3.3 ML‑KEM.Decaps

\[ \begin{aligned} & (dk_{\text{PKE}}, ek, h, z) = \text{ParseDK}(dk) \\ & m' = \text{K-PKE.Decrypt}(dk_{\text{PKE}}, c) \\ & (\bar{K}', r') = G(m' \| h) \\ & c' = \text{K-PKE.Encrypt}(ek, m', r') \\ & \text{if } c' == c: \\ & \quad K = \text{KDF}(\bar{K}' \| H(c)) \\ & \text{else:} \\ & \quad K = \text{KDF}(z \| H(c)) \\ & \text{return } K \end{aligned} \]

Note: the comparison \(c' == c\) must be performed in constant time to avoid side‑channel attacks.

8.4 Auxiliary primitive functions

Hashes used

Function Input Output Use
\(H = \text{SHA3-256}\) any 32 bytes generic hashing
\(G = \text{SHA3-512}\) any 64 bytes key derivation
\(\text{XOF} = \text{SHAKE128}\) any variable length generate \(A\)
\(\text{PRF}_\eta = \text{SHAKE256}\) seed+nonce variable length sample \(s\), \(e\)
\(\text{KDF} = \text{SHAKE256}\) any variable length derive final \(K\)

Sampling of \(A\) (the SampleNTT algorithm)

The matrix \(A \in R_q^{k \times k}\) is generated deterministically from a public seed \(\rho \in \{0,1\}^{256}\):

for i = 0..k-1, j = 0..k-1:
    A[i][j] = SampleNTT(XOF(ρ || j || i))

SampleNTT reads bytes from the XOF and builds uniform coefficients in \(\{0, \ldots, q-1\}\) (discarding values \(\geq q\)).

Noise sampling (the SamplePolyCBD algorithm)

Noise is sampled from the centered binomial distribution \(B_\eta\):

given a 32-byte seed σ and a nonce b:
bytes = PRFη(σ, b)   // 64η bytes
for each pair of bits (a_i, b_i):
    coefficient = Σa_i - Σb_i

The result is a polynomial with coefficients in \([-\eta, \eta]\).

8.5 Compression and decompression

ML-KEM uses compression to reduce ciphertext size. Polynomial coefficients are in \(\{0, \ldots, q-1\}\) (12 bits), but are compressed to \(d_u\) or \(d_v\) bits.

\[ \text{Compress}_d(x) = \left\lfloor \frac{2^d}{q} \cdot x \right\rceil \bmod 2^d \]
\[ \text{Decompress}_d(y) = \left\lfloor \frac{q}{2^d} \cdot y \right\rceil \]

Error introduced by compression: compression introduces an error \(\epsilon = \text{Decompress}_d(\text{Compress}_d(x)) - x\). For \(d_v = 4\): \(|\epsilon| \leq q/2^5 \approx 104\). This error must be small enough not to cause decryption failure, which imposes a constraint on the parameters \(\eta_1\), \(\eta_2\), \(d_u\), \(d_v\).

Noise budget

The total noise reaching decryption is:

\[ \epsilon_{\text{total}} = \hat{\mathbf{e}}^T\hat{\mathbf{r}} + e_2 - \hat{\mathbf{s}}^T e_1 + \epsilon_u + \epsilon_v \]

For correct decryption, we need \(|\epsilon_{\text{total}}| < \lfloor q/4 \rfloor = 832\). The parameters are chosen to ensure this holds with probability \(1 - 2^{-139}\) for ML-KEM-768.

8.6 Correctness and security

Correctness of K‑PKE

The error probability of K‑PKE is analyzed by sampling \(s\), \(e\), \(r\), \(e_1\), \(e_2\) from the \(B_\eta\) distribution. For ML-KEM-768 (\(k=3\), \(\eta_1=\eta_2=2\)), the error probability for a single coefficient is \(< 2^{-150}\), and with 256 coefficients and the union bound the total probability is \(< 2^{-139}\).

IND‑CCA2 security of ML‑KEM

Step 1: From MLWE to K‑PKE IND‑CPA

If an adversary distinguishes K‑PKE ciphertexts, it can be used to solve MLWE (polynomial reduction).

Step 2: From K‑PKE IND‑CPA to ML‑KEM IND‑CCA2

Via the FO transformation in the random oracle model. The re-encryption in decryption is the key: it prevents the adversary from using decryption as an oracle.

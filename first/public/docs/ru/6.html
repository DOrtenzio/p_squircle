6.1 Формальное определение KEM

Тройка алгоритмов

Механизм инкапсуляции ключа (KEM) — это тройка вероятностных полиномиальных алгоритмов:

\[ \text{KEM} = (\text{KeyGen},\ \text{Encaps},\ \text{Decaps}) \]
  • KeyGen() → (ek, dk)
    Вероятностный алгоритм (использует внутреннюю случайность). Не принимает входных данных.
    • ek: ключ инкапсуляции (открытый ключ)
    • dk: ключ декапсуляции (закрытый ключ)
  • Encaps(ek) → (K, c)
    По ek производит:
    • \(K \in \{0,1\}^\ell\): секретный симметричный ключ (обычно 256 бит)
    • c: шифртекст ( "капсула")
  • Decaps(dk, c) → K
    По dk и c восстанавливает \(K\).

Терминологическое примечание FIPS 203: стандарт использует ek для ключа инкапсуляции (не pk) и dk для ключа декапсуляции (не sk). Различие преднамеренное: подчёркивается, что открытый ключ служит для инкапсуляции, а не для шифрования произвольных сообщений.

Корректность

KEM корректен, если для каждой допустимой пары ключей:

\[ \Pr\bigl[\text{Decaps}(dk,\, c) = K \mid (K, c) \leftarrow \text{Encaps}(ek)\bigr] \geq 1 - \delta \]

где \(\delta\) — пренебрежимая вероятность ошибки (обычно \(< 2^{-128}\)).
Для ML-KEM-768: \(\delta < 2^{-142}\).

6.2 Свойства безопасности

IND-CPA (Неразличимость при атаке на основе выбранного открытого текста)

Игра безопасности IND-CPA

Вызывающая сторона Противник \(\mathcal{A}\)
\((ek, dk) \leftarrow \text{KeyGen}()\)
\(ek \longrightarrow\)
Выбирает вызов (неявный в KEM)
\((K_0, c) \leftarrow \text{Encaps}(ek)\)
\(K_1 \leftarrow \text{Random}\)
\(b \leftarrow \{0, 1\}\)
\((c, K_b) \longrightarrow\)
Возвращает \(b'\)

Преимущество: \(\text{Adv}^{\text{IND-CPA}}_{\text{KEM}}(\mathcal{A}) = \left| \Pr[b' = b] - \frac{1}{2} \right|\)

KEM является IND-CPA, если преимущество пренебрежимо для любого полиномиального противника. Интуитивно: противник не может отличить реальный ключ \(K\) от случайного, даже видя шифртекст c.

IND-CCA2 (Неразличимость при адаптивной атаке на основе выбранного шифртекста)

Как CPA, но противник также имеет доступ к оракулу декапсуляции:

Фаза Действие
Инициализация \((ek, dk) \leftarrow \text{KeyGen}()\), отправляет \(ek\)
Фаза 1 (Запросы) \(c_i \to K_i = \text{Decaps}(dk, c_i)\)
Вызов \((K_0, c^*) \leftarrow \text{Encaps}(ek)\), \(K_1 \leftarrow \text{Random}\), \(b \leftarrow \{0,1\}\). Отправляет \((c^*, K_b)\).
Фаза 2 (Запросы) \(c_j \to K_j = \text{Decaps}(dk, c_j)\) с \(c_j \neq c^*\)
Угадывание Возвращает \(b'\)

IND-CCA2 — это стандарт безопасности, требуемый для KEM в реальном использовании.

Почему необходим CCA2? В реальном протоколе (TLS, SSH) активный противник может отправлять модифицированные шифртексты и наблюдать ответы сервера. Даже в MLWE противник, знающий декапсуляцию шифртекстов, близких к шифртексту-вызову, может извлечь информацию о секрете. ML-KEM является IND-CCA2.

Дополнительные желаемые свойства

  • Устойчивость (Robustness): трудно построить шифртекст, который декапсулируется в тот же ключ с двумя разными закрытыми ключами.
  • Перспективная секретность (Forward secrecy): если закрытый ключ dk будет скомпрометирован в будущем, прошлые сессии остаются безопасными (требует эфемерных ключей).

6.3 KEM vs PKE: почему KEM

PKE (Шифрование с открытым ключом)

PKE шифрует произвольные сообщения: \(\text{Enc}(ek, m) \to c\). Проблема в том, что если сообщение \(m\) имеет предсказуемую структуру (короткий пароль, номер карты), противник может использовать атаки с низкой энтропией или атаки на оракул дополнения (Блейхенбахер).

KEM: разделение ролей

KEM не шифрует пользовательские сообщения. Он генерирует симметричный ключ с высокой энтропией и инкапсулирует его:

\[ \text{Система} = \underbrace{\text{KEM}}_{\text{обмен } K} + \underbrace{\text{AES-GCM}}_{\text{шифрование данных на } K} \]

Преимущества:

  • Ключ \(K\) всегда псевдослучаен → нет атак с низкой энтропией.
  • Не требуется сложное дополнение для пользовательских сообщений.
  • \(K\) используется с симметричным шифром (DEM) для шифрования реальных данных.

6.4 Интуитивный пример: KEM из Диффи-Хеллмана

До ML-KEM наиболее используемым KEM был построенный на основе Диффи-Хеллмана. Этот пример помогает понять структуру.

Публичные параметры: простое число \(p\), генератор \(g\) группы \(\mathbb{Z}_p^*\).

Алиса
  1. Выбирает секретное \(a\)
  2. Вычисляет \(A = g^a \bmod p\)
A → ← B
Боб
  1. Выбирает секретное \(b\)
  2. Вычисляет \(B = g^b \bmod p\)
\[ \begin{aligned} \text{Алиса вычисляет: } & K = B^a \bmod p = g^{ab} \bmod p \\ \text{Боб вычисляет: } & K = A^b \bmod p = g^{ab} \bmod p \end{aligned} \]

Числовой пример: \(p = 17\), \(g = 3\), \(a = 5\).

  • \(ek = 3^5 \bmod 17 = 5\)
  • Боб выбирает \(b = 7\): \(c = 3^7 \bmod 17 = 11\), \(K = H(5^7 \bmod 17) = H(10)\)
  • Алиса декапсулирует: \(K = H(11^5 \bmod 17) = H(10)\) ✓

6.5 Преобразование Фуджисаки-Окамото (FO)

Проблема: от CPA к CCA2

Имея PKE, безопасный только в смысле CPA, как построить KEM IND-CCA2? Ответ — преобразование FO.

Центральная идея

  • Детерминированное шифрование: случайность, используемая при шифровании, детерминированно выводится из сообщения через хеш. Если шифртекст изменён, повторное шифрование даёт что-то другое.
  • Верификация при расшифровке: вместо прямого расшифровывания, расшифрованное сообщение снова шифруется и сравнивается с полученным шифртекстом. Если не совпадают → неявное отклонение.

Упрощённая схема FO

\[ \begin{aligned} \text{Encaps}(ek): & \quad m \leftarrow \{0,1\}^\ell, \ (K, r) = G(m), \ c = \text{Enc}(ek, m; r) \\ \text{Decaps}(dk, c): & \quad m' = \text{Dec}(dk, c), \ (K', r') = G(m'), \ c' = \text{Enc}(ek, m'; r') \\ & \quad \text{return } \begin{cases} K' & \text{если } c' = c \\ K_{\text{reject}} & \text{иначе} \end{cases} \end{aligned} \]

Где \(K_{\text{reject}} = H(z \| c)\) с фиксированным секретным \(z\). Это "неявное отклонение" не позволяет противнику использовать ошибки как оракул.

6.6 От K-PKE (CPA) к ML-KEM (CCA2)

В ML-KEM двухуровневая структура такова:

ML-KEM (IND-CCA2)
└── K-PKE (IND-CPA) + преобразование FO
    └── задача MLWE

ML-KEM.Encaps(ek)

m ← Random(32)                  // случайное 256-битное сообщение
(K̄, r) = G(m ‖ H(ek))          // SHA3-512: K̄ = первые 32 байта, r = последние 32 байта
c = K-PKE.Encrypt(ek, m, r)     // детерминированное шифрование со случайностью r
K = KDF(K̄ ‖ H(c))              // финальный ключ
return (K, c)

ML-KEM.Decaps(dk, c)

(dk_PKE, ek, h, z) = dk         // h = H(ek), z = запасной секрет
m' = K-PKE.Decrypt(dk_PKE, c)   // попытка расшифровки
(K̄', r') = G(m' ‖ h)           // пересчёт
c' = K-PKE.Encrypt(ek, m', r')  // верификационное повторное шифрование
если c' == c:
    K = KDF(K̄' ‖ H(c))         // расшифровка успешна
иначе:
    K = KDF(z ‖ H(c))           // запасной вариант: псевдослучайный ключ
return K

Важные детали: Закрытый ключ dk также содержит ek, чтобы можно было выполнить повторное шифрование. Сравнение c' == c должно выполняться за постоянное время.

6.7 KEM в реальном протоколе: TLS 1.3

Клиент (Боб)
Сервер (Алиса)
ClientHello (поддерживает ML-KEM-768)
ServerHello + Сертификат + KeyShare (ek)
KeyShare (c) + Finished (MAC с K)
Finished (MAC с K)

Гибрид X25519 + ML-KEM

На практике TLS 1.3 использует гибридный подход:

\[ K_{\text{TLS}} = \text{HKDF}(K_{\text{X25519}} \,\|\, K_{\text{ML-KEM}}) \]

Это гарантирует безопасность, если хотя бы одна из двух схем сохраняется. Группа X25519MLKEM768 уже развёрнута в Chrome 131+.

6.8 Общая структура потока KEM

Полный поток Алиса (Получатель) / Боб (Отправитель)

  1. Алиса: KeyGen() генерирует \((ek, dk)\). Публикует \(ek\).
  2. Боб: Получает \(ek\). Выполняет Encaps(ek):
    • Генерирует случайное \(m\)
    • \((\bar{K}, r) = G(m \| H(ek))\)
    • \(c = \text{K-PKE.Encrypt}(ek, m, r)\)
    • \(K = \text{KDF}(\bar{K} \| H(c))\)
  3. Боб: Шифрует данные с помощью AES-256-GCM, используя \(K\) и случайный одноразовый номер.
  4. Боб: Отправляет \((c, \text{nonce}, \text{ciphertext}, \text{tag})\) Алисе.
  5. Алиса: Выполняет Decaps(dk, c) для восстановления \(K\).
  6. Алиса: Расшифровывает данные с помощью AES-256-GCM. Если тег не совпадает, отбрасывает сообщение.

Двойная защита: Если c изменён, Decaps возвращает псевдослучайный ключ (\(K_{\text{reject}}\)). Даже если противник угадает этот ключ, тег AEAD AES-GCM не сойдётся, гарантируя целостность.
